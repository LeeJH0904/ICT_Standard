# 생성형 AI 활용 단계 및 검증 방식 — 뼈대 (F-189)

> **상태: 뼈대만 존재한다. 본문은 아직 없다.** 아래 §2의 각 절은 "무엇을 채워야
> 하는가"만 적혀 있고 내용은 비어 있다 — 개발이 아직 단계 7(`web/`)·단계 8(보드
> 3종 실물 통합) 중이라, 단계 전체를 아우르는 서술을 지금 쓰면 마지막 두 단계의
> 실적을 다루지 않은 채 "작성 완료"로 보일 위험이 있다(CLAUDE.md §1-1 "명백한
> 허위" 조항과 같은 원칙 — 아직 없는 결과를 있는 것처럼 적지 않는다).
> **작성 시점: 단계 8 완료 직후.** `fix_log/F-189_llm_draft_always_fallback.md`가
> 이 결정의 처리 기록이다.

## 1. 이 문서가 답해야 하는 질문

정본은 공고문 1차 평가 배점표의 「생성형 AI 활용성」(15점) 항목이다.

> "기획, 코드 작성, UI 설계, 데이터 정리, 기능 등 **바이브코딩이 수행한 단계 및
> 역할**과 산출물(소스코드 검증 등) **검토 방식**"

즉 이 문서가 증명해야 하는 것은 **"배포된 앱이 런타임에 생성형 AI를 호출하는가"가
아니라 "이 제출물을 만드는 개발 과정에서 생성형 AI(바이브코딩)를 어떤 단계·역할로
썼고, 그 산출물을 어떻게 검증했는가"** 다. `project_docs/demo/시연_시나리오.md:285`도
"AI가 만든 코드를 어떻게 검증했나"의 근거를 이 문서로 지정해 두었다.

이 프로젝트 자체는 두 층위에서 생성형 AI와 관련이 있고, 이 문서는 **둘 다** 다뤄야
한다 — 섞으면 안 된다(§3.6이 "표준결함"과 "미규정 결정"을 분리해 기록하는 것과 같은
원칙).

| 층위 | 무엇 | 이 문서에서의 절 |
|---|---|---|
| A. 개발 과정 | 이 리포 자체를 Claude Code(바이브코딩)로 만든 과정 | §2.1~§2.3 |
| B. 앱 기능 | `backend/services/mms.py`의 `exec_method='llm_draft'` — 사용자에게 보이는 생성형 AI 기능 | §2.4 |

## 2. 채워야 할 절 (목차 + 각 절이 담아야 할 내용)

### 2.1 개발 단계별 AI 역할 정리표

`project_docs/dev/개발_착수_지시서.md`가 정의한 단계 0~11(또는 완료 시점 기준 실제
단계 수)을 행으로, **기획 / 코드 작성 / UI 설계 / 데이터 정리 / 기능 구현** 을 열로
하는 표. 각 칸은 "AI가 무엇을 했는가"를 한 문장으로 — 예: "단계 1(`contracts/`
이관): 골든 벡터는 사람이 손으로 만든 레이아웃(`golden_layout.py`)을 AI가 코드로
결합만 했다"처럼, **AI가 자율적으로 만든 것과 사람이 값을 확정한 것을 구분**해서
적는다(§3.6 "손으로 만들고 코드로 검증한다" 원칙과 같은 이유 — 자기 검증 순환을
피하려면 어디가 사람 결정이고 어디가 AI 실행인지 갈라야 한다).

### 2.2 산출물 검증 방식

- 단계별 출구 명령 전체 목록과 그 성격(호스트 유닛테스트 / 골든 벡터 대조 / 설계
  문서-구현 교차 검증 / fault injection) — `개발_착수_지시서.md` §6.1 인용
- `fix_log/` 워크플로우 — GPT가 코드·문서를 교차 검증해 `신규`로만 추가하고
  (`GPT.md`가 역할 지시서), Claude가 재현 → 확인 → 수정완료/기각/보류/이관 하는
  절차(CLAUDE.md §11). 완료 시점의 총 처리 건수(`fix_log/bug_fix_list.md` 현황
  표 인용)
- `tools/*_verify.py` · `project_docs/**/*_verify.py` 검증기 총 개수와 각각이
  "구현이 설계와 같은가"/"설계가 표준과 같은가" 중 무엇을 보는지(CLAUDE.md §2
  디렉터리 구조 설명과 동일 구분)

### 2.3 사람 검토 지점

- CLAUDE.md §1-7 "미승인 AI 규칙이 구동기로 전달되는 경로를 만들지 않는다" —
  이게 지켜졌다는 구조적 증거(`schema.sql`의 승인 게이트 CHECK·트리거 8종,
  `tools/gate_e2e.py`)
- `contracts/` 변경 절차(§5) — AI가 표준 조항 근거를 대고 **사용자가 확인한
  뒤에만** 계약을 바꾼 사례들(F-120의 N 상한 등, 실제 승인 기록 인용)
- 이번 세션의 F-186·F-190·F-189 자체도 예시다 — 설계 문서와 실제 구현이
  갈리는 지점을 AI가 멈추고 사용자에게 물은 뒤(`AskUserQuestion` 사용 기록)
  진행한 사례로 인용

### 2.4 앱 기능으로서의 생성형 AI — `mms.py` `exec_method='llm_draft'`

- `control_rule.origin`(요청자 의도) / `generation`(서버가 실제로 실행한 결과)을
  분리한 설계(F-083) — 이 구분이 있어야 "AI를 썼다고 주장하지만 실제로는 안
  썼다"는 상태가 데이터로 드러난다는 점을 설명
- 이 참조 구현이 **실제 외부 생성형 AI 제공자를 연동했는지 여부**를 있는 그대로
  적는다 — 연동했다면 어떤 제공자·호출 방식(예: `dms.py`의 KMA 연동과 같은
  `urllib` 기반, 키 부재 시 자동 폴백)을, 연동하지 않았다면 그 이유(오프라인
  기본 경로 원칙 CLAUDE.md §7, 의존성 최소화 §4.1, 채점 기준이 런타임 호출을
  요구하지 않는다는 §1의 판단 근거)를 적는다. **이 결정은 단계 8 완료 시점에
  최종 확정한다** — 그 전까지는 F-189 처리 기록이 임시 근거다.
- `HIGH_TEMP_THRESHOLD_C` 상수 제거와 `control_model.output_spec.recommend_action`
  데이터 기반 전환(F-190)도 여기서 같이 설명 — "서버가 장치 종류를 하드코딩하지
  않는다"는 §0 주장 3과 "AI/threshold 모델을 데이터로 등록한다"는 같은 원칙의
  적용이라는 점

### 2.5 한계

- 다루지 않는 것을 명시한다(예: 실시간 스트리밍 LLM 호출, 프롬프트 버전 관리
  등 — 이 참조 구현의 범위 밖이면 왜 밖인지 한 줄로)
