## 근거

`CLAUDE.md` §6.2는 검증 대상 하나의 자기 일치가 아니라 독립 입력과의 의미 대조를 요구한다. 화면 설계서 §11도 화면↔API 대응과 금지 계약을 검사한다고 선언한다.

## 현상

현재 실행은 다음 불일치가 실제 파일에 존재하는데도 40/40, 종료코드 0이다.

- 화면 설계서는 OpenAPI “경로 21종”이라 적지만 실제는 경로 20개·오퍼레이션 21개다. 검증기는 출력에 `경로 20`을 찍고도 존재 여부만 보아 PASS한다.
- 파일 구조에는 없는 `static/app.js`를 §1에서 로드한다고 적는다.
- 코드 예시는 `dev.subtype_name`을 읽지만 `Device` 스키마의 필드는 `subtype`이다.
- 기능 2 주입 오퍼레이션, `Frame.fields`/`judgement`, 기능 3 모델 실행 오퍼레이션, 설정용 FrameBuilder는 검사하지 않는다.

## 영향

화면별 operationId 목록의 존재만 맞으면 사용자 흐름이 구현 불가능해도 녹색 결과가 유지된다. “설계 문서 완료” 판정의 회귀 근거로 사용할 수 없다.

## 재현

```text
python project_docs/web/web_verify.py
→ 경로 20을 출력하면서 40/40 통과, exit 0
```

## 제안

화면의 동작별 입력·출력 필드를 OpenAPI 스키마와 대조하고, 브라우저 유발 동작은 호출 가능한 오퍼레이션을 반드시 갖게 한다. 파일 구조·필드명·경로/오퍼레이션 수치도 실제 입력에서 재산출한다. 기능 2·3·설정 화면의 결함 주입 반례를 고정한다.
