## 근거

공고문 평가기준 「생성형 AI 활용성」은 "산출물(소스코드 검증 등) 검토 방식"을 평가하고, 「구현완성도·서비스 가능성」은 실제 작동·오류 대응을 평가한다.

0943 6.1.2는 GCG→노드 Notify의 ACK를 요구하고, 그림 8-45·8-46은 Notify의 ACK·재전송 흐름을 정의한다.

## 현상

검증기는 상태표에서 상태 이름이 다이어그램에 존재하는지와 각 상태에 나가는 행이 하나 이상 있는지만 본다. 사건·동작의 필수 집합은 검사하지 않는다. 숫자도 선택된 몇 표만 파싱하므로 요약·Flash 표의 값은 검증 대상이 아니다.

독립 메모리 변형에서 다음 세 반례가 모두 **26/26, exit 0**이었다.

- §0의 `재시도 가능 3종 / 불가 7종`을 `99종 / 0종`으로 변경
- `RUNNING | G→N Notify 수신 | ... | ACK 회신` 전이행 삭제
- `subtype_registry.h`의 `17종`을 `99종`으로 변경

## 영향

F-071·F-073처럼 표준 동작이나 핵심 수치가 깨져도 "펌웨어 설계서 검증 26/26"이라는 녹색 결과가 유지된다. 검증 결과가 설계 완결성의 증거로 쓰이지 못한다.

```text

→ 세 경우 모두 26/26, exit 0
```

## 제안

상태표는 최소 필수 전이 집합과 대조하고, 요약의 재시도 수·Subtype 개수·구조체 포인터 산술을 독립 계약에서 재산출한다. 검사 이름이 "문서 전반 일관"이면 한 문자열 존재가 아니라 모든 관련 표기를 검증해야 한다.
