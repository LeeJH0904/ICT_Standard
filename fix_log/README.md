# fix_log — 발견 사항 기록 규약

> **검증자(검증) ↔ 작업자(수정) 사이의 계약 문서.** 양쪽 모두 이 규약을 따른다.
> 검증자는 발견을 여기 기록하고, 작업자는 여기서 읽어 처리한다.

---

## 1. 구조

```
fix_log/
├── README.md            ← 이 파일. 양식·명명·분류·상태 정의
├── bug_fix_list.md      ← 인덱스. 모든 항목이 여기 1줄로 존재한다
├── _TEMPLATE.md         ← 개별 건 작성 양식
└── F-013_<슬러그>.md     ← 개별 건 (F-013부터 신규)
```

**원칙: 인덱스는 하나뿐이다.** 모든 발견은 `bug_fix_list.md`에 한 줄이 있어야 하며, 개별 파일은 그 줄의 상세다. 인덱스에 없는 개별 파일은 존재해서는 안 된다.

---

## 2. ID 및 파일명

| 규칙 | 내용 |
|---|---|
| ID | `F-###` (Finding). 3자리 0채움. **번호는 재사용하지 않는다** — 기각된 항목의 번호도 비워둔다 |
| 파일명 | `F-###_<영문_슬러그>.md` — 예: `F-013_frame_msgid_overflow.md` |
| 다음 번호 | `bug_fix_list.md`의 마지막 ID + 1. **F-001 ~ F-012는 사용 중** |
| 슬러그 | 소문자 영문 + 밑줄. 3~5단어. 무엇이 문제인지 드러날 것 |

---

## 3. 분류 — 처리 방식이 갈리는 축

| 분류 | 의미 | 처리 |
|---|---|---|
| `요건위반` | 공고문 위반 (실격·감점 사유) | **최우선.** 즉시 수정 |
| `코드버그` | 구현 오류 · 계층 위반 · 테스트 결함 | 수정 |
| `문서불일치` | 명세서 ↔ 코드 ↔ 표준 간 어긋남 | 어느 쪽이 옳은지 **판정 후** 수정 |
| `표준결함` | TTA 표준 원문 자체의 문제 | **고칠 수 없다.** `docs/standard-findings.md`로 이관해 기획서 자산으로 활용 |

> **`표준결함`과 나머지를 혼동하지 마라.** 표준결함은 우리 잘못이 아니고 수정 대상도 아니다. 오히려 프로젝트의 차별화 자산이다.

---

## 4. 심각도

`GPT.md` §4.4와 동일하다.

| 등급 | 기준 |
|---|---|
| `치명` | 실격 사유 / 표준 위반 / 핵심 주장 붕괴 / 재현 불가 |
| `오류` | 표준 원문과 불일치 / 코드 버그 / 계약 위반 |
| `위험` | 지금은 동작하나 무너질 수 있음 / 근거 부족 |
| `제안` | 개선 여지. 필수 아님 |

---

## 5. 상태

| 상태 | 의미 | 기록 주체 |
|---|---|---|
| `신규` | 검증자가 보고. 작업자 미확인 | 검증자 |
| `확인` | 작업자가 재현·검증함. 수정 대기 | 작업자 |
| `수정완료` | 코드·문서에 반영 완료 | 작업자 |
| `기각` | 오탐 또는 의도된 설계. **사유 필수** | 작업자 |
| `보류` | 타당하나 일정상 미룸. **사유 및 재검토 시점 필수** | 작업자 |
| `이관` | `표준결함` → `docs/standard-findings.md`로 옮김 | 작업자 |

---

## 6. 처리 순서 (작업자)

```
요건위반  →  코드버그  →  문서불일치  →  표준결함(이관)  →  제안
```

같은 분류 안에서는 심각도 순: `치명` → `오류` → `위험` → `제안`

---

## 7. 개별 파일 양식

`_TEMPLATE.md`를 복사해 쓴다. 필수 항목은 다음과 같다.

| 절 | 필수 | 작성 주체 |
|---|---|---|
| 헤더 표 (심각도·분류·대상·발견일·상태) | ✅ | 검증자 |
| 근거 | ✅ | 검증자 — **표준 조항 번호 또는 공고문 조항 + 원문 인용** |
| 현상 | ✅ | 검증자 |
| 영향 | ✅ | 검증자 |
| 재현 | 코드버그일 때 ✅ | 검증자 |
| 제안 | 선택 | 검증자 |
| 작업자 처리 기록 | ✅ | 작업자 |

**근거 없는 항목은 기록하지 마라.** 근거를 못 찾으면 심각도를 `제안`으로 낮추고 "확인 불가"라고 명시한다.

---

## 8. 기존 12건에 대하여

`F-001` ~ `F-012`는 전부 `표준결함`이며 **개별 파일을 만들지 않는다.** 상세 서술이 이미 설계 명세서에 존재하기 때문이다.

| 정본 위치 | 담당 |
|---|---|
| `project_docs/siap/SIAP_메시지_명세서.md` §6 | F-001 ~ F-009 (0943) |
| `project_docs/db/DB_스키마_설계서.md` §5 | F-010 ~ F-012 (1369-Part1) |
| `docs/standard-findings.md` | 개발 착수 후 위 둘을 통합한 최종 정본 |

`bug_fix_list.md`는 이들에 대해 **인덱스 역할만** 한다. 상세를 여기 중복 기록하지 마라 — 두 곳이 어긋난다.

---

## 9. 워크플로

```
검증자                                 작업자
 │                                       │
 ├─ 검증 → 발견                          │
 ├─ bug_fix_list.md 에 행 추가 (상태 신규)│
 ├─ F-###_*.md 생성 (표준결함 제외)       │
 │                                       │
 │                          세션 시작 ───┤
 │                     '신규' 항목 확인 ──┤
 │                     재현·검증 → 확인 ──┤
 │                     수정 → 수정완료 ───┤
 │                     오탐 → 기각(+사유)─┤
 │                                       │
 └─ 다음 검증 시 '기각' 사유를 읽고        │
    같은 지적을 반복하지 않는다            │
```

**검증자는 상태 컬럼을 `신규` 외의 값으로 바꾸지 않는다.** 상태 전이는 작업자만 한다.
**작업자는 인덱스의 행을 삭제하지 않는다.** 상태만 갱신한다 — 기록이 남아야 중복 보고를 막는다.
