## 근거

대조표 §0.2는 `✅ 충족`을 “코드·스키마에 대응이 존재한다”로 정의한다. 그러나 다음 필수 또는 필수(능력) 행은 제시된 스키마·API·모듈 계약을 역추적해도 요구 전체를 수행하는 경로가 닫히지 않는다.

| 조항 | 표준 요구 | 대조표 근거의 공백 |
|---|---|---|
| 6.1-1 | 장치 등록·변경·삭제·연결 | `ems.on_node_connect()`와 테이블만 제시한다. `ems.py` 계약과 OpenAPI에는 삭제 진입점이 없고 노드·장치 API는 조회뿐이다. |
| 6.3-1 | 모델·알고리즘 등록 규약 제공 | 인용한 `POST /api/v1/rules`는 `createRuleDraft`로 제어 규칙 초안을 만들 뿐 `control_model`을 등록하지 않는다. |
| 6.3-2 | 모델 메타정보 등록·수정 | `control_model` 컬럼은 저장 형태일 뿐 등록·수정 API나 `mms.py` 진입점이 없다. |
| 6.3-6 | 메타정보의 실행 방법에 따라 모델 구동·출력 수신 | `control_execution`은 장치 제어 명령 실행 이력이며 모델 실행이 아니다. `mms.py` 계약에도 모델 실행 진입점이 없다. |
| 6.4-2 | 수집 주기와 구역을 지정해 환경 데이터 수집 | 근거의 `device_install_info.zone` 컬럼은 존재하지 않는다. 실제 스키마는 `install_location`만 있고 구역별 수집 설정 경로가 없다. |
| 6.4-3 | 정해진 시간에 환경 데이터가 미수집되면 알림 | 노드 `Keep Alive` 만료는 노드 생존성 검사다. 노드는 살아 있고 `NOTI_DEVICE_VALUE`만 멈춘 반례를 잡지 못하며, 장치별 Period·마지막 측정시각 기반 감시 계약이 없다. |

부속서 A.1-1·A.2-1과 A.1-4도 같은 근거를 재사용하므로 주 요구사항을 보완하지 못한다.

## 현상

대조표는 위 6개 행을 모두 `✅`로 표시하고 §1.7의 충족 24건에 포함한다. 구현 코드는 아직 작성 전이며, 현재 설계 산출물에도 위 동작을 완결하는 진입점이나 API가 없다.

## 영향

필수 요구가 구현 계획에서 누락된 채 “충족”으로 고정될 수 있다. 특히 장치 삭제, 모델 등록·실행, 구역별 수집, 환경 데이터 누락 경보는 이후 구현 단계에서 담당 모듈과 API가 없어질 가능성이 높다.

## 제안

- 현재 단계의 판정 의미를 “설계 대응/구현 완료”로 분리한다.
- 6.1-1에는 장치 삭제 계약, 6.3-1·2·6에는 모델 등록·수정·실행 계약을 추가한다.
- 6.4-2에는 구역 식별·설정 경로, 6.4-3에는 장치별 수집 기한 감시와 알림 경로를 추가한다.
- 근거가 생기기 전까지 해당 행은 `⚠️ 부분`으로 낮추고 부속서의 연동 판정도 함께 재산출한다.
