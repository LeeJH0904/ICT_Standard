# F-053 · API 쓰기 엔드포인트가 DB 단일 쓰기 주체 원칙과 충돌함

| 항목 | 값 |
|---|---|
| 심각도 | 오류 |
| 분류 | 문서불일치 |
| 대상 | `project_docs/api/API_명세서.md:43-68`, `project_docs/arch/아키텍처_설계서.md:283-292` |
| 발견일 | 2026-08-03 |
| 상태 | 수정완료 |

## 근거

아키텍처 §4.4 — DB 쓰기 주체는 "I/O 스레드 단독", API 스레드는 "읽기 전용 (제어 실행 기록은 예외)"

API 명세서 §3은 쓰기 오퍼레이션 4건이 이 원칙을 지킨 결과라고 주장한다.

## 현상

쓰기 4건 중 `POST /rules`는 `control_rule`을 INSERT하고 `/rules/{id}/approve`는 같은 테이블을 UPDATE해야 한다. 둘은 제어 실행 기록 예외가 아니다. I/O 스레드로 넘기는 별도 큐·트랜잭션 경로도 API 명세와 아키텍처에 정의되지 않았다.

## 영향

문서대로 직접 구현하면 API 스레드가 DB 쓰기 단독 소유 규칙을 위반한다. 반대로 I/O 스레드에 위임하면 현재 API 동작·응답·실패 계약이 빠져 있다. SQLite 쓰기 경합 제거라는 동시성 설계 근거가 무너진다.

## 제안

규칙 생성·승인도 API 쓰기 예외로 명시해 WAL 트랜잭션 정책을 정하거나, 모든 DB mutation을 전용 쓰기 큐로 직렬화하도록 아키텍처를 변경한다.
