# F-104 · where.py가 avr-size 실측값을 예산과 비교하지 않음

| 항목 | 값 |
|---|---|
| 심각도 | 오류 |
| 분류 | 코드버그 |
| 대상 | `tools/where.py:286-321` |
| 발견일 | 2026-08-08 |
| 상태 | 수정완료 |

## 근거

개발 착수 지시서 §3.10 출구 ①은 보드 3종을 빌드하고 `avr-size` 실측값이 펌웨어 설계서 §7의 예산 안인지 확인하도록 요구한다.

F-098 처리 기록도 단계 8에서 보드 3종의 `make`와 `avr-size`를 실제 실행하도록 고쳤다고 기록한다.

## 현상

`_build_and_size()`는 `make` 성공과 `.elf` 존재를 확인한 뒤 `avr-size`를 실행하지만, 출력의 text·data·bss 값을 파싱하거나 설계 예산과 비교하지 않는다. 명령의 종료 코드가 0이면 크기와 무관하게 `avr-size 실측`을 통과로 반환한다.

가짜 `.elf`와 성공하는 실행 함수를 주입하고 `avr-size` 출력에 text·data·bss 각각 999,999,999를 넣었다. 두 결과는 모두 `True`였고 과대 크기는 차단되지 않았다.

F-098의 기존 누락이었던 단계 2c 전수 실행과 단계 7·8의 MANUAL 항목은 이번 재검증에서 각각 7건·3건·8건으로 확인됐다. 이 건은 새로 추가된 크기 실행 경로가 출구의 절반인 예산 비교를 구현하지 않은 별도 반례다.

## 영향

보드 바이너리가 설계 메모리 예산을 초과해도 `where.py`는 해당 자동 검사에 OK를 표시한다. 단계 8에는 실측 로그 MANUAL 항목이 있어 현재 전체 단계를 자동 통과시키지는 않지만, 보드 크기 출구 자체의 판정은 거짓이다.

## 재현

1. 임시 보드 디렉터리에 `Makefile`과 `.elf` 파일을 둔다.
2. `_run()`이 `make`에는 성공을, `avr-size`에는 text·data·bss가 각각 999,999,999인 출력과 성공을 반환하도록 주입한다.
3. `_build_and_size()`를 호출한다.
4. 실제 결과: `make=True`, `avr-size 실측=True`.

## 제안

보드별 `avr-size` 출력 형식을 파싱해 플래시와 SRAM 사용량을 펌웨어 설계서 §7의 정본 예산과 비교한다. 파싱 실패, 보드별 도구 형식 차이, 예산 초과는 모두 실패로 판정한다.
