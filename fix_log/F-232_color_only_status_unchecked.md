# F-232 · 동적 위반 표시가 색상뿐이어도 웹 출구가 통과

| 항목 | 값 |
|---|---|
| 심각도 | 오류 |
| 분류 | 코드버그 |
| 대상 | `project_docs/web/web_verify.py:L196-L198` · `tools/web_live_verify.py` · `project_code/web/verify.html:L94-L100` |
| 발견일 | 2026-08-13 |
| 상태 | 수정완료 |

## 근거

공고문 1차 평가 「공공편익·포용성」 — “사회적 약자·디지털 취약계층 접근성 등.” 화면 설계서 §8.2는 위반 프레임에 적색뿐 아니라 `⚠`·“위반”·코드명·조항을 함께 주도록 정하고, §8.1은 색에만 의존하면 기능 2 자체가 무의미해진다고 판정한다.

## 현상

`web_verify.py`는 설계서의 색 의존 금지표가 6행이고 각 행의 “함께 주는 것” 셀이 비지 않았는지만 검사한다. 실제 `verify.html`의 동적 렌더 결과는 검사하지 않는다. `web_live_verify.py`도 CSS 명도대비는 계산하지만 상태 아이콘·문자 존재를 확인하지 않는다.

현재 제품은 프레임 목록에 `${m.icon}`과 `${m.text}`를 출력해 올바르다. 그러나 그 두 보간을 제거하고 프레임 ID만 남기면 `normal`·`violation`·`alert` 클래스의 색만 상태를 구분하게 되는데도 두 출구가 통과한다.

## 영향

색각 이상 사용자가 프레임 목록에서 정상·위반·알림을 구분할 수 없는 회귀가 접근성 출구를 통과한다. 화면 설계서가 기능 2 성립 조건이라고 한 보장을 검증기가 증명하지 못한다.

## 재현

제품 파일을 수정하지 않고 `pathlib.Path.read_text` 결과에서 `verify.html`의 `${m.icon} ${f.id} — ${m.text}`를 `${f.id}`로 메모리 치환했다. 두 검증기가 각각 파일을 읽을 때 치환된 횟수는 2회였다.

```text
MUTATIONS=2
python project_docs/web/web_verify.py -> 68/68, exit 0
python tools/web_live_verify.py       -> 23/23, exit 0
```

## 제안

동적 카드·목록을 실제 DOM으로 렌더해 상태별 아이콘·문자·접근 가능한 이름을 검사한다. 정적 검사만 유지한다면 최소한 `frameListItemHtml()`의 세 판정 모두에 색 외 상태 문자가 존재하는지를 구현 파일에서 확인한다.
