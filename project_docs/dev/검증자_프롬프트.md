# 독립 검증자 프롬프트

> 개발 단계마다 독립 검증자에게 넣을 프롬프트를 고정한다.
> **역할 분리의 정본은 `ROLES.md`, 역할·원칙·보고 형식의 정본은 `GPT.md`, 기록 규약의 정본은 `fix_log/README.md`다.**
> 이 문서는 그 둘을 개발 단계에 맞게 **호출하는 방법**만 정한다.
>
> 검증: `python project_docs/dev/dev_verify.py`

---

## 0. 제품명이 아니라 현재 환경의 능력으로 범위를 정한다

사용 중인 AI나 도구 이름으로 검증 가능 범위를 가정하지 않는다. 검증자는 세션마다 아래 능력과 접근 권한을 실제로 확인한다.

| 영역 | 판정 원칙 |
|---|---|
| 저장소와 표준 원문 | 읽기 권한이 있으면 직접 읽는다. 없으면 검증 불가로 보고한다 |
| 파이썬 검증기 | 명령 실행 권한과 Python이 있으면 직접 실행한다 |
| C 컴파일·호스트 테스트 | 명령 실행 권한과 `gcc`가 있으면 직접 실행한다 |
| 표준 원문 그림 | 이미지 해석 기능과 원문 접근이 모두 있을 때만 판정한다 |
| 브라우저 렌더링 | 실제 브라우저 런타임으로 렌더링했을 때만 판정한다 |
| 실물 하드웨어 | 실제 장비에 접근했을 때만 판정한다 |

**실행 가능한 검사는 제출 로그로 대신하지 말고 직접 실행한다. 실행할 수 없는 검사는 이유와 함께 "검증 불가"로 남긴다.**
제출된 로그를 믿지 않는 것이 독립 검증의 핵심이다 — 로그는 위조하기 쉽고,
`0/0 통과` 같은 공백 통과도 로그만으로는 드러나지 않는다.

## 1. 환경 준비 (사용자가 검증 세션에 해줄 것)

| # | 준비 | 이유 |
|---|---|---|
| 1 | **저장소 폴더** 접근 권한 | 검증 대상 |
| 2 | (표준 원문은 **저장소 안** `표준 문서 md 파일/` 에 있다) | 유일한 정본. 폴더를 따로 연결하지 않아도 된다 |
| 3 | 쓰기 권한을 **`fix_log/` 로 한정** | 검증자가 코드를 고치면 독립 검증이 아니다 (`GPT.md` §7) |
| 4 | `python3` · `gcc` 사용 가능 여부 확인 | 안 되면 프롬프트의 "직접 실행" 항목을 "불가"로 보고하게 한다 |

> 네트워크가 막혀 있어도 된다. 표준 원문·공고문·진행보고서까지 **저장소 하나 안에** 있다.
> (`표준 문서 md 파일/` 은 개발·검증용이며 제출물에서는 제외한다 — `CLAUDE.md` §2.1)

## 3. 단계별 추가 지시

프롬프트 마지막 `[추가 지시]` 에 붙여넣는다. 각 단계에서 **가장 무너지기 쉬운 지점**만 골랐다.

### 단계 0 — 골격 · 오프라인 의존성

```text
- requirements.txt 의 3개(fastapi·uvicorn·pyserial) 외에 의존성이 늘지 않았는가.
- wheels/ 만으로 네트워크 없이 설치되는가. 직접 --no-index 로 설치해 보라.
  전이 의존성의 플랫폼별 휠(win_amd64 / manylinux)이 빠지지 않았는가 (F-029 의 재발).
- 저장소를 zip 으로 묶었을 때 200MB 이하인가. 실행파일 확장자가 0개인가.
- CLAUDE.md §2.1 제외 대상(표준 문서 md 파일/ · .omc/ · __pycache__/ · _to_delete/)이
  .gitignore 와 패키징 대상에서 빠져 있는가. 표준 원문 재배포는 제출물에 있으면 안 된다.
- tools/where.py 가 저장소가 비어 있을 때도 오류 없이 "단계 0"을 출력하는가.
- tools/run_all.py 가 검증기 목록을 하드코딩했는가 → 하드코딩이면 새 검증기를
  누락하게 되므로 지적하라 (F-094 와 같은 부류).
```

### 단계 1 — `contracts/` 이관

```text
- 이관 전후로 golden.jsonl 의 바이트가 바뀌지 않았는가. 해시로 대조하라.
- contracts/ 의 내용이 근거 없이 수정되었는가 → CLAUDE.md §5 절차 위반이다.
- fake_link.py 가 SiapLink Protocol 의 메서드를 전부 구현하는가.
  하나라도 빠지면 개발용 대역이 실제 링크와 갈린다.
- import 경로가 project_docs.contracts.* 에서 contracts.* 로 정리되었는가 (F-025).
```

### 단계 2a — `bitpack.c`

```text
- 범위 검사식이 nbits==32 에서 정의되지 않은 동작을 피하는가.
  1u << 32 형태가 남아 있으면 치명이다 (F-078 의 재발).
- 쓰기 2종이 실패할 때 버퍼를 건드리지 않는가. 부분 기록이 남으면 마스킹 래핑 금지가 무너진다.
- SIAP_WUR(warn_unused_result)이 쓰기 2종에 붙었는가. 반환형만 bool 로는 경고가 나오지 않는다.
- 직접 컴파일해 1~32bit 전 폭을 돌려보라. 경고가 하나라도 나오면 보고하라.
```

### 단계 2b — `siap_frame.c`

```text
- N 산출 분기가 contracts/frame.py 의 LAYOUT 과 줄 단위로 대응하는가.
  갈리는 지점이 곧 C↔Python 상호운용성이 깨지는 지점이다.
- 스트리밍 수신 윈도가 51 byte 를 넘지 않는가. 넘으면 SRAM 예산이 무너진다.
- 위반 8종의 clause_id 가 골든 벡터의 기대와 일치하는가.
- firmware/core/ 가 플랫폼 헤더를 include 하거나 보드 판별 매크로를 쓰는가
  → CLAUDE.md §1-5 위반이자 핵심 주장 1의 붕괴다.
- Value 32bit 범위 초과를 거부하는가. 마스킹 래핑이 남아 있으면 F-044 의 재발이다.
```

### 단계 2c — `node_state.c`

```text
- RES_SET_CONNECTION 오류 RSC 9종의 목적지 상태가 CLAUDE.md §3.5 표와 같은가.
  재시도 가능 2종 / 불가 7종 → HALTED. F-076 이 가장 재발하기 쉬운 지점이다.
- HALTED 에서 벗어나는 전이가 있는가 → 있으면 안 된다 (전원 재인가 외).
- FAULT 진입이 RUNNING 외의 상태에서도 가능한가 → 연결 승인 우회 경로가 된다 (F-072).
- 주기 알림 두 종류가 동시에 만료할 때 한쪽이 영구히 굶는가 (F-077).
- 재전송 시 Message Identifier 를 유지하는가. 새로 발번하면 노드가 중복 요청으로 처리한다 (F-041).
```

### 단계 3 — `siap/` 게이트웨이

```text
- C 인코더와 Python 인코더가 골든 53건 전량에서 같은 바이트를 내는가.
  tools/xcodec_verify.py 를 직접 실행하고, 그 스크립트가 정말 두 구현을 비교하는지 읽어라.
  한쪽 출력만 자기 자신과 비교하고 있으면 F-080 의 재발이다.
- 디코딩 실패가 예외를 던지는가 → violations 채운 Frame 을 반환해야 한다 (CLAUDE.md §4.3).
- 응답 매칭이 Node ID + Message Identifier + Message Type 세 조건인가 (F-046).
- send() 대기 상한이 Timeout x (Retry Count + 1) 인가 (F-041).
- siap/ 이 backend/ 를 import 하는가 → 계층 위반.
```

### 단계 4 — `sim/` · 전송 계층

```text
- socat 등 외부 도구에 의존하는가 → CLAUDE.md §1-8 위반. TCP 소켓만 쓴다.
- 네트워크 없이 --mode simulate / --mode replay 가 도는가. 직접 돌려보라.
- 주입 벡터 X01~X08 의 바이트가 golden.jsonl 과 정확히 같은가.
  다르면 영상에 나올 hex 와 제출 벡터가 갈려 공고문 "진위" 조항에 걸린다.
- replay 가 dir="rx" 만 주입하는가. tx 를 주입하면 기대 출력을 입력으로 되먹인다 (F-042).
- logs/ 에 random·math.sin 같은 무작위·주기함수 생성 데이터가 있는가 → 실격 사유다.
- logs/ 의 하드코딩 센서값이 golden.jsonl 원본과 다른가(값을 새로 지어냈는가)
  → 실격 사유다. golden.jsonl 원본 그대로의 재사용은 CLAUDE.md §1-1·§7 이
  정한 단계 4~7 한정 예외이며 실격이 아니다(F-148·F-152) — 단계 8 실측
  캡처로 교체될 때까지의 정식 중간 상태다. `sim/golden_log.py`·
  `sim/virtual_node.py` 가 이 예외를 구현한다.
```

### 단계 5 — `backend/` 저장 계층

```text
- ingest.handle(frame) 위쪽에 로직이 있는가 → 계층 위반. Frame 이 어디서 왔는지
  서비스 계층이 알면 안 된다.
- 정상 NEC 알림이 violations 에 들어가 격리되는가 → F-060 의 재발. alert 저장과
  ACK 회신이 사라진다.
- DB 연결이 backend/db.py 팩토리 밖에서 만들어지는가. foreign_keys=ON 이 빠진
  연결이 하나라도 있으면 참조 무결성이 그 경로에서 무너진다.
- project_code/backend/schema.sql 이 project_docs/db/schema.sql 과 같은가.
  갈리면 제약 98종의 근거가 사라진다.
- backend/ 가 siap/ 내부 심볼을 import 하는가 → 계층 위반.
```

### 단계 6 — `services/` · `api.py`

```text
- 실행 라우트 집합이 openapi.json 의 오퍼레이션 25종과 정확히 같은가.
  개수가 아니라 집합이다 (F-056).
- 쓰기 경로가 7건인가. 8번째가 생겼다면 승인 게이트 주변 검증 표면이 넓어진 것이다.
- 승인 없이 구동기 명령이 나가는 경로가 있는가. DB 트리거를 믿지 말고 HTTP 로 직접 뚫어보라.
  거부된 규칙 실행 / 승인 후 대상 변조 / action 이 NULL 인 승인 경유를 각각 시도하라.
- createRuleDraft 가 실제로 mms.run_model() 을 호출하고 generation 을 기록하는가.
  클라이언트 문장을 그대로 AI_DRAFT 로 저장하면 생성형 AI 활용 주장이 무너진다 (F-083·F-091).
- backend/ 에 노드·디바이스 종류 문자열이 하드코딩되었는가 → 핵심 주장 3의 붕괴.
- 표준 해석(위반 판정·코드→의미 매핑)이 서비스 계층에 다시 등장했는가 (CLAUDE.md §3.4).
```

### 단계 7 — `web/` 화면 4종

```text
- 외부 CDN·번들러·localStorage 를 쓰는가 → 화면 설계서 §10 금지.
- 미승인 규칙에 실행 버튼이 렌더링되는가. disabled 는 DOM 조작으로 풀린다 — 아예 없어야 한다.
- 위반 표시가 색에만 의존하는가 → 색각 이상 사용자에게 기능 2가 무의미해진다.
- 화면이 비트 언팩이나 위반 코드→한국어 매핑을 하는가 → 표준 해석이 두 곳에 생긴다.
- 화면이 fetch 하는 경로가 실행 라우트에 전부 존재하는가. 직접 실행해 대조하라.
- 렌더링을 확인할 수 없으면 "검증 불가"로 적어라. 된다고 가정하지 마라.
```

### 단계 8 — 보드 3종 바인딩 · 실물 통합

```text
- 3종 빌드에서 core/ 오브젝트 해시가 동일한가. 갈리면 "동일 응용계층"이 아니라
  "분기가 있는 공통 코드"이며 핵심 주장 1이 약해진다.
- 보드별 디렉터리 밖에 플랫폼 헤더가 있는가.
- avr-size 실측이 펌웨어 설계서 §3.5 예산(SRAM 40% 이하) 안인가.
  설계서의 추정치가 실측으로 교체되었는가.
- logs/ 의 캡처에 결측·위반·지연·오류알림이 실제로 들어 있는가.
  전부 정상 프레임뿐이면 "의도적으로 포함"이라는 서술이 거짓이 된다.
- 캡처 로그에 합성 흔적(균일 간격·사인파 형태의 값)이 있는가 → 실격 사유다.
```

## 4. 재검증 회차 (수정 반영 후)

작업자가 지적을 처리한 뒤 같은 단계를 다시 볼 때는 §2 프롬프트에 아래를 덧붙인다.

```text
[재검증]
  직전 회차에서 당신이 올린 F-### 항목들의 처리 결과를 확인하라.
  ① 상태가 `수정완료` 인데 코드가 그대로인 항목이 있는가.
  ② 수정이 지적한 범위만 덮고 같은 부류의 다른 곳은 그대로인가.
     이 프로젝트의 지난 라운드들에서 새 지적의 대부분이 "직전 수정이 남긴 빈틈"이었다
     (정확한 라운드 수는 `fix_log/bug_fix_list.md`의 처리 이력을 그 자리에서 센다 — F-100).
  ③ 수정으로 새로 생긴 검사가 실제로 반례를 잡는가. 고친 것을 되돌려 보고
     그 검사가 실패로 뒤집히는지 직접 확인하라. 뒤집히지 않으면 그 검사는 장식이다.
  ④ 상태가 `기각`·`보류` 인 항목의 사유에 동의하는가. 동의하지 않으면
     새 ID 로 올리되 기존 번호를 인용하고 사유가 왜 불충분한지 근거를 대라.
```

## 5. 이 프롬프트가 노리는 것

지난 여러 라운드에서 가장 무거웠던 지적 넷은 전부 **검증기 자신의 결함**이었다
(정확한 라운드 수는 `fix_log/bug_fix_list.md`의 처리 이력을 그 자리에서 센다 — F-100).

| 라운드 | 결함 | 형태 |
|---|---|---|
| F-074 | 초안 검증기 26/26 이 필수 전이 삭제를 통과 | 이름의 존재만 검사 |
| F-080 | 검증기가 대조표 한 파일만 읽음 | 자기 자신과의 일치만 검사 |
| F-089 | 화면 검증기가 40/40 으로 거짓 통과 | 값을 읽고 대조하지 않음 |
| F-095 | 자체 JSON Schema 검사기가 키워드 미구현 | 미구현 문법이 통과로 바뀜 |

그래서 §2 `[3]①` 에 **"이 검사를 통과하면서 틀린 코드를 실제로 만들어 보여라"** 를 넣었다.
코드의 결함보다 **검사의 결함**을 찾는 것이 이 프로젝트에서 더 값이 나갔다.
