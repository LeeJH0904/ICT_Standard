## 1. 단계를 11개로 나눈 기준

**"이 단계가 끝나면 지금까지 못 돌던 명령 하나가 돌고 통과한다."**

이 기준을 쓰지 않으면 단계 완료가 "구현했다"는 자기 신고가 되고, 독립 검증자는 코드를 읽어
설계서와 비교하는 것밖에 할 수 없다. 설계 문서 19라운드에서 가장 무거웠던 지적들이 전부
*실행 가능한 판정 근거가 없는 검사*에서 나왔다.

**펌웨어 코어를 셋(2a·2b·2c)으로 나눈 이유**는 3일짜리 단계가 중간 실패를 늦게 드러내기
때문이다. 비트 패커의 범위 검사식이 정의되지 않은 동작이었던 건(F-078)은 프레임 구현을
시작하기 전에 잡혔어야 하는 종류였다.

## 2. 지금 있는 검증기는 전부 설계 문서용이다

착수 전에 짚어야 했던 문제다. 아홉 개 검증기는 `openapi.json` 을 검사하지 서버 라우트를
검사하지 않고, `schema.sql` 을 검사하지 실제 DB 를 검사하지 않는다.
**코드가 설계와 같은지를 보는 검증기는 아직 하나도 없다.**

그래서 단계마다 하나씩 신설한다(지시서 §4). 이것들이 곧 `CLAUDE.md` §0 이 선언한
**반드시 성립해야 하는 주장 넷의 기계 판정**이 된다.

| 주장 | 판정 방법 | 신설 단계 |
|---|---|---|
| MCU 3종이 동일 프로토콜로 혼용 동작 | `core/` 오브젝트 해시 3종 동일 · 보드 판별 매크로 0개 · C↔Python 골든 53건 바이트 일치 | 2b · 3 · 8 |
| 하드웨어 없이 표준 준수를 검증 | 외부 도구 의존 0 · 네트워크 없이 `replay`/`simulate` 왕복 | 4 |
| 노드 추가 시 서버 코드 수정 0줄 | `backend/` 에 장치 종류 문자열 하드코딩 0 | 6 |
| 표준의 실구현 장애 지점을 발견·해소 | 표준결함 19건 — 이미 문서로 확정 | — |

**검증기 자신도 검증 대상이다.** 설계 단계에서 검증기 결함이 네 번 나왔다.

| 라운드 | 결함 | 형태 |
|---|---|---|
| F-074 | 초안 검증기 26/26 이 필수 전이 삭제를 통과 | 이름의 존재만 검사 |
| F-080 | 검증기가 대조표 한 파일만 읽음 | 자기 자신과의 일치만 검사 |
| F-089 | 화면 검증기가 40/40 으로 거짓 통과 | 값을 읽고 대조하지 않음 |
| F-095 | 자체 JSON Schema 검사기가 키워드 미구현 | 미구현 문법이 통과로 바뀜 |

그래서 지시서 §5.2 에 **"고친 것을 되돌려 실패하는지 확인"** 을 종료 조건으로 넣었다.
단계 종료 보고에 결함 주입 결과가 없으면 그 단계는 끝난 것이 아니다.

## 5. 독립 검증자 운영

### 5.1 회차

**매 단계 종료 시 1회** — 총 11회. 단계 출구 명령이 전부 통과한 뒤에만 넘긴다.
통과하지 않은 상태로 넘기면 미완성을 결함으로 보고해 처리 비용만 늘어난다.

프롬프트는 `검증자_프롬프트.md` 에 있다. 단계 번호만 바꿔 재사용하며, 단계별 공격 지점은
그 문서 §3 에 준비되어 있다.

### 5.2 현재 검증 환경의 능력 확인

| 확인할 능력 | 대응 |
|---|---|
| 저장소 읽기 | 접근 권한이 있으면 정본과 구현을 직접 읽는다. 없으면 검증 불가로 보고한다 |
| 명령 실행·C 컴파일 | 실행 권한과 `python`·`gcc`가 있으면 직접 실행한다. 없으면 제출 로그를 통과 근거로 대신 쓰지 않는다 |
| 표준 원문의 **그림** (0943 61장 등) | 이미지 해석 기능과 원문 접근이 모두 있을 때만 직접 판정한다. 아니면 본문으로 간접 검증하고 추측하지 않는다 |
| **브라우저 렌더링** | 실제 브라우저 런타임이 있을 때만 렌더 결과를 판정한다 |
| **하드웨어 접근** | 실제 장비에 접근할 수 있을 때만 실측을 판정한다. 아니면 캡처 내용과 자동 검증 가능 범위를 분리해 보고한다 |

이것을 명시하지 않으면 "검증했다"고 답하는데 실제로는 확인 못 한 영역이 생긴다.
`GPT.md` §3 이 같은 이유로 현재 환경의 능력 확인과 검증 불가 보고 원칙을 명시하고 있다.

### 5.3 지적 처리

`ROLES.md`와 `CLAUDE.md` §11 그대로다. 검증자는 `신규`로만 추가하고, 상태 전이는 작업자만 한다.

| 분류 | 처리 |
|---|---|
| `요건위반` | 공고문 조항. **최우선**, 다른 작업 중단 |
| `코드버그` | 재현 → 수정 → **회귀 테스트 추가** |
| `문서불일치` | **표준 원문으로 어느 쪽이 옳은지 먼저 판정** |
| `표준결함` | `docs/standard-findings.md` 로 이관. 현재 19건 |

`기각`·`보류` 는 사용자가 동의하지 않을 수 있으므로 사유를 함께 보고받는다.

## 6. 사람이 판단해야 하는 지점

에이전트는 아래 셋에서 멈추고 보고한다(지시서 §0.2). 그때 결정이 필요하다.

| 시점 | 결정할 것 |
|---|---|
| 단계 착수 전 | 이 단계로 진행할지, 축소·순서 변경이 필요한지 |
| 설계서와 어긋난 것 발견 | 설계서를 고칠지 구현을 고칠지 — **표준 원문이 판정 근거** |
| 단계 종료 | 독립 검증자에게 넘길지, 보완 후 넘길지 |

여기에 더해 **`contracts/` 변경**은 언제나 사용자 확인이 필요하다(`CLAUDE.md` §5).
표준 조항 번호를 근거로 제시받고 승인한다. 근거 없는 `contracts/` 변경은 통합 실패의 유일한 원인이다.
