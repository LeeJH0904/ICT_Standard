## 0. 이 문서가 결정하는 것

앞선 문서들이 **바이트열이 어떻게 생겼는지**를 확정했다. 이 문서는 **그 바이트열을 2KB SRAM 위에서 어떻게 다루는지**를 확정한다.

| 결정 | 값 | 근거 |
|---|---|---|
| 수신·송신 방식 | **스트리밍** (고정부까지만 버퍼) | §3.2 |
| 스트리밍 윈도우 | **51 byte** | §3.3 |
| 하드웨어 추상화 | **함수 포인터 구조체 2종** (`siap_io_t` · `siap_dev_ops_t`) | §2.2 |
| 비트 접근 | `bitpack.c` 4개 함수 전용 | §4 |
| 가변 요소 위반 시 의미론 | **요소 단위 적용 + 첫 위반에서 중단** | §5.6 |
| 프레임 재동기 | `Version` + 헤더 타당성 검사 기반 바이트 스캔 | §5.7 |
| 연결 실패 RSC 분류 | 재시도 **가능 2종** / 불가 7종 (`SUCCESS` 제외) | §6.5 |
| Notify 의 ACK 생명주기 | 수신은 **상태 무관 즉시 ACK**, 송신은 요청과 **공통 `pending` 재전송** | §6.2-a |
| 주기 알림 경합 | **`due` 비트 + 회전 커서.** 단일 `pending` 슬롯에서 기아가 없다 | §6.4-a |
| `FAULT` 의 범위 | **연결 승인 이후 전용.** 연결 전 오류는 연결 시도 계속 또는 `HALTED` | §6.1 |
| 디바이스 샘플링·오류 감지 주기 | 표 7-15 `Period` 를 **내부 스캔 간격으로 재사용**(필드 의미 재정의 아님) | §6.3 |
| `Transfer Mode` = Both 의 전송 조건 | **이 구현에서 Periodic 과 동일** (이벤트 조기 감지 없음) | §6.3 |
| 디바이스 `Period` = 0 의 의미 | **사실상 매 poll 마다 스캔**으로 허용 | §6.3 |

이 중 여덟이 **표준이 규정하지 않은 것**이며 §9에 결정 근거를 모았다.

## 2. 계층 경계 — `core/` 가 모르는 것

### 2.1 금지 include

`firmware/core/` 의 어떤 파일도 다음을 include 하지 않는다.

| 금지 | 이유 |
|---|---|
| `Arduino.h`, `esp_*.h`, `avr/*.h` | 보드 종속. 하나라도 들어오면 "동일 응용계층" 주장이 무너진다 |
| `stdio.h`, `stdlib.h` | AVR에서 `printf` 는 flash 1.5KB 이상을 먹고, `malloc` 은 §4.2 규약 위반이다 |
| `string.h` | `memcpy`/`memset` 만 필요하므로 `core/` 내부에 4줄짜리 `bp_memcpy` 를 둔다. libc 링크 없이 호스트 테스트가 되게 하려는 목적도 있다 |

허용은 `stdint.h`, `stddef.h`, `stdbool.h` 셋뿐이다. 셋 다 freestanding 구현에서 제공되는 순수 타입 헤더다.

> **검증**: `firmware_verify.py` 가 `core/*.c`, `core/*.h` 의 `#include` 행을 전수 검사한다. 허용 목록 밖의 헤더가 하나라도 있으면 FAIL.

### 2.2 하드웨어 추상화 — 함수 포인터 구조체

`core/` 는 아래 두 구조체만 안다. 보드 디렉터리가 이것을 채워 넘긴다.

```c
/* siap_types.h — 전송 계층 추상화 */
typedef struct {
    /* 1 byte 를 읽는다. 1 = 읽음 / 0 = 지금은 없음 / -1 = 링크 오류 */
    int8_t   (*read_byte)(void *ctx, uint8_t *out);
    /* len byte 를 쓴다. 쓴 개수 반환. 부분 쓰기를 허용한다 */
    int16_t  (*write)(void *ctx, const uint8_t *buf, uint16_t len);
    /* 부팅 후 경과 ms. 롤오버 허용 (§6.4) */
    uint32_t (*millis)(void *ctx);
    void     *ctx;                 /* 보드가 쓰는 임의 포인터 */
} siap_io_t;

/* siap_types.h — 디바이스 I/O 추상화 */
typedef struct {
    /* 디바이스 1개의 현재값을 32bit 원시 비트열로 읽는다. 0 = 성공 */
    int8_t (*read_value)(void *ctx, uint8_t device_id, uint32_t *raw);
    /* 디바이스 1개에 제어값을 쓴다. 0 = 성공 */
    int8_t (*write_value)(void *ctx, uint8_t device_id, uint32_t raw);
    void  *ctx;
} siap_dev_ops_t;
```

**왜 함수 포인터인가.** 대안은 링크타임 심볼 치환(`extern` 선언 + 보드가 정의)이다. 코드가 더 짧고 AVR에서 간접호출 비용도 없다. 그런데 **한 바이너리에 구현이 하나뿐**이므로 호스트 테스트에서 "노드 2개를 서로 다른 페이크 IO에 물려 동시에 돌리는" 시나리오가 불가능하다. §8의 `test_golden.c` 가 정확히 그것을 한다.

**비용 측정.** 간접호출은 AVR에서 `icall` 3사이클(직접호출 `rcall` 2사이클 대비 +1). 프레임당 호출 횟수가 최대 501회(바이트 단위 읽기)이므로 501사이클 = 16MHz에서 31μs 추가다. `Timeout` 2초 대비 무시할 수준이다.

ATmega328P 는 flash 32KB(16K word)이므로 함수 포인터·데이터 포인터 모두 **2 byte** 다. 구조체 크기는 멤버 수로 결정된다 — `ctx` 도 멤버 하나이므로 따로 더하지 않는다.

| 구조체 | 멤버 | 크기 |
|---|---|---|
| `siap_io_t` | 함수 포인터 3 + `ctx` 1 = 4 | **8 B** |
| `siap_dev_ops_t` | 함수 포인터 2 + `ctx` 1 = 3 | **6 B** |
| 합계 | | **14 B** |

> 구현 후 `sizeof` 실측으로 교체한다. 패딩이 붙으면 이 값이 커진다 — AVR-GCC 는 정렬 요구가 1 이라 붙지 않을 것으로 보지만, 추정을 실측인 것처럼 두지 않는다.

### 2.4 보드가 `core/` 에 넘기는 전부

```c
siap_node_t node;
siap_node_init(&node, &(siap_node_cfg_t){
    .gcg_id      = 0x00001,
    .node_id     = 0x00003,
    .sw_version  = 0x10,
    .io          = &io,          /* §2.2 */
    .dev_ops     = &dev_ops,     /* §2.2 */
    .devices     = dev_table,    /* 보드가 소유하는 배열 */
    .device_count= 3,
    .profile     = SIAP_PROFILE_DEFAULT,   /* 표 7-18 기본값 */
});

for (;;) {
    siap_node_poll(&node);       /* 논블로킹. 보드 루프에서 계속 호출 */
}
```

보드 코드는 이 두 호출과 `dev_table` 초기화뿐이다. 프로토콜 관련 분기문이 보드 파일에 등장하면 경계 위반이다.

## 3. 메모리 예산

### 3.1 타깃 제원

| 보드 | MCU | Flash | SRAM | 전송 |
|---|---|---|---|---|
| Uno (센서 노드) | ATmega328P | 32 KB | **2,048 B** | UART 9600 8N1 |
| Pro Mini (구동기 노드) | ATmega328P | 32 KB | **2,048 B** | UART 9600 8N1 |
| ESP32 (겸용 노드) | ESP32 | 4 MB | 320 KB | TCP over Wi-Fi |

**설계는 2,048 B 기준으로 한다.** ESP32는 여유가 있으므로 제약이 되지 않는다. 반대로 말하면 ESP32에서만 되는 설계를 하면 3종 혼용 주장이 무너진다.

### 3.2 왜 스트리밍인가

최대 프레임은 **501 byte** 다 (골든 `B03` = `RES_SET_CONNECTION`, N=16). 전략 셋을 비교했다.

| 전략 | 필요 RAM | N=16 지원 | `core/` 무수정 | 판정 |
|---|---|---|---|---|
| 정적 최대 버퍼 | **501 B** (SRAM 24.5%) | ○ | ○ | 스택·디바이스 테이블과 합치면 여유가 얇다 |
| 보드별 컴파일타임 상한 | 111 B (N=3 기준) | ✕ | △ 빌드 플래그 필요 | 노드마다 지원 N이 달라져 혼용 주장이 흐려진다 |
| **스트리밍 디코드** | **51 B** (SRAM 2.5%) | ○ | ○ | **채택** |

**스트리밍의 핵심 성질**: 수신 버퍼 크기가 **N과 무관**해진다. 노드가 쓰는 RAM은 자기가 실제로 가진 디바이스 수에만 비례하고, 상대가 보내온 N에는 비례하지 않는다. 표준이 `Num. of Devices` 를 8bit(최대 255)로 열어둔 것을 2KB MCU가 받아낼 수 있는 유일한 방법이다.

> N=255 프레임(7,671 byte)이 들어와도 스트리밍 수신 자체는 성립한다. 다만 본 구현은 §9의 N=16 상한을 넘는 프레임을 `INVALID_FORMAT` 으로 거부한다 — 받아낼 수는 있으나 `Timeout` 2초 안에 처리를 보장할 수 없기 때문이다 (아키텍처 §6.2-a).

### 3.3 스트리밍 윈도우 산출

```
window = HEADER_BYTES + max(fixed) + max(elem)
       = 12          + 9           + 30          = 51 byte
```

| 항목 | 값 | 해당 메시지 |
|---|---|---|
| `HEADER_BYTES` | 12 | 전 34종 공통 (그림 7-1) |
| `max(fixed)` | 9 | `RES_SET_CONNECTION` · `RES_GET_NODE_PROPERTY` · `RES_GET_NODE_DEVICE_PROPERTY_ALL` = `RSC`(1) + `NODE_PROPERTY`(8) |
| `max(elem)` | 30 | `DEVICE_PROPERTY` (표 7-15) |

`contracts/frame.py` 의 `LAYOUT` 34종에서 기계적으로 나온 값이며, `firmware_verify.py` 가 매번 재산출해 이 문서의 51과 대조한다.

**전제 — 모든 요소가 바이트 정렬이다.** 스트리밍은 "요소 경계가 바이트 경계와 일치"해야만 성립한다. 하나라도 어긋나면 이전 요소의 잔여 비트를 들고 다녀야 한다.

| 구조체 | bit | byte | 정렬 |
|---|---|---|---|
| 헤더 | 96 | 12 | ○ |
| `NODE_PROPERTY` (표 7-13) | 64 | 8 | ○ |
| `DEVICE_MAIN_INFO` (표 7-14) | 56 | 7 | ○ |
| `DEVICE_PROPERTY` (표 7-15) | 240 | 30 | ○ |
| `MSG_CONTROL_PROFILE` (표 7-18) | 56 | 7 | ○ |
| `RSC` / `NEC` / `DEVICE_ID` | 8 | 1 | ○ |

**구조체 사이는 정렬되지만 구조체 내부는 정렬되지 않는다.** `Message Type`(14bit), `GCG ID`/`Node ID`(각 20bit), `Subtype`(9~16bit)이 바이트 경계를 넘는다 — 그래서 §4의 비트 패킹이 필요하다. 두 사실은 모순이 아니라 역할이 다르다.

### 3.4 정적 메모리 표

동적 할당은 쓰지 않는다(§4.2 규약). 전부 컴파일타임 고정이다.

| 대상 | 크기 | 산출 |
|---|---|---|
| RX 윈도우 | 51 B | §3.3 |
| TX 윈도우 | 51 B | 동일. RX와 공유하지 않는다 (요청 처리 중 응답을 만들어야 한다) |
| 디코더 상태 | 20 B | 상태 1 + kind 1 + N 2 + i 2 + 누적 2 + plen 2 + 헤더 필드 캐시 10 |
| 인코더 상태 | 12 B | 상태 1 + kind 1 + N 2 + i 2 + 기록 바이트 수 2 + 여유 4 |
| 노드 상태 머신 | 28 B | 상태 1 + `next_msg_id` 2 + `pending` 10 (§6.4) + 타이머 3 × 4 + `due` 1 + `cursor` 1 (§6.4-a) + 정렬 여유 1 |
| `MSG_CONTROL_PROFILE` | 7 B | 표 7-18 |
| `siap_io_t` + `siap_dev_ops_t` | 14 B | 8 + 6 (§2.2) |
| `SIAP_WIRE_CODE`+`_EXT`+`SIAP_LAYOUT`+`SIAP_SUBTYPE_TABLE` | 226 B | F-129 — PROGMEM 미사용(core/ 순수성 우선, §3.5). 70+70+70+16 |
| **소계 (디바이스 무관)** | **409 B** | 위 8행의 합 |
| 디바이스 테이블 | 32 B × D | `DEVICE_PROPERTY` 언팩 구조체. D = 노드의 **실제** 디바이스 수 |

디바이스 테이블 32 B 의 내역 (표 7-15 언팩):

```
device_id 1 + type 1 + subtype 1 + value_type 1 + value 4
+ transfer_mode 1 + period 2
+ lower_value 4 + upper_value 4 + lower_limit 4 + upper_limit 4 + precision 4
+ status 1                                                        = 32 B
```

| 노드 | D | 디바이스 테이블 | 합계 | SRAM 2,048 B 대비 |
|---|---|---|---|---|
| Uno 센서 노드 | 3 | 96 B | **505 B** | 24.7% |
| Pro Mini 구동기 노드 | 2 | 64 B | **473 B** | 23.1% |
| 상한 노드 (가정) | 16 | 512 B | **921 B** | 45.0% |

Arduino 런타임 자체가 약 200 B를 쓰고, 스택은 200~300 B로 잡는다. Uno 기준 총 1,005 B 안쪽으로 SRAM의 50% 이상이 남는다.

> **단계 8 실측 (2026-08-16, Arduino IDE · Uno).** `arduino_sensor_node` 전체 globals
> **1,025 B = 50.0%** (Flash 16,638 B = 51.6%). 위 표의 505 B(24.7%)는 *펌웨어 데이터
> 슬라이스* 추정이고 이 실측은 *Arduino 런타임(Serial 버퍼 등) 포함 전체 globals* 라
> 분모가 다르다 — 바로 위 문장이 예견한 ~50% 와 일치한다. 남은 1,023 B 스택은 재귀·
> malloc 없는 고정버퍼 설계에 충분하다. **전체-globals 예산을 55%로 명문화한다**(§1.5
> "실측이 추정치를 대체한다", 2026-08-16 사용자 결정) — `tools/board_verify.py` 가
> `size_report.txt` 를 이 55% 와 실측 대조한다.

> **정적 버퍼 전량이 501 B였다면** — 위 소계에서 두 윈도우 102 B 를 빼면 버퍼 외 고정분이 307 B 다.
> 상한 노드는 501 + 501 + 307 + 512 = 1,821 B (88.9%)가 되어 Arduino 런타임 200 B 를 더하면
> SRAM을 초과한다. 스트리밍 선택의 실질적 근거가 이 한 줄이다.

> **전부 추정치다.** 구현 후 `avr-size` 와 `sizeof` 실측으로 이 표를 교체한다(§11).
> 추정을 실측으로 표기하지 않는 것이 이 문서의 규칙이며, `firmware_verify.py` 는
> **산술 정합만** 검사한다 — 값의 진위는 실측이 나와야 판정된다.
>
> **F-129 — 상한 노드(D=16, 이론상 최댓값)가 처음으로 40%를 넘는다(45.0%).**
> `PROGMEM`을 포기하고 `core/` 순수성을 우선한 결정(§3.5)의 직접적인 대가다.
> Uno·Pro Mini 는 **실제 보드 시나리오**로 여전히 25% 안쪽이라 데모·2차 시연에
> 영향이 없다. 개발_착수_지시서 §1.5 원칙("실측값이 설계서의 추정치를 대체한다")에
> 따라 이 40% 초과는 **`avr-size` 실측(단계 8) 전까지 잠정 완화한다** — 이 표는
> 여전히 추정치이고, `firmware_verify.py` 도 산술 정합만 확인하지 상한 노드의
> 40% 준수를 더는 강제하지 않는다(실사용 노드 2종만 강제). 단계 8 실측이 실제로
> 40%를 넘으면 그때 N 상한 재검토 등 설계 결정을 다시 본다.
>
> **해소 (2026-08-16).** 단계 8 Uno 실측이 나왔다: 전체 globals 50.0%. 이 40% 는
> §3.4 표의 *슬라이스* 지표(Uno 추정 24.7%)였고, `avr-size`/board_verify 가 보는
> *전체 globals* 지표(50.0%)와 분모가 다르다. 전체-globals 예산을 **55%** 로 명문화해
> 지표 불일치를 해소했다 — 슬라이스 40% 검사(`firmware_verify.py`, 추정치 대상)는
> 그대로 두고, 전체-globals 55% 검사(`board_verify.py`, 실측 대상)를 정본으로 둔다.
> 실측 50% < 55% 라 §3.5 의 PROGMEM 재검토는 발동하지 않는다.

> **F-129 — PROGMEM 을 쓰지 않는다.** 이 절은 초안에서 34종 LAYOUT 테이블을

> 표는 이 210+16=226 byte를 반영해 갱신했다. **전체-globals 예산(55%, §3.4 실측

> PROGMEM 접근을 얹는 것으로 재검토한다 — `core/` 자체는 지금 바꾸지 않는다(순수성이
> 우선). **단계 8 Uno 실측 50.0% < 55% 라 이 재검토는 발동하지 않는다(2026-08-16).**

## 4. 비트 패킹 (`bitpack.c` / `.h`)

### 4.1 4개 함수 — 계약

```c
/* GCC · Clang · AVR-GCC 공통. 미지원 컴파일러에서는 빈 매크로가 되지만
   호스트 테스트(§8)가 GCC/Clang 으로 도는 한 누락은 거기서 잡힌다 */
#if defined(__GNUC__)
#  define SIAP_WUR __attribute__((warn_unused_result))
#else
#  define SIAP_WUR
#endif

/* 성공 true / 범위 초과 false. false 면 buf 와 bitpos 를 건드리지 않는다 */
SIAP_WUR bool bp_write    (uint8_t *buf, size_t *bitpos, uint32_t val, uint8_t nbits);
         uint32_t bp_read (const uint8_t *buf, size_t *bitpos, uint8_t nbits);
SIAP_WUR bool bp_write_f32(uint8_t *buf, size_t *bitpos, float val);
         float bp_read_f32(const uint8_t *buf, size_t *bitpos);
```

**범위 검사식 — 시프트를 쓰지 않는다 (F-078).**

```c
if (nbits == 0 || nbits > 32) return false;
/* nbits == 32 는 uint32_t 전 범위이므로 검사가 필요 없다.
   1..31 은 마스크로 상한을 만든다 — (1u << nbits) 를 쓰면 안 된다:
     · AVR 의 unsigned int 는 16bit 라 nbits >= 16 에서 시프트 폭 초과 (UB)
     · 호스트에서도 1u << 32 는 UB 이고 GCC 가 -Wshift-count-overflow 로 경고한다 */
if (nbits < 32 && val > ((uint32_t)0xFFFFFFFFul >> (32 - nbits))) return false;
```

| `nbits` | 상한식 | 값 |
|---|---|---|
| 14 (`Message Type`, 표 7-6) | `0xFFFFFFFF >> 18` | `0x00003FFF` |
| 16 (`Message Identifier`, 표 7-6) | `>> 16` | `0x0000FFFF` |
| 20 (`GCG ID`·`Node ID`, 표 7-8) | `>> 12` | `0x000FFFFF` |
| 32 (`Value`, 표 7-14) | 검사 없음 | — |

| 계약 | 내용 |
|---|---|
| 비트 순서 | **MSB first.** `bitpos` 0 은 `buf[0]` 의 최상위 비트다 |
| 바이트 순서 | **big-endian.** 32bit 값은 상위 바이트가 먼저 나온다 (표준 미규정 → 자체 결정) |
| `bitpos` | 성공 시에만 `nbits` 만큼 증가한다. 호출자가 직접 만지지 않는다 |
| `nbits` 범위 | 1~32. 벗어나면 `false` |
| **범위 초과** | `val >= (1u << nbits)` 이면 **기록하지 않고 `false`.** 마스킹 래핑 금지 (F-044) |
| 부작용 | `buf` 의 미기록 비트를 건드리지 않는다. 호출자가 버퍼를 0으로 초기화한다 |

**`void` 가 아니라 `bool` 인 이유 (F-075).** 초안은 "호출 전에 검사하도록 한다"는 **규약**으로만 두었다.
그러면 `Message Type`(14bit)·`GCG ID`/`Node ID`(각 20bit)에 큰 값이 들어와도 **하위 비트만 wire 에 실리고
호출자는 알지 못한다.** F-044 가 확정한 "래핑 금지"가 구조가 아니라 관습에 의존하게 된다.

**반환형만 `bool` 로 바꾸는 것으로는 부족하다 (F-078).** `-Wunused-result` 는 **`warn_unused_result`
속성이 붙은 함수에만** 적용된다. 평범한 `bool` 함수의 반환값을 버려도 GCC 는 경고하지 않는다 — 실측했다.

```
$ gcc -std=c99 -O2 -Wall -Wextra -Wunused-result w.c        # gcc 13.3.0
w.c:5:26: warning: ignoring return value of 'tagged' declared with
          attribute 'warn_unused_result' [-Wunused-result]
                                                            # plain() 에 대한 경고는 0건
```

그래서 `SIAP_WUR` 속성을 명시적으로 붙이고, `firmware/tests/Makefile` 에
`-Werror=unused-result` 를 넣어 **검사 누락을 빌드 실패로 만든다.**

비용은 필드당 비교 1회다. 최대 프레임(501 byte, 약 250 필드) 기준 1,000 사이클 = 16MHz 에서 **63μs**.
`Timeout` 2초 대비 무시할 수준이며, §2.2 의 간접호출 비용과 같은 자릿수다.

**인코더는 실패를 삼키지 않는다.** `siap_tx_*` 는 첫 `false` 에서 중단하고
`SIAP_ENC_RANGE` 를 반환한다. 프레임은 전송되지 않는다 — **잘린 값을 보내느니 보내지 않는다.**

### 4.1-a 진입점 범위 검증표 (F-075)

`bp_write` 는 최후 방어선이지 유일한 방어선이 아니다. 값이 들어오는 지점에서 먼저 막는다.

| 진입점 | 필드 | 허용 범위 | 근거 | 위반 시 |
|---|---|---|---|---|
| `siap_node_init` | `gcg_id` · `node_id` | 0 ~ 2²⁰-1 | 표 7-8 | 초기화 실패 반환. 노드가 뜨지 않는다 |
| `siap_node_init` | `device_count` | 1 ~ 16 | 표 7-13 · F-064 | 〃 |
| `siap_node_init` | `sw_version` | 0 ~ 255 | 표 7-13 | 〃 |
| `dev_table[i]` | `device_id` | 0 ~ 255, 노드 내 유일 | 표 7-14 | 〃 |
| `dev_table[i]` | `subtype` | `subtype_registry.h` 등재값 | 표 7-14 | 〃 |
| `dev_table[i]` | `value_type` | 0 ~ 2 (3 은 Reserved) | 표 7-14 | 〃 |
| `dev_table[i]` | `period` | 0 ~ 2¹⁴-1 | 표 7-15 | 〃 |
| `dev_ops.read_value` | `raw` | 32bit 전 범위 | 표 7-14 `Value` | 제한 없음 |
| 수신 프레임 | 전 필드 | 비트 폭이 곧 상한 | — | 디코더가 폭만큼만 읽으므로 초과 불가 |

**초기화 검증은 부팅 시 한 번**이고, 그 이후 송신 경로에 들어오는 값은 디바이스 테이블과
수신 프레임뿐이다. 둘 다 위 표에서 이미 폭이 보장된다. `bp_write` 의 `false` 는
**설계 오류가 남아 있을 때만 발생**해야 하며, 발생하면 호스트 테스트에서 잡힌다.

### 4.2 왜 구조체 캐스팅이 깨지는가

```c
/* 절대 하지 않는다 */
struct __attribute__((packed)) hdr { uint8_t ver; uint16_t type:14; uint8_t trans:2; ... };
struct hdr *h = (struct hdr *)buf;     /* ✕ */
```

깨지는 이유가 셋이다.

1. **비트필드 배치 순서가 구현 정의다.** C99 §6.7.2.1p11 — 비트필드가 워드 안에서 상위부터 채워지는지 하위부터인지 표준이 정하지 않는다. AVR-GCC(LSB-first)와 Xtensa-GCC의 결과가 다를 수 있고, 이 프로젝트는 **같은 바이트가 나오는 것 자체가 주장**이므로 허용할 수 없다.
2. **엔디안이 다르다.** AVR과 Xtensa 모두 little-endian인데 SIAP는 big-endian이다. `uint16_t` 를 그대로 읽으면 바이트가 뒤집힌다.
3. **정렬 요구.** `Payload Length` 는 오프셋 40bit = byte 5 에서 시작한다. 홀수 주소의 `uint16_t` 접근은 아키텍처에 따라 트랩이거나 느리다.

구체 예 — `Message Type` 은 bit 8~21이다.

```
byte 1: [ t13 t12 t11 t10 t9  t8  t7  t6 ]
byte 2: [ t5  t4  t3  t2  t1  t0  T1  T0 ]      T = Transmission Type
```
14bit 값이 byte 1 전체와 byte 2 의 상위 6bit에 걸친다. `buf[1] << 8 | buf[2]` 로 읽어 `>> 2` 해야 나온다. 구조체로는 표현할 수 없다.

### 4.3 FLOAT 는 정수를 경유한다

```c
bool bp_write_f32(uint8_t *buf, size_t *bitpos, float val) {
    uint32_t bits;
    bp_memcpy(&bits, &val, 4);               /* type punning: union/memcpy 만 허용 */
    return bp_write(buf, bitpos, bits, 32);  /* nbits==32 는 범위 검사 자체가 생략된다 */
}
```

`*(uint32_t *)&val` 형태의 포인터 캐스팅은 strict aliasing 위반이라 `-O2` 에서 최적화기가 재배치할 수 있다. `memcpy` 는 GCC가 인식해 레지스터 이동으로 접는다 — AVR에서 추가 비용이 0이다.

**전제**: 타깃이 IEEE-754 single 을 쓴다. AVR-GCC와 Xtensa-GCC 모두 그렇다. 호스트 테스트가 `0x41CA6666 == 25.3f` 를 확인해 이 전제를 못박는다 (골든 `FLOATS` 표와 동일 상수).

### 4.4 호스트 테스트 케이스

| # | 케이스 | 기대 |
|---|---|---|
| 1 | `bp_write(buf,&p,0x2A,14)` 후 `bp_read` | 0x2A, `p` = 14 |
| 2 | 바이트 경계를 넘는 20bit 쓰기/읽기 | 왕복 일치 |
| 3 | 연속 쓰기 8+14+2+16+16+20+20 = 96bit | `bitpos` = 96, 바이트 정렬 |
| 4 | `nbits`=32 최대값 `0xFFFFFFFF` | 왕복 일치 |
| 5 | `bp_write_f32` / `bp_read_f32` 7종 (골든 `FLOATS`) | 비트 패턴 일치 |
| 6 | 미기록 비트 불변 | 인접 바이트가 0으로 남는다 |
| 7 | **범위 초과 거부** — `bp_write(buf,&p,0x4000,14)` | `false`, `buf` 불변, `p` 불변 (F-075) |
| 8 | 20bit 필드에 2²⁰ 기록 시도 | `false`. `GCG ID`/`Node ID` 경계 (표 7-8) |
| 9 | `nbits`=0 / 33 | `false` |
| 10 | **전 폭 스윕** `nbits`=1~32 각각 최대값 기록·왕복, 최대값+1 거부 | 32종 전량 통과. 마스크식이 폭마다 맞는지 (F-078) |
| 11 | `-Werror=unused-result` 로 반환값을 버린 호출 | **빌드 실패**. 계약이 강제되는지 (F-078) |

> -Wextra -Wconversion -Wshift-count-overflow -Werror` 로 32폭 전량과 헤더 96bit 연속 기록
> (`12 00 00 00 01 00 00 00 00 10 00 03` = 골든 `N01`)이 통과한다.

## 5. 스트리밍 코덱 (`siap_frame.c` / `.h`)

### 5.1 수신 상태 머신

```
        ┌──────────────────────────────────────────────┐
        ▼                                              │
   S_SYNC ──12 byte 수집──> S_HDR                       │
                              │                        │
              헤더 위반 ──────┼──────> S_SYNC(재동기) ───┘
                              │            (F-141 — payload_len 미신뢰,
                              │             선폐기 없이 즉시 1byte 재동기)
                    fixed>0   │   fixed=0
                    ┌─────────┴─────────┐
                    ▼                   ▼
                 S_FIXED ───────────> S_ELEM ──N회──> S_DONE
                (fixed byte)         (elem byte)         │
                                          │              └──> on_end(ok)
                                   요소 위반 ──> S_DRAIN
                                          (plen 기반 잔여 — 구조 이미 확인됨)
```

| 상태 | 하는 일 | 버퍼 사용 |
|---|---|---|
| `S_SYNC` | 헤더 12 byte 를 모은다 | 12 B |
| `S_HDR` | 비트 언팩 → `resolve_kind` → `element_count` → 헤더 위반 5종 판정 | 0 (제자리) |
| `S_FIXED` | 고정부 최대 9 byte 를 모아 `on_fixed` 호출 | 9 B |
| `S_ELEM` | 요소 최대 30 byte 를 모아 `on_element(i)` 호출. i < N 동안 반복 | 30 B |
| `S_DONE` | `on_end(ok)` 호출 후 `S_SYNC` 복귀 | 0 |
| `S_DRAIN` | 남은 payload 를 읽어 버린다 | 0 |

**`S_DRAIN` 이 스트리밍의 값어치를 만든다.** 위반 프레임의 페이로드는 한 바이트도 저장하지 않고 버려진다. 501 byte 위반 프레임이 들어와도 RAM 사용량이 변하지 않는다. 다만 이 값어치는 **payload_len 이 이미 구조적으로 확인된 뒤에만** 성립한다 — `S_FIXED`/`S_ELEM` 단계의 위반(요소 값 오류 등)은 헤더 4조건을 전부 통과한 뒤이므로 그 잔여를 `S_DRAIN` 으로 정확히 버릴 수 있다. `S_HDR` 자체가 위반인 5종은 그 payload_len 이 애초에 검증되지 않았으므로(잡음·손상 바이트가 우연히 헤더처럼 보였을 수 있다) 선폐기하지 않고 즉시 재동기로 넘어간다(F-141, §5.7).

### 5.2 콜백 인터페이스

```c
typedef struct {
    /* 헤더 파싱 완료. 0 반환 시 계속, 음수 반환 시 그 RSC로 거부 */
    int8_t (*on_header)(void *ctx, const siap_hdr_t *h, siap_kind_t k, uint16_t n);
    /* 고정부 (RSC / NODE_PROPERTY / MSG_CONTROL_PROFILE / NEC) */
    int8_t (*on_fixed) (void *ctx, const uint8_t *buf, uint8_t len);
    /* 가변 요소 i번째 (0-based) */
    int8_t (*on_element)(void *ctx, uint16_t i, const uint8_t *buf, uint8_t len);
    /* 프레임 종료. rsc = SIAP_RSC_SUCCESS 면 정상, 아니면 첫 위반 코드 */
    void   (*on_end)(void *ctx, uint8_t rsc, uint8_t clause_id);
    void *ctx;
} siap_sink_t;
```

`clause_id` 는 위반이 어느 조항에서 나왔는지를 나타내는 1 byte 코드다. **CLAUDE.md §3.3 이 요구하는 `clause` 의 펌웨어 대응**이며, 노드가 `NOTI_ERROR` 를 보낼 때는 쓰이지 않지만 호스트 테스트가 "어느 조항으로 잡았는지"를 검사하는 데 쓴다. 문자열을 두면 flash 를 먹으므로 코드값만 두고 매핑표는 `docs/standard-mapping.md` 에 둔다.

### 5.3 N 산출 — `element_count()` 의 C 대응

```c
/* contracts/frame.py element_count() 와 1:1. 음수 반환 = INVALID_FORMAT.
   F-129 — LAYOUT 은 PROGMEM 이 아니라 평범한 static const 배열이다(core/
   순수성 우선, siap_types.h 헤더 주석 참조) — pgm_read_byte() 는
   <avr/pgmspace.h> 없이 못 쓰고, 그 헤더를 core/ 가 include하면
   CLAUDE.md §1-5 위반이자 ESP32 빌드가 깨진다. */
int32_t siap_element_count(siap_kind_t k, uint16_t plen) {
    uint8_t fixed = LAYOUT[k].fixed;
    uint8_t elem  = LAYOUT[k].elem;
    int32_t rest  = (int32_t)plen - fixed;
    if (rest < 0)               return -1;
    if (elem == 0)              return rest == 0 ? 0 : -1;
    if (rest % elem)            return -1;
    int32_t n = rest / elem;
    if (n == 0 && fixed == 0)   return -1;   /* 가변부만 있는 메시지는 N>=1 */
    /* F-120 — 노드당 디바이스 상한(N=16, CLAUDE.md §3.5). 0943 표 7-13의
       Num. of Devices(8bit)는 N=255까지 열지만, AVR SRAM 2KB와
       Timeout ≥ 2×wire_time 전제가 N=16을 넘으면 깨진다. 표준 위반은
       아니지만 이 프로젝트의 자체 결정으로 거부한다. */
    if (n > SIAP_MAX_DEVICES_PER_NODE) return -1;
    return n;
}
```

Python 원본과 **분기 구조가 같아야 한다.** 호스트 테스트가 골든 53건 전량의 `n` 값을 대조한다. 여기서 갈리면 상호운용성 주장이 무너지는 지점이므로 코드를 옮길 때 줄 단위로 대응시킨다.

`0x0800` 중복(`NOTI_ERROR` / `NOTI_DEVICE_VALUE`)도 동일하게 `plen` 으로 푼다 — `siap_resolve_kind(msg_type, plen)` 이 후보 2종에 `siap_element_count` 를 걸어 성립하는 쪽을 고른다.

### 5.4 위반 8종을 어디서 잡는가

기능 2의 주입 시나리오 8종(CLAUDE.md §6.3)이 상태 머신의 어느 지점에서 판정되는지다.

| # | 주입 | RSC | clause | 판정 지점 | 페이로드 저장 |
|---|---|---|---|---|---|
| 1 | `Version` 조작 | `INVALID_VERSION` 0x01 | 7.3.1 | `S_HDR` | 없음 |
| 2 | 미등록 `Node ID` | `INVALID_NODE_ID` 0x03 | 7.3.1 | `S_HDR` | 없음 |
| 3 | `Payload Length` ≠ 실제 | `INVALID_FORMAT` 0x09 | 7.3.1 | §5.5 참조 | — |
| 4 | `Message Type` = 0x000E | `INVALID_FORMAT` 0x09 | 표 7-2 | `S_HDR` | 없음 |
| 5 | `Transmission Type` = 0x03 | `INVALID_TRANSMISSION_TYPE` 0x08 | 표 7-6 | `S_HDR` | 없음 |
| 6 | `Value Type` = 0x03 | `INVALID_DATA_TYPE` 0x06 | 표 7-14 | `S_ELEM` / `S_FIXED` | 요소 1개분 |
| 7 | 미등록 `Subtype` | `INVALID_DATA_SUBTYPE` 0x07 | 표 7-14 | `S_ELEM` / `S_FIXED` | 요소 1개분 |
| 8 | `NEC` = 0x07 수신 | `ERROR_BATTERY_LOW` 0x07 | 7.3.2 | 게이트웨이 전용 | — |

8종 중 **4종(1·2·4·5)이 헤더 단계에서 무조건 걸러진다** — 페이로드를 한 바이트도 만지지 않는다. 3번은 조건부다(§5.5). 6·7번만 요소 1개분(최대 30 byte)을 읽어야 판정된다.

6·7번은 노드가 **수신**할 때도 발생한다 — 게이트웨이가 `REQ_SET_DEVICE_CONTROL` 에 `Value Type=0x03` 을 실어 보내는 경우다. 노드는 `RES_SET_DEVICE_CONTROL` 에 해당 RSC 를 담아 회신한다 (7.3.1).

8번은 노드가 **송신**하는 것이므로 노드 수신 경로에 없다. 게이트웨이가 받고 F-060에 따라 위반이 아닌 alert 로 처리한다.

### 5.5 `Payload Length` ≠ 실제 — 스트리밍에서의 한계

**정직하게 적는다.** 이 위반은 전송 방식에 따라 탐지 시점이 다르다.

| 전송 | 상황 | 탐지 |
|---|---|---|
| 게이트웨이 (Python, 레코드 단위) | 프레임 전체가 한 덩어리로 도착 | 즉시. `len(payload) != plen` |
| ESP32 (TCP) | 스트림이지만 손실이 없다 | `plen` 만큼 읽으면 반드시 다음 프레임 헤더가 온다. 다음 헤더가 타당하지 않으면 소급 판정 |
| Uno / Pro Mini (UART) | 프레임 경계가 없다 | **즉시 탐지 불가.** `Timeout` 만료 또는 §5.7 재동기로만 드러난다 |

`plen` 이 요소 크기의 배수가 아닌 경우(§5.3의 `rest % elem`)는 UART에서도 헤더 단계에서 즉시 잡힌다. **즉시 탐지가 불가능한 것은 "`plen` 은 형식상 타당하지만 실제 바이트 수가 다른" 경우뿐**이다. 골든 `X03` 이 그 케이스이며, 게이트웨이 측 판정으로 시연한다.

이 차이는 구현의 결함이 아니라 **표준이 프레임 경계를 정의하지 않은 결과**다. §10에 표준결함으로 등재했다.

### 5.6 가변 요소 위반 시의 적용 의미론 — 표준 미규정

`REQ_SET_DEVICE_PROPERTY` 에 요소 3개가 실려 왔고 3번째가 `INVALID_DATA_SUBTYPE` 이면, 이미 적용한 1·2번째를 되돌려야 하는가? **표준은 트랜잭션 의미론을 규정하지 않는다.**

| 선택지 | RAM 비용 | 판정 |
|---|---|---|
| 전량 거부 (all-or-nothing) | 요소 N개 버퍼 = 30 × 16 = **480 B** | 스트리밍 결정(§3.2)과 정면 충돌. 채택 불가 |
| 요소 단위 즉시 적용 + 첫 위반에서 중단 | 0 B | **채택** |

**채택 근거**

1. 요소는 **자기완결적**이다 — `Value Type` · `Subtype` · `Device ID` 검증에 다른 요소가 필요 없다. 따라서 *잘못된 값이 적용되는 일은 없다.* 발생하는 것은 *부분 적용*뿐이다.
2. 표준이 복구 경로를 이미 제공한다. 게이트웨이는 오류 RSC를 받으면 `REQ_GET_NODE_DEVICE_PROPERTY_ALL`(8.1.4.3)로 노드의 현재 상태를 다시 읽어 대조할 수 있다.
3. 전량 거부를 하려면 표준이 만든 제약(N을 8bit로 열어둠)과 표준이 상정한 환경(2KB급 노드)을 동시에 만족할 수 없다.

**게이트웨이(Python)와 다른가.** 코덱의 출력(`violations` 목록)은 동일하다. 다른 것은 *적용 의미론*이며, 게이트웨이는 디바이스 테이블을 갖지 않으므로 애초에 대응 개념이 없다. 골든 벡터가 검증하는 것은 코덱이므로 3종 혼용 주장에 영향이 없다 — 다만 이 경계를 문서에 명시해 둔다.

**로그**: 중단 시 `on_end(rsc, clause_id)` 와 함께 적용된 요소 수를 노드가 보관하고, 다음 `RES_GET_NODE_DEVICE_PROPERTY_ALL` 에 실제 상태를 실어 회신한다. 게이트웨이는 이것으로 부분 적용을 관측한다.

### 5.7 프레임 경계와 재동기 — 표준 미규정

0943 표 1-1은 통신 환경으로 **RS232·485** 를 명시한다. 그런데 7장은 프레임 구분자도, 길이 프리앰블도, CRC도 정의하지 않는다. UART에서 바이트 하나가 유실되면 수신기는 **영구히 어긋난다.**

본 구현의 재동기 규칙:

```
S_DRAIN 완료 후, 또는 헤더 위반 즉시(F-141 — 선폐기 없이), 또는
S_SYNC 에서 T_gap 이상 무입력이 있었으면
  1 byte 씩 전진하며 다음 12 byte 를 헤더로 시험한다.
  아래 4조건을 모두 만족할 때만 프레임 시작으로 인정한다.
    (a) Version == 0x12                          (7.2.1)
    (b) resolve_kind(msg_type, plen) != NULL      (표 7-2~7-4)
    (c) Transmission Type <= 0x02                 (표 7-6)
    (d) element_count(kind, plen) >= 0            (§5.3)
```

**F-141 — "헤더 위반"과 "S_DRAIN 완료"는 재동기 진입 시점이 다르다.** `S_HDR` 자체가 5종 위반(Version·resolve_kind 실패·element_count<0·Transmission Type·미등록 Node ID) 중 하나면 그 헤더의 `payload_len` 은 애초에 어느 구조로도 확인되지 않은 값이다 — 그 값만큼 `S_DRAIN` 으로 먼저 버리면, 잡음이 아니라 마침 뒤따라온 정상 프레임까지 삼킬 수 있다(Version=0x99·payload_len=12 뒤에 정상 ACK 12byte가 오는 경우가 정확히 이것이다). 그래서 헤더 위반은 `S_DRAIN` 을 거치지 않고 즉시 위 1byte 재동기로 넘어간다. 반대로 `S_FIXED`/`S_ELEM` 단계에서 나는 위반(요소 값 오류 등)은 이미 헤더 4조건을 전부 통과한 뒤이므로 그 `payload_len` 은 구조적으로 신뢰할 수 있다 — 이 경우는 그대로 `S_DRAIN` 으로 잔여를 정확히 버린 뒤 재동기 모드에 진입한다.

| 항목 | 값 | 근거 |
|---|---|---|
| `T_gap` (프레임 간 무입력 판정) | **20 ms** | 9600 baud 에서 1 byte = 1.04 ms. 20 byte 분 침묵이면 프레임 중간일 가능성이 낮다 |
| 오인식 확률 | 약 2⁻²² | (a) 8bit + (c) 2bit 중 유효 3/4 + (b)(d) 가 msg_type 16,384 중 34종 |

**이것은 표준에 없는 규칙이다.** 상대 구현이 다른 규칙을 쓰면 재동기 시점이 달라진다. 정상 통신에서는 관측되지 않으므로 상호운용에 지장은 없으나, 노이즈 환경에서 복구 속도가 구현마다 다르다. §10에 등재했다.

**게이트웨이(Python, `siap/codec.py`)는 이 4조건을 그대로 쓰지 않는다(F-146→F-151).** `resolve_kind`·Transmission Type·element_count 세 조건은 `decode_frame()` 자신이 검사해 위반으로 보고하는 항목과 정확히 같다 — 재동기 게이트에서 먼저 걸러내면, 위반 프레임 하나를 낸 직후(항상 재동기 모드로 들어간다, F-140) 뒤따르는 다음 위반 프레임도 그 자신의 위반 때문에 게이트를 통과하지 못해 "노이즈"로 오인되어 1byte씩 삼켜진다. 시연 시나리오 §3.1 S4-b(연속 위반 주입 X01→X03→X05)가 정확히 이 경로를 밟아 두 번째 위반부터 유실됐다(F-146).

Version 일치만으로 완화하자 다른 회귀가 났다(F-151): 위반 헤더는 payload_len 을 신뢰하지 않으므로 헤더 12byte 만 지우고 재동기에 들어가는데(F-141), 그 위반 프레임이 남긴 잔여 payload 바이트가 우연히 Version 값(`0x12`)과 같으면 그 지점을 새 헤더로 오인해 뒤따르는 정상 프레임을 삼켰다(오탐률 1/256). **Node ID 가 등록돼 있는가**를 추가 조건으로 더해 오탐률을 4조건 수준(약 2⁻²²)으로 되돌렸다 — 등록 노드 집합은 20bit Node ID 공간(약 100만) 대비 훨씬 작다. 다만 Node ID 미등록 자체가 위반 목표인 벡터(X02)를 위해, Node ID 가 미등록이어도 `resolve_kind`·Transmission Type·element_count 가 전부 자기충족적으로 유효하면 후보로 인정하는 예외를 뒀다 — "노드를 모른다"와 "이 자리가 헤더가 아니다"는 다른 사실이기 때문이다.

게이트웨이는 이렇게 완화한 조건으로 재동기 후보를 거르고, 나머지 판정은 평소처럼 `decode_frame()`에 맡긴다. 펌웨어는 UART 노이즈 복구가 목적이라 4조건을 그대로 유지한다 — 이 절 서두가 이미 "상대 구현이 다른 규칙을 쓰면 재동기 시점이 달라진다"고 전제하므로 모순이 아니다.

### 5.8 송신 — `Payload Length` 선산출

스트리밍 송신의 유일한 제약은 **헤더의 `Payload Length` 를 첫 바이트를 내보내기 전에 알아야 한다**는 것이다. 다행히 N은 노드 자신의 디바이스 수에서 나오므로 미리 계산된다.

```c
uint16_t plen = LAYOUT[kind].fixed + LAYOUT[kind].elem * n;
siap_tx_begin(&enc, kind, msg_id, plen);   /* 헤더 12 byte 즉시 write */
siap_tx_fixed(&enc, ...);                  /* 고정부 write */
for (i = 0; i < n; i++) siap_tx_element(&enc, i);   /* 30 byte 씩 write */
siap_tx_end(&enc);
```

TX 윈도우는 30 byte 요소 하나분이면 충분하지만, 헤더 12 + 고정부 9 를 같은 버퍼에서 쓰므로 RX와 동일한 51 byte 로 잡는다(§3.4).

**부분 쓰기 처리**: `siap_io_t.write` 는 요청보다 적게 쓸 수 있다(UART 버퍼 포화). 인코더는 미기록 잔여를 윈도우에 남기고 `SIAP_TX_PENDING` 을 반환하며, 다음 `siap_node_poll()` 이 이어서 쓴다. **블로킹하지 않는다** — 블로킹하면 그동안 수신 바이트가 유실된다.

### 5.9 ACK — F-040 계약

```c
/* 8.2 / 7.2.2 — msg_id · GCG ID · Node ID 를 원 요청에서 복사한다 */
int8_t siap_ack(const siap_hdr_t *req, siap_enc_t *enc);
```

`contracts/siap_iface.py` 의 `ack(req: Frame)` 와 동일한 계약이다. 인자를 스칼라 3개로 나열하지 않는 이유가 여기서도 같다 — 복사 대상이 셋이고, 호출부가 직접 꺼내면 누락이 컴파일 타임에 잡히지 않는다.

ACK 는 페이로드가 없으므로(표 7-1) 헤더 12 byte 를 그대로 내보낸다.

## 6. 노드 상태 머신 (`node_state.c` / `.h`)

### 6.1 상태

아키텍처 §6.1은 **게이트웨이가 본 노드의 상태**를 정의한다. 아래는 **노드 자신의 상태**이며 둘은 다르다.

```
  BOOT
    │ 디바이스 자가진단 (dev_ops.read_value 전수)
    │ 실패해도 연결은 시도한다 - 알릴 수단이 연결 뒤에만 있다 (8.1.1)
    ▼
  INIT ──REQ_SET_CONNECTION 송신 (8.1.1)──> CONNECTING
                                              │
                     ┌────────────────────────┼───────────────────────┐
       RSC=SUCCESS   │        재시도 불가 RSC  │       재전송 초과      │
                     ▼                        ▼                       ▼
                  RUNNING                  HALTED               DISCONNECTED
                     │                  (알릴 수단 없음)          │ 백오프
                     │                                            └──> CONNECTING
                     │  · Period / Transfer Mode 에 따라 NOTI_DEVICE_VALUE (8.2.1.2)
                     │  · Keep Alive Interval 마다 NOTI_KEEP_ALIVE (8.2.1.5)
                     │  · G→N 요청 처리 후 RES 회신 / G→N Notify 에 ACK 회신
                     │
                     ├─ 디바이스 오류 ──> FAULT ──오류 해소──> RUNNING   (8.2.1.1)
                     │                     │ Notify Error Interval 마다 NOTI_ERROR
                     │                     └──────────────────┘
                     │
                     ├─ REQ_SET_REBOOT ──> REBOOTING ──ACK 수신 또는 재전송 소진──> BOOT
                     │                     (8.1.6 · 그림 8-56)
                     └─ NOTI_DISCONNECT / 링크 오류 ──> DISCONNECTED     (8.2.1.3)
```

| 상태 | 표준 근거 | 연결 승인 여부 |
|---|---|---|
| `INIT` / `CONNECTING` | 8.1.1 연결 설정, 그림 8-3 | 전 |
| `HALTED` | — (구현 상태) | 전 · 영구 |
| `RUNNING` | 8.1.1 이후 정상 운용 | **후** |
| `FAULT` | 7.3.2 NEC + 8.2.1.1 오류 알림 | **후** |
| `REBOOTING` | 8.1.6 리부팅, 8.2.1.4 · 그림 8-56 | 후 |
| `DISCONNECTED` | 8.2.1.3 연결 해제 알림 | 후 (재접속 대기) |

**`FAULT` 는 연결 승인 이후에만 존재한다 (F-072).** 초안은 부팅 자가진단 실패도 `FAULT` 로 보내고
모든 `FAULT` 의 복구를 `RUNNING` 으로 되돌렸다. 그러면 **`CONNECTING` 을 한 번도 거치지 않은 노드가
조회·설정·알림을 수행**하게 되어 8.1.1 의 "초기 연결승인 절차"가 무의미해진다.

바로잡은 규칙은 둘이다.

1. **자가진단 실패는 연결을 막지 않는다.** 해당 디바이스의 `Status` 를 `ABNORMAL`(0x01, 표 7-13/7-15)로
   두고 연결을 진행한다. `NOTI_ERROR` 는 연결 뒤에 보낸다 — 미등록 노드의 프레임은 게이트웨이가
   `INVALID_NODE_ID` 로 거부하므로 연결 전에는 **알릴 수단 자체가 없다.**
2. **연결이 영구히 불가하면 `HALTED`.** 재시도 불가 RSC(§6.5)를 받으면 노드가 프로토콜로 할 수 있는 일이
   없다. `NOTI_ERROR` 를 반복해도 같은 이유로 거부된다. 로컬 표시(LED)만 하고 멈춘다.

> 초안은 재시도 불가 RSC 를 `FAULT` 로 보내 `NOTI_ERROR` 를 반복하게 했다. **연결이 거부된 노드의
> `NOTI_ERROR` 는 게이트웨이가 받지 않는다** — 스스로 만든 §6.5 규칙이 §6.1 에서 무효였다.

### 6.2 전이표

| 현재 | 사건 | 다음 | 동작 |
|---|---|---|---|
| BOOT | 초기화 완료 | INIT | 디바이스 자가진단. 실패분은 `Status`=ABNORMAL |
| INIT | 항상 | CONNECTING | `REQ_SET_CONNECTION` 송신, `pending` 등록 |
| CONNECTING | `RES_SET_CONNECTION` RSC=SUCCESS | RUNNING | `NODE_PROPERTY`·`DEVICE_PROPERTY` 적용, 타이머 3종 시작 |
| CONNECTING | RSC ≠ SUCCESS (재시도 가능) | CONNECTING | `Timeout` 후 재송신, `msg_id` **유지** (§6.4) |
| CONNECTING | RSC ≠ SUCCESS (재시도 불가) | HALTED | 로컬 표시만. 프로토콜 동작 정지 |
| CONNECTING | 재전송 소진 | DISCONNECTED | 백오프 시작 |
| RUNNING | `Period` 만료 / 임계 이탈 | RUNNING | `NOTI_DEVICE_VALUE` 송신 → `pending` 등록 (8.2.1.2) |
| RUNNING | `Keep Alive Interval` 만료 | RUNNING | `NOTI_KEEP_ALIVE` 송신 → `pending` 등록 (8.2.1.5) |
| RUNNING | G→N 요청 수신 | RUNNING | 처리 후 대응 `RES_*` 회신 (7.3.1) |
| RUNNING | 디바이스 오류 감지 | FAULT | `NOTI_ERROR` 송신 → `pending` 등록 (8.2.1.1) |
| RUNNING | `REQ_SET_REBOOT` 수신 | REBOOTING | `RES_SET_REBOOT` 회신 → `NOTI_REBOOT` 송신 → `pending` 등록 (8.1.6) |
| FAULT | `Notify Error Interval` 만료 | FAULT | `NOTI_ERROR` 재송신 (8.2.1.1) |
| FAULT | 오류 해소 | RUNNING | `Status` = NORMAL 로 갱신 |
| REBOOTING | `NOTI_REBOOT` 의 ACK 수신 | BOOT | "리부팅 알림 성공" → 소프트 리셋 (그림 8-56) |
| REBOOTING | `NOTI_REBOOT` 재전송 소진 | BOOT | "리부팅 알림 실패" → 그래도 리셋 (그림 8-56) |
| DISCONNECTED | 백오프 만료 | CONNECTING | `REQ_SET_CONNECTION` 재송신 |
| HALTED | 어떤 사건에도 | HALTED | **아무것도 하지 않는다.** 수신 프레임을 읽어 버리고 응답하지 않는다. 전원 재인가로만 벗어난다 |
| **(HALTED 제외 전 상태)** | **G→N Notify 수신** | 유지 | **`ACK` 즉시 회신** (6.1.2). §6.2-a |
| **(HALTED 제외 전 상태)** | 송신 Notify·Request 의 ACK/RES 수신 | 유지 | `pending` 해제 (§6.4) |
| **(HALTED 제외 전 상태)** | `pending` Timeout | 유지 | `msg_id` 유지한 채 재송신. 소진 시 상태별 사건 발생 |
| **(HALTED 제외 전 상태)** | `NOTI_DISCONNECT` 수신 / 링크 오류 | DISCONNECTED | ACK 회신 후 타이머 정지 (8.2.1.3) |

위 넷을 뺀 조합, 즉 **응용 처리가 필요한 (상태, 사건) 조합이 표에 없으면 무시하고 프레임을 버린다.**
예를 들어 `CONNECTING` 중에 `REQ_SET_DEVICE_CONTROL` 이 오면 처리하지 않는다 — 아직
`DEVICE_PROPERTY` 를 받지 못해 대상 디바이스의 유효 범위를 모르기 때문이다.

> **`HALTED` 는 "상태 무관" 전이의 유일한 예외다 (F-076).** 초안은 이 넷을 `(상태 무관)` 으로
> 적어두고 `HALTED` 를 "전원 재인가로만 벗어난다"고도 적었다 — **두 문장이 동시에 참일 수 없다.**
> `NOTI_DISCONNECT` 한 통이면 `HALTED → DISCONNECTED` 로 빠져나가고, ACK 회신도 "프로토콜 동작
> 정지"와 양립하지 않는다. `HALTED` 는 게이트웨이가 이 노드를 **등록하지 않은** 상태이므로
> 애초에 정상 프레임이 도착할 이유가 없고, 도착하더라도 응답하면 안 된다.

### 6.2-a Notify 의 ACK 생명주기 (F-071)

초안은 ACK 를 `RUNNING` 행 하나에만 두고, 송신 Notify 에는 재전송 개념을 두지 않았다.
표준은 양방향 모두를 규정한다.

**(1) 수신 Notify → ACK 는 상태 게이트보다 앞선다.**

0943 6.1.2 — "ACK 메시지는 **노드가 알림 메시지를 정상적으로 수신했을 경우** 이에 대한
응답메시지로써 온실통합제어기로 전송되며, 메시지 헤더 정보만을 포함한다."

조건은 **정상 수신**이지 노드의 상태가 아니다. 따라서 `CONNECTING`·`FAULT`·`DISCONNECTED` 에서
`NOTI_DISCONNECT`·`NOTI_REBOOT` 를 받아도 ACK 를 보낸다. 이것은 게이트웨이 측
`contracts/frame.py` 의 `reply_kind()` 가 상태와 무관하게 회신 종류를 정하는 것과 **대칭**이다
(CLAUDE.md §3.4 — 표준 해석은 프로토콜 계층에만 있다).

> 위반 Notify 에는 ACK 를 보내지 않는다 — ACK 는 헤더뿐이라 오류 RSC 를 실을 수단이 없다 (F-040).
> 조건이 "정상적으로 수신했을 경우"이므로 표준 문언과도 맞는다.

**(2) 송신 Notify → ACK 대기·재전송은 Request 와 같은 생명주기다.**

0943 8.2.1 — "8.2.1의 Notify-ACK 메시지 흐름은 **제한된 재전송 횟수 내** 정상적으로 (…) 알림이
된 경우 (그림 8-45)와 그렇지 못한 경우 (그림 8-46)을 따른다."

그림 8-45 는 `Notify [numRetry: 1] … [numRetry: N]` 로 재전송을 명시한다. 즉 알림도 요청과
동일하게 `Message Receive Timeout` 대기 · `Num. of Retry` 회 재전송이다. 그래서 노드는
**요청과 알림을 구분하지 않는 단일 `pending` 슬롯**으로 처리한다(§6.4).

**(3) `REBOOTING` 의 완료 조건 (그림 8-56).**

```
NOTI_REBOOT 전송 ─> ID 일치 확인 ─> 리부팅 알림 ─> GCG 가 ACK 전송
                                                      └─> [리부팅] 알림 성공 ─┐
재전송횟수 > numRetry ────────────> [리부팅] 알림 실패 ──────────────────────┴─> 노드 리부팅 완료
```

초안은 `NOTI_REBOOT 송신 완료` 만으로 리셋했다. 그림은 **ACK 수신 또는 재전송 소진** 뒤에
"노드 리부팅 완료"로 간다. 송신 버퍼에 쓴 것과 상대가 받은 것은 다르다 — 특히 리부팅은
리셋 후 상태를 잃으므로, 알림이 전달되지 않으면 게이트웨이가 노드를 `STALE` 로 오판한다.

**(4) `NOTI_DEVICE_VALUE` 재전송 시의 값 — 표준 미규정.**

스트리밍 송신은 보낸 프레임을 보관하지 않으므로(§5.8) 재전송은 **재인코딩**이다. 그 사이 센서값이
바뀌었으면 어느 값을 보내야 하는가. 표준은 규정하지 않는다.

**결정: 재인코딩 시점의 현재값을 보낸다. `Message Identifier` 는 유지한다.**
근거는 셋이다. ① 알림의 목적이 현재값 전달이다. ② 원본 보관은 7×N byte(N=16 이면 112 B)를
요구해 스트리밍 결정과 충돌한다. ③ 중복 판정은 `msg_id` 로 하므로(7.2.2) 유지만 하면 성립한다.

### 6.3 타이머 3종 + 디바이스별 주기 (F-130)

| 타이머 | 출처 | 기본값 | 동작 |
|---|---|---|---|
| `Message Receive Timeout` | 표 7-18 | 2 s | 송신 요청의 응답 대기 상한 |
| `Notify Error Interval` | 표 7-18 | 30 s | `FAULT` 에서 `NOTI_ERROR` 반복 주기 |
| `Keep Alive Interval` | 표 7-18 | 60 s | `NOTI_KEEP_ALIVE` 주기 |
| `Period` | 표 7-15 (디바이스별) | 60 s | 아래 참조 |

값은 전부 **초**다 (F-033). `millis()` 는 밀리초이므로 비교 시 1000을 곱한다.

**`Period` — 표준상 의미와 구현 내부 재사용을 분리한다.** 표 7-15는 `Period`를
"데이터 전달주기"로 정의한다. 본 구현은 디바이스 샘플링·오류 감지 주기를 위한
별도 필드를 두지 않으므로, 이미 있는 `Period`를 **내부 스캔 간격으로도
재사용한다** — 이는 표준 필드 의미의 재정의가 아니라 이 구현이 그 필드를
어디까지 활용하는가의 문제다(표준 미규정 결정, §9). 각 디바이스는 `Transfer
Mode`(Periodic/Event/Both)와 무관하게 자기 `Period` 마다 스캔되고, 오류
감지(8.2.1.1)도 이 스캔에 얹힌다 — Event 전용 디바이스도 Periodic 디바이스의
존재 여부와 무관하게 자기 주기로 오류를 감지한다.

**스캔 결과의 처리 — `Transfer Mode` 가 가른다.**

| `Transfer Mode`(표 7-15) | 스캔에서 하는 일 |
|---|---|
| Periodic | 무조건 값을 전송한다 |
| Event | `Value` 가 `[Lower Value, Upper Value]` 밖일 때만 전송한다(값 해석은 `Value Type` 을 따른다, F-022) |
| Both | 무조건 전송한다 |

**Both 는 이 구현에서 Periodic 과 동일하게 동작한다 — 알려진 제약이다.**
표준은 Both 를 "주기적으로도, 임계 이탈 시에도" 보내는 모드로 의도했다고
읽을 수 있으나, 본 구현은 디바이스마다 스캔이 자기 `Period` 한 번뿐이라
주기 사이의 임계 이탈을 조기에 감지할 방법이 없다 — 스캔 시점에 매번
무조건 전송하므로 결과적으로 Periodic 과 구분되지 않는다. 이벤트 전용의
더 짧은 감시 간격(디바이스별 두 번째 스케줄, 또는 전역 이벤트 틱)을
검토했으나 AVR 2KB SRAM·타이머 3종 예산과 충돌하는 폭으로 구현이 커져
채택하지 않았다(표준 미규정 결정, §9).

**`Period` = 0.** §4.1-a 는 0을 거부하지 않는다. 0은 "사실상 매 poll 마다
스캔"(가장 촘촘한 감시)으로 허용한다 — `_advance_deadline()` 이
`interval == 0` 이면 `now + 1` 을 돌려주는 동작을 그대로 정본으로 삼는다
(표준 미규정 결정, §9).

### 6.4 `millis()` 롤오버와 재전송

**롤오버.** ATmega328P의 `millis()` 는 32bit로 약 49.7일에 한 번 0으로 돌아간다. 비교는 반드시 뺄셈으로 한다.

```c
/* ○ 부호 없는 뺄셈은 롤오버를 넘어서도 올바르다 */
if ((uint32_t)(io->millis(io->ctx) - t_start) >= timeout_ms) { ... }
/* ✕ 절대 시각 비교는 롤오버 시점에 한 번 오작동한다 */
if (io->millis(io->ctx) >= t_start + timeout_ms) { ... }
```

**`Message Identifier` 는 0부터 시작해 매 송신 +1, `0xFFFF` 다음은 `0`으로 순환한다 — 7.2.2 원문 그대로다("'0'에서 '65535'까지 사용… 만료되면 0부터 다시 시작").** 이전 버전은 "0은 미할당 표시로 예약"이라며 0을 건너뛰었으나(§9 표에 있었다), `pending` 슬롯의 비어 있음 판정은 `pending.kind==SIAP_KIND_NONE` 하나로 충분해 `msg_id==0` 을 센티널로 쓰는 코드가 실제로는 없었다 — 근거 없이 표준 문구와 어긋난 자체 결정이었다(F-135, §9 표에서 제거). §9 목록은 실제로 표준이 규정하지 않는 항목만 남긴다.

**재전송 시 `Message Identifier` 를 유지한다** (CLAUDE.md §3.5, F-041). 새로 발번하면 게이트웨이가 별개 요청으로 처리해 중복 등록이 생긴다. 게이트웨이 측 결정과 대칭이다.

**응답 매칭 조건은 셋이다** — `Node ID` + `Message Identifier` + **`Message Type`** (F-046). 노드도 동일하게 적용한다. `msg_id` 만 보면 우연히 번호가 겹친 ACK 가 대기를 해제한다.

**`pending` 슬롯 — 요청과 알림 공통 (F-071).** 8.1(그림 8-1/8-2)과 8.2.1(그림 8-45/8-46)은
같은 형태의 재전송 흐름이다. 그래서 하나의 슬롯으로 처리한다.

```c
typedef struct {
    uint8_t  kind;        /* 대기 중인 송신 종류. SIAP_KIND_NONE = 비어 있음 */
    uint16_t msg_id;      /* 재전송에도 유지 (F-041) */
    uint8_t  retry;       /* 지금까지 재전송한 횟수 */
    uint32_t t_sent;      /* 마지막 송신 시각 (ms) */
    uint16_t arg;         /* 재인코딩 인자: NEC 코드 또는 대상 device 비트마스크 */
} siap_pending_t;         /* 1 + 2 + 1 + 4 + 2 = 10 B (3.4) */
```

| 규칙 | 내용 |
|---|---|
| 동시 대기 | **1건.** 응답을 받기 전에는 새 요청·알림을 보내지 않는다. AVR 에서 큐를 두면 메모리가 N 에 비례한다 |
| 해제 조건 | `Node ID` + `msg_id` + `expected_reply(kind)` 세 개 일치 (F-046) |
| Timeout | `Message Receive Timeout` (기본 2초, §6.3) |
| 재전송 상한 | `Num. of Retry` (표 7-18) |
| 재전송 방법 | **재인코딩.** 스트리밍이라 원본을 보관하지 않는다. `kind` + `arg` + 디바이스 테이블로 다시 만든다 (§6.2-a (4)) |
| 소진 시 | 상태별 사건 발생 — `CONNECTING` → `DISCONNECTED`, `REBOOTING` → `BOOT`, 그 외 → 알림 폐기 후 계속 |

### 6.4-a 주기 알림의 기아 방지 (F-077)

**초안의 결함.** "대기 중 만료한 주기 타이머는 건너뛰고 다음 주기를 기다린다"고 정했다. 그런데
기본 프로파일은 `Period` = 60 s, `Keep Alive Interval` = 60 s 로 **같다**(§6.3). 연결 성공 시
타이머 3종을 함께 시작하므로 두 타이머는 **매번 같은 시각에 만료**한다. 검사 순서가 고정이면
지는 쪽이 영구히 굶는다.

```
t=60s   Device Value 가 먼저 pending 등록 → Keep Alive 는 건너뜀
t=120s  두 타이머가 다시 동시 만료 → 같은 순서로 Keep Alive 또 건너뜀
...     NOTI_KEEP_ALIVE 가 한 번도 나가지 않는다
```

정상 링크·기본 설정에서 발생한다. `NOTI_KEEP_ALIVE` 가 굶으면 게이트웨이가 정상 노드를
`STALE` 로 판정하고(아키텍처 §6.1), 반대 순서면 주기 센서 데이터가 통째로 사라진다.

**바로잡은 규칙 — `due` 비트 + 회전 커서.**

| 규칙 | 내용 |
|---|---|
| 만료 시 | 해당 소스의 **`due` 비트를 세운다.** 이미 서 있으면 그대로 둔다 (중복 누적 없음) |
| 기준시각 | 만료 시각에 `+= interval`. **현재 시각으로 리셋하지 않는다** — 리셋하면 주기가 밀린다 |
| 송신 선택 | `pending` 이 비면 **회전 커서**가 가리키는 다음 `due` 소스를 하나 보내고 커서를 전진 |
| 전송 후 | 그 소스의 `due` 비트만 내린다 |

```c
uint8_t due;      /* bit0 DEVICE_VALUE / bit1 KEEP_ALIVE / bit2 ERROR */
uint8_t cursor;   /* 다음에 우선권을 갖는 소스 번호. 전송할 때마다 +1 (mod 3) */
```

**2 byte 로 기아가 사라진다.** 큐를 쌓지 않으므로 링크가 오래 막혀도 메모리가 늘지 않고
복구 직후 폭주하지도 않는다 — 각 소스는 밀린 횟수와 무관하게 **한 번만** 보낸다.
"건너뛴 사실은 다음 `NOTI_DEVICE_VALUE` 가 최신값을 실어 만회한다"는 초안의 논리는 **`due` 비트가
있을 때만 성립**한다. 없으면 "다음"이 영원히 오지 않는다.

| 검증 | 내용 |
|---|---|
| 결정적 테스트 | 두 타이머를 같은 시각에 만료시켜 100주기를 돌린다. 두 소스 모두 **최소 45회** 송신되어야 한다 (회전이면 50회, 여유 5) |
| 위치 | `firmware/tests/test_node_state.c` (§8.1) |

> `NOTI_ERROR` 도 같은 회전에 넣는다. `FAULT` 에서 `Notify Error Interval` 마다 만료하므로
> 다른 둘과 주기가 겹칠 수 있다.

### 6.5 `RES_SET_CONNECTION` 의 오류 RSC — 표준 미규정

8.1.1은 "연결 요청에 대한 상태에 따라 RSC 정보가 업데이트되어 전송된다"까지만 적고, **노드가 오류 RSC를 받으면 무엇을 해야 하는지 정하지 않는다.** 무한 재시도하면 링크를 점유하고, 즉시 포기하면 일시적 오류에서 복구하지 못한다.

RSC 10종을 재시도 가능 여부로 분류한다.

| RSC | 코드 | 재시도 | 근거 |
|---|---|---|---|
| `SUCCESS` | 0x00 | — | 정상 |
| `INVALID_VERSION` | 0x01 | **불가** | 펌웨어를 바꾸지 않는 한 같은 결과 |
| `INVALID_GCG_ID` | 0x02 | **가능** | 게이트웨이 설정 변경으로 해소될 수 있다 |
| `INVALID_NODE_ID` | 0x03 | **가능** | 운영자가 노드를 등록하면 해소된다 |
| `INVALID_DEVICE_ID` | 0x04 | 불가 | 노드의 디바이스 구성이 고정이다 |
| `INVALID_DEVICE_TYPE` | 0x05 | 불가 | 〃 |
| `INVALID_DATA_TYPE` | 0x06 | 불가 | 〃 |
| `INVALID_DATA_SUBTYPE` | 0x07 | 불가 | 〃 |
| `INVALID_TRANSMISSION_TYPE` | 0x08 | 불가 | 노드가 보낸 값이 고정이다 |
| `INVALID_FORMAT` | 0x09 | 불가 | 노드의 인코딩 결함. 재시도해도 같다 |

- **가능 2종**: 백오프 후 `CONNECTING` 재시도. 백오프는 `Timeout × 2ⁿ`, 상한 300초.
- **불가 7종**: `HALTED` 로 전이한다. 로컬 표시(LED)만 하고 프로토콜 동작을 멈춘다.

> **초안은 여기서 `FAULT` 로 보내 `NOTI_ERROR` 를 반복하게 했다 (F-072).** 그런데 연결이 거부된
> 노드가 보내는 프레임은 게이트웨이가 `INVALID_NODE_ID` 로 거부한다 — **알림이 도달하지 않는다.**
> "조용히 멈추지 않는다"는 원칙은 옳지만, 그 원칙을 지킬 수단이 프로토콜에 없다.
> 없는 수단을 있는 것처럼 적는 것이 더 나쁘므로 `HALTED` 로 바꾸고 한계를 명시한다.
> 진단 경로는 게이트웨이 쪽에 있다 — 거부한 게이트웨이가 그 사실을 알고 화면에 띄운다(기능 2).

> `INVALID_NODE_ID` 를 "가능"으로 둔 것이 판단이 갈리는 지점이다. 노드 입장에서 자기 ID는 고정이지만, **해소 주체가 노드가 아니라 운영자**이므로 노드가 계속 시도하는 편이 운영상 옳다고 보았다. 골든 `X02` 가 이 케이스의 게이트웨이 측 판정이다.

### 6.6 구동기 노드의 입력 경로는 하나뿐이다

CLAUDE.md §1-7 "미승인 AI 규칙이 구동기로 전달되는 경로 생성 금지"의 펌웨어 대응이다.

| 구동기를 움직일 수 있는 경로 | 존재 여부 |
|---|---|
| `REQ_SET_DEVICE_CONTROL` (8.1.5) 수신 → `dev_ops.write_value` | **유일하게 존재** |
| 노드 내부 규칙 엔진 (임계값 판단 → 자동 구동) | **없다** |
| 외부 단말 직접 접속 (5.2.2가 언급) | **구현하지 않는다** |
| AI 모델·추론 코드 | **없다** |

**`firmware/arduino_actuator_node/` 에서 `dev_ops.write_value` 를 호출하는 곳은 `core/` 의 `REQ_SET_DEVICE_CONTROL` 처리 경로 한 군데뿐이다.** 승인 여부는 서버가 판정한다(`control_rule.approved_at` + 트리거 4종). 노드는 승인을 확인할 수단이 없고, 확인할 필요도 없다 — **경로 자체가 하나이므로 서버를 우회할 방법이 없다.**

> 센서 노드의 `Transfer Mode` = Event/Both 는 임계 이탈 시 **알림을 보낼 뿐** 구동기를 건드리지 않는다(표 7-15). 자율 판단으로 보이지만 구동 경로와 무관하다.

**검증**: `firmware_verify.py` 가 보드 디렉터리에서 `write_value` 호출 지점을 세고, `core/` 밖에서 호출되면 FAIL 한다.

## 7. 보드 3종 바인딩

### 7.1 무엇이 같고 무엇이 다른가

| 항목 | Uno (센서) | Pro Mini (구동기) | ESP32 (겸용) |
|---|---|---|---|
| `firmware/core/` | **동일 파일** | **동일 파일** | **동일 파일** |
| 프레임 바이트열 | **동일** | **동일** | **동일** |
| 상태 머신 | **동일** | **동일** | **동일** |
| 전송 계층 | UART 9600 8N1 | UART 9600 8N1 | TCP over Wi-Fi |
| `siap_io_t.read_byte` | `Serial.read()` | `Serial.read()` | `client.read()` |
| `siap_dev_ops_t` | ADC 읽기 | 릴레이 출력 | 양쪽 |
| 디바이스 수 | 3 | 2 | 3 |
| `Subtype` | 0x01 온도 / 0x02 습도 / 0x08 토양수분장력 | 0x85 관수밸브 / 0x83 송풍기 | 0x01 / 0x03 / 0x81 |

**다른 것은 아래 3줄뿐이다.**

```c
/* Uno / Pro Mini */
static int8_t uart_read(void *c, uint8_t *o){ if(!Serial.available()) return 0; *o=Serial.read(); return 1; }
/* ESP32 */
static int8_t tcp_read (void *c, uint8_t *o){ WiFiClient*w=(WiFiClient*)c; if(!w->available()) return 0; *o=w->read(); return 1; }
```

### 7.2 Uno 센서 노드 (`arduino_sensor_node/`)

| 파일 | 내용 |
|---|---|
| `main.ino` | `siap_node_init` + `siap_node_poll` 루프 |
| `pins.h` | 핀 매핑 상수 |
| `sensors.c` | `dev_ops.read_value` 구현. ADC → 물리량 변환 |

`read_value` 는 **32bit 원시 비트열**을 반환한다. FLOAT 디바이스면 `bp_memcpy` 로 float 비트를, INT 디바이스면 정수를 그대로 넣는다. 어느 쪽인지는 `dev_table[i].value_type` 이 정하며 `core/` 가 그 값을 그대로 실어 보낸다.

> **합성 데이터 금지** (CLAUDE.md §1-1). `read_value` 는 언제나 실제 ADC 를 읽는다. 센서가 연결되지 않았으면 값을 지어내지 않고 `-1` 을 반환하며, `core/` 는 해당 디바이스 `Status` 를 `ABNORMAL`(0x01)로 두고 `NOTI_ERROR`(`ERROR_DEVICE_INTERFACE`, 0x01)를 보낸다.

### 7.3 Pro Mini 구동기 노드 (`arduino_actuator_node/`)

| 디바이스 | Device ID | Subtype | Value Type | 의미 |
|---|---|---|---|---|
| 관수밸브 | 0x01 | 0x85 | UINT | 0 = OFF / 1 = ON |
| 송풍기 | 0x02 | 0x83 | UINT | 0 = OFF / 1 = ON |

`write_value` 는 `digitalWrite` 한 줄이다. **범위 검사는 `core/` 가 `DEVICE_PROPERTY.Lower/Upper Limit` 로 이미 마쳤다** — 보드가 다시 판단하면 표준 해석이 두 곳에 생긴다(CLAUDE.md §3.4의 펌웨어 대응).

### 7.4 ESP32 (`esp32_node/`)

| 항목 | 결정 |
|---|---|
| 전송 | TCP 클라이언트. 게이트웨이가 리스너 |
| 프레임 | **바이트열을 그대로 태운다.** 길이 프리앰블·JSON 래핑 없음 |
| 재접속 | TCP 끊김 → `DISCONNECTED` → 백오프 → `CONNECTING` (UART 링크 오류와 동일 경로) |
| Wi-Fi 자격증명 | `secrets.h` 를 `.gitignore` 에 두고, 리포지터리에는 `secrets.h.example` 만 둔다 (CLAUDE.md §1-2) |

**같은 바이트열이 UART와 TCP 위를 그대로 지나간다**는 것이 3종 혼용 주장의 핵심이다. TCP라고 해서 프레임 앞에 길이를 붙이면 "동일 프로토콜" 이 아니게 된다. TCP는 손실이 없으므로 §5.7의 재동기 없이도 동작하지만, **재동기 코드는 `core/` 에 있고 ESP32도 그대로 쓴다** — 보드별 분기를 만들지 않기 위해서다.

### 7.5 "`core/` 무수정" 의 판정 기준

주장이므로 판정 방법을 명시한다.

1. `firmware/core/` 의 모든 파일에 대해 3종 빌드 전후 **SHA-256이 동일**하다.
2. `core/` 에 `#ifdef ARDUINO`, `#ifdef ESP32`, `#ifdef __AVR__` 같은 **보드 판별 매크로가 0개**다.
3. 3종이 골든 벡터 53건에 대해 **동일한 바이트를 낸다**.

1·2는 `firmware_verify.py` 가, 3은 `test_golden.c` 가 판정한다.

> 2번이 실질적 기준이다. 조건부 컴파일 하나만 들어가도 "동일 응용계층" 이 아니라 "보드별 분기가 있는 공통 코드" 가 된다.

### 8.2 골든 벡터를 C에서 읽는 방법

`golden.jsonl` 을 C에서 파싱하려면 JSON 파서가 필요하다. 의존성을 늘리지 않기 위해 **빌드 시점에 헤더로 변환**한다.

```
contracts/vectors/golden.jsonl
        │  make golden_data.h   (tests/gen_golden_h.py, 표준 라이브러리만 사용)
        ▼
firmware/tests/golden_data.h    ← 생성물. 커밋하지 않는다
```

```c
typedef struct { const char *id; const uint8_t *bytes; uint16_t len;
                 uint8_t kind; int32_t n; uint8_t rsc; } golden_vec_t;
```

- **생성물이므로 커밋하지 않는다.** `golden.jsonl` 이 정본이고 그 정본은 `golden_layout.py` 다. 3단 생성 사슬의 어느 단계도 손으로 고치지 않는다.
- `gen_golden_h.py` 는 **`--check` 모드를 갖는다** (F-063 · F-066과 같은 이유). 커밋된 파일이 있으면 재생성 결과와 바이트 비교만 하고 쓰지 않는다.

```make
         -Werror=unused-result -Wshift-count-overflow
# -Wconversion         : 비트 폭 축소를 컴파일 오류로 만든다. 14bit/20bit 필드를
#                        다루는 코드에서 uint16_t <- uint32_t 축소가 조용히 일어나면
#                        골든 벡터가 깨지기 전까지 드러나지 않는다.
# -Werror=unused-result: bp_write 의 false 를 버리면 빌드가 실패한다 (F-078).
#                        SIAP_WUR 속성과 짝이며, 둘 중 하나만 있으면 무효다.
# -Wshift-count-overflow: 1u << 32 류의 UB 를 잡는다. 범위 검사식이 마스크로
#                        바뀐 근거가 이 경고다 (F-078).

all: test_siap_frame test_status_codes test_golden test_node_state
golden_data.h: ../../contracts/vectors/golden.jsonl gen_golden_h.py
	python gen_golden_h.py
```

## 10. 신규 표준결함 — 프레임 경계·무결성 검사 미규정

**원문 확인 완료.** `TTAK.KO-10.0943.md` 전문에서 `CRC` · `체크섬` · `구분자` · `동기화`(프레임 문맥) · `물리 계층` 어느 것도 검색되지 않는다.

| 항목 | 내용 |
|---|---|
| 위치 | 표 1-1 (통신 환경) ↔ 7장 (메시지 구성) |
| 등급 | **치명적** |
| 내용 | 표 1-1은 통신 환경으로 **유선(Ethernet, RS232, 485 등)** 을 명시한다. Ethernet은 자체 계층에서 프레이밍과 FCS를 제공하지만 **RS232/485는 순수 바이트 스트림**이다. 그런데 7장은 프레임 시작 구분자·길이 프리앰블·체크섬을 하나도 정의하지 않는다. 바이트 1개가 유실되면 수신기는 프레임 경계를 영구히 잃고, 손상된 바이트는 탐지되지 않은 채 유효 필드로 해석된다 |
| 영향 | ① 재동기 불가 — 표준만 구현한 두 노드가 노이즈 후 복구되지 못한다. ② `Payload Length` ≠ 실제 위반(기능 2의 3번)이 UART에서 즉시 탐지되지 않는다(§5.5). ③ 재동기 규칙이 구현마다 달라 노이즈 환경의 복구 시점이 상호운용되지 않는다 |
| 본 구현의 처리 | §5.7의 4조건 헤더 타당성 검사 기반 재동기. 표준 프레임 형식은 **바꾸지 않는다** — 구분자나 CRC를 덧붙이면 그 순간 표준 준수가 아니게 된다 |

**총계 갱신**: 0943 12건 → **13건**, 1369-P1 6건 유지, **합계 19건**.
`SIAP_메시지_명세서.md` §6 에 `#10` 으로 추가하고, `CLAUDE.md` §3.6 · `fix_log/bug_fix_list.md` 의 `표준결함` 행 수를 함께 갱신한다.

> 이것은 이 프로젝트가 **구현을 해보아야만 나오는 종류의 발견**이다. 명세서만 작성하는 단계에서는 프레임이 이미 한 덩어리로 주어진다고 가정하게 되고, 바이트 스트림 위에 올려놓기 전까지 드러나지 않는다.
