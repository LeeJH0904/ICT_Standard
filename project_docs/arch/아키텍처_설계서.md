## 3. 데이터 흐름

### 3.1 수신 (노드 → 화면)

```
  바이트          Frame                     회신 Frame
    │               │                            │
[transport] ──> [codec] ──┬──> [link._default_reply] ──> [transport]   (즉시 회신, §3.1-a)
                           │
                           └──> [ingest.handle] ──> [repository] ──> [api] ──> [web]
                                     │
                                     ├─ frame_log + frame_violation   (기능 2)
                                     ├─ device_install_info 자동 등록  (기능 1)
                                     ├─ env_state_data + env_measurement
                                     └─ alert                          (0937 6.4·6.5)
```

**F-154 — 회신 구성과 DB 반영은 서로 다른 두 갈래다.** 이전 판(F-040 채택 시점)은
`ingest.handle(frame) -> Frame | None`이 즉시 회신까지 반환하는 단일 진입점이었다.
`backend/`가 회신을 만들려면 `siap/build.py`(`FrameBuilder`)를 알아야 했는데, 그러면
**표준 해석이 `backend/`에도 생긴다** — CLAUDE.md §3.4("표준 해석은 프로토콜 계층에만")
위반이다. 실제 구현은 반대로 갈렸다:

- **회신은 `siap/link.py::_default_reply()`가 만든다.** `siap/`가 `siap/build.py`를
  그대로 쓰므로 `backend/`를 몰라도 완결된다 — `backend/`가 아직 없던 단계 4부터
  이미 이렇게 동작했고, 단계 5에서 `backend/`가 생긴 뒤에도 바뀌지 않는다.
- **`backend.ingest.handle(frame, conn)`은 DB 반영만 하고 아무것도 반환하지 않는다
  (`-> None`).** `siap/link.py`의 `on_frame` 훅(부수효과 전용, 반환값 무시)에
  연결한다(`run.py`, F-160). `backend.ingest.bind(conn)`(단일 인자 콜백 어댑터)이
  있지만 `run.py`는 이를 직접 쓰지 않는다 — `on_frame`은 SIAP I/O 스레드 안에서
  호출되는데 `bind(conn)`은 호출자가 미리 연 연결을 그대로 가두므로, 다른
  스레드(메인 스레드)에서 연 연결을 넘기면 `sqlite3.ProgrammingError`가 난다
  (§4.1 "스레드별 연결", F-160 재현·F-167). `run.py::_make_on_frame(db_path)`는
  DB **경로**만 받아 그 스레드 안에서 지연 연결한다 — `bind(conn)`은 스레드
  경계가 이미 보장된 호출자(테스트 등)를 위해 남아 있다.

**`ingest.handle(frame, conn)` 이 서비스 계층의 유일한 진입점이다.** 이 함수 위쪽에 로직을 두면 `Frame`이 어디서 왔는지 서비스 계층이 알게 되어 계층이 무너진다.

```python
def handle(frame: Frame, conn: sqlite3.Connection) -> None:
    """Frame 1건을 DB에 반영한다. 회신은 여기서 만들지 않는다(F-154) —
    회신은 항상 siap/link.py::_default_reply() 가 만들고, 이 함수는
    on_frame 훅으로 부수효과만 수행한다."""
    repo.insert_frame_log(conn, frame)             # 모든 프레임 (기능 2)

    if frame.violations:                          # 0943 7.3.1
        repo.insert_violations(conn, frame)        # 격리 (기능 2 화면의 정본)
        return

    match frame.kind:
        case MsgKind.NOTI_DEVICE_VALUE:        _handle_device_value(conn, frame)  # 8.2.1.2
        case MsgKind.NOTI_ERROR:               _handle_error(conn, frame)         # 8.2.1.1
        # F-198 — 아래 두 case 는 REQ_SET_CONNECTION(8.1.1)이 아니다. 그
        # 메시지는 페이로드가 없어(LAYOUT (0,0)) device_properties 를 실을
        # 수 없다 — 예전 버전은 REQ_SET_CONNECTION 에 등록 로직을 바인딩해
        # 둬 한 번도 실행되지 않는 죽은 코드였다. 노드가 자신의 디바이스
        # 구성을 선언하는 실제 통로는 이 두 메시지다(8.1.3.2/.3, 노드→GCG).
        #
        # 한 case 안에 서로 다른 두 관심사가 함께 있다 — ①
        # _handle_device_property() 는 등록(1369-P1 device_info 등, F-198,
        # 이미 구현됨) ② ems.on_*() 는 0937 6.1 "업무 로직"(F-079, 예: 6.1-2
        # "구동 주기 관리" 판정 — DEVICE_PROPERTY.Period 가 그 대상이다)이며
        # 단계 6에서 여전히 미구현이다(services/ems.py 에 on_* 함수 없음,
        # F-198 처리 중 재확인 — F-163 이 이미 남긴 미해결 지점과 같다).
        # 회신의 RSC 는 이미 _default_reply() 가 SUCCESS 로 낸 뒤이므로,
        # ems 판정을 즉시 회신에 반영하려면 이 배치를 다시 본다.
        case MsgKind.REQ_SET_DEVICE_PROPERTY:
            _handle_device_property(conn, frame)            # 8.1.3.2 — 등록(F-198)
            # ems.on_device_property(frame)                   # 0937 6.1 업무 로직 — 미구현(F-079)
        case MsgKind.REQ_SET_NODE_DEVICE_PROPERTY_ALL:
            _handle_device_property(conn, frame)            # 8.1.3.3 — 등록(F-198)
            # ems.on_node_device_all(frame)                    # 0937 6.1 업무 로직 — 미구현(F-079)
        case MsgKind.REQ_SET_NODE_PROPERTY:
            pass
            # ems.on_node_property(frame)                      # 8.1.3.1 역방향 — 0937 6.1 업무 로직, 미구현(F-079)
        # 그 외(REQ_SET_MSG_FLOW_CONTROL_PROFILE, NOTI_DISCONNECT/REBOOT/
        # KEEP_ALIVE, RES_*, ACK 등)는 frame_log 만으로 충분하다.
```

```python
# siap/link.py — 즉시 회신은 이 함수가 전담한다. FrameBuilder(self._build)를
# 그대로 참조하므로 backend/ 없이도 완결된다.
def _default_reply(self, frame: Frame) -> Frame | None:
    if frame.violations:
        return self._build.error_response(frame, RSC(frame.violations[0].code))
    match frame.kind:
        case MsgKind.REQ_SET_CONNECTION:
            rsc, node = self._registry.on_connect(frame)
            return self._build.res_set_connection(frame, RSC.SUCCESS, node=node, devices=())
        # ...REQ_SET_NODE_PROPERTY / REQ_SET_DEVICE_PROPERTY / REQ_SET_NODE_DEVICE_PROPERTY_ALL
        # / REQ_SET_MSG_FLOW_CONTROL_PROFILE 도 같은 패턴 (8.1.3.1~4 역방향)
        case MsgKind.NOTI_ERROR | MsgKind.NOTI_DEVICE_VALUE | MsgKind.NOTI_DISCONNECT \
             | MsgKind.NOTI_REBOOT | MsgKind.NOTI_KEEP_ALIVE:
            return self._build.ack(frame)           # Notify 5종 공통 (6.2.2, 8.2.1)
        case _:
            return None      # RES_* / ACK — I/O 스레드가 대기 중인 요청과 매칭한다
```

### 3.1-a 즉시 회신 경로 (0943 6.2)

**0943은 양방향 모델이다.** 노드도 Request를 보내고(8.1.1 연결 설정, 8.1.3.1~8.1.3.4 설정 요청의 역방향), 모든 Notify에는 ACK가 필요하다(6.2.2). 회신 경로가 없으면 노드가 연결을 완료하지 못하고 Notify를 재전송한다 — 기능 1이 성립하지 않는다.

> **`_default_reply()` 안에서 `link.send()`를 부르면 안 된다.** `send()`는 요청 큐에 넣고 `Event`를 기다리는데, 그 큐를 처리하는 것이 지금 블로킹된 바로 그 I/O 스레드다 — **자기대기 교착**이다. 회신은 반드시 반환값으로 돌려준다(F-154 이전에는 `ingest.handle()`이 이 반환값을 냈다 — 지금은 `_default_reply()`가 낸다. 자기대기 회피라는 이유 자체는 바뀌지 않았다).

**회신 표 (정본: `contracts/frame.py` 의 `NODE_ORIGINATED_*` / `RESPONSE_OF` / `reply_kind()`)**

| 수신 | 회신 | 조항 |
|---|---|---|
| `REQ_SET_CONNECTION` | `RES_SET_CONNECTION` (RSC + NODE_PROPERTY + DEVICE_PROPERTY×N) | 8.1.1 |
| `REQ_SET_NODE_PROPERTY` | `RES_SET_NODE_PROPERTY` (RSC) | 8.1.3.1 |
| `REQ_SET_DEVICE_PROPERTY` | `RES_SET_DEVICE_PROPERTY` (RSC) | 8.1.3.2 |
| `REQ_SET_NODE_DEVICE_PROPERTY_ALL` | `RES_SET_NODE_DEVICE_PROPERTY_ALL` (RSC) | 8.1.3.3 |
| `REQ_SET_MSG_FLOW_CONTROL_PROFILE` | `RES_SET_MSG_FLOW_CONTROL_PROFILE` (RSC) | 8.1.3.4 |
| `NOTI_ERROR` · `NOTI_DEVICE_VALUE` · `NOTI_DISCONNECT` · `NOTI_REBOOT` · `NOTI_KEEP_ALIVE` | `ACK` (헤더만) | 6.2.2, 8.2.1.1~5 |
| `RES_*` · `ACK` | 없음 — I/O 스레드가 `Message Identifier`로 대기 중인 요청과 매칭 | 8.1 |

**위반 프레임의 회신 (F-040 / 0943 7.3.1)**

7.3.1은 "요청 처리 실패 시 Response에 해당 오류 코드를 담아 보낸다"고 규정한다. 표 7-10의 `INVALID_*` 코드는 그러기 위해 존재한다. 따라서 위반 프레임도 **버리지 않고 오류 RSC로 답한다.**

| 위반 프레임 | 회신 | 근거 |
|---|---|---|
| `kind`가 노드발 Request로 해석됨 | 대응 `RES_*` + 위반 RSC | 7.3.1, 표 7-10 |
| `kind`가 Notify로 해석됨 | **없음** | ACK는 헤더뿐이라 오류를 실을 수단이 없다 |
| `msg_type` 해석 불가 (Reserved 등) | **없음** | 어떤 Response를 만들지 정할 수 없다 |
| 헤더 12byte 미달 | **없음** | `Message Identifier`·`Node ID`를 모른다 |

> Notify 위반에 회신하지 않는 것은 **표준 미규정 사항에 대한 자체 결정**이다. 노드는 재전송하고, 재전송분도 같은 이유로 위반이면 기능 2 화면에 반복 위반으로 기록된다. `docs/standard-findings.md`에 등재한다.

회신 Frame의 `Message Identifier`·`GCG ID`·`Node ID`는 **수신 프레임의 값을 그대로 복사**한다(7.2.2). 새로 발번하면 노드가 매칭하지 못한다. 그래서 회신 빌더는 전부 원본 `Frame`을 인자로 받는다 — `build.ack(node_id, msg_id)`가 아니라 `build.ack(req)`다.

### 3.1-b I/O 이벤트 루프 (F-041)

수신 루프를 무한 블로킹으로 두면 **프레임이 한 건도 오지 않는 동안 API의 송신 요청이 포트로 나가지 못한다.** 수신·송신·재전송을 같은 루프에서 매 회 처리한다.

```python
# siap/link.py — SIAP I/O 스레드. 시리얼/소켓의 유일한 소유자.
def _io_loop(self) -> None:
    self._port.timeout = 0.05          # ★ 유한 read timeout — 무수신에도 루프가 돈다
    while not self._stop.is_set():
        # ① 수신 — timeout 이 지나면 b"" 를 돌려주고 넘어간다
        for frame in self._codec.feed(self._port.read(4096)):
            reply = self._dispatch(frame)    # F-154: 회신은 _default_reply() 가 만든다
            if reply is not None:
                self._write(reply)           # 같은 스레드에서 직접 송신
            self._match_pending(frame)       # RES_*/ACK 이면 대기자에게 전달
        # ② API 가 넣어둔 송신 요청 — 수신 여부와 무관하게 매 회 처리한다
        self._drain_request_queue()
        # ③ 응답이 오지 않은 요청의 재전송·타임아웃 (표 7-18)
        self._expire_pending()

def _dispatch(self, frame: Frame) -> Frame | None:
    """F-154 — 회신은 항상 _default_reply() 가 만든다(표준 해석은 프로토콜
    계층에만, CLAUDE.md §3.4). on_frame 이 설정돼 있으면(run.py 의
    _make_on_frame(db_path) — F-167, bind(conn) 이 아니다) 부수효과로
    추가 호출될 뿐이고 반환값은 쓰지 않는다."""
    reply = self._default_reply(frame)
    if self._on_frame is not None:
        self._on_frame(frame)                # 부수효과 전용 — DB 반영, 반환값 무시
    return reply
```

**`_dispatch()`를 먼저 부른다.** `RES_*`·`ACK`도 `frame_log`에 남아야 기능 2가 성립하므로, 매칭 때문에 기록을 건너뛰지 않는다 — `on_frame`(= `run.py::_make_on_frame(db_path)`, F-167)이 이들에 대해서도 `frame_log` 기록은 수행한다(`ingest.handle()`은 회신을 만들지 않을 뿐 모든 프레임을 기록한다, §3.1).

```python
def _match_pending(self, frame: Frame) -> None:
    """대기 중인 요청과 맞춘다 (7.2.2).

    F-046 — 매칭 조건은 세 개다: Node ID · Message Identifier · **Message Type**.
    앞의 둘만 보면 다른 요청의 지연 Response 나 우연히 번호가 같은 ACK 가
    현재 호출의 결과로 반환되고, 진짜 Response 는 미매칭으로 버려진다."""
    pend = self._pending.get((frame.header.node_id, frame.header.msg_id))
    if pend is None:
        return                                    # 지연 도착·중복 — 로그만 남기고 흘린다
    if frame.kind is not pend.expect:             # ★ 기대한 종류가 아니면 소비하지 않는다
        return                                    # 진짜 응답이 아직 올 수 있다
    del self._pending[(frame.header.node_id, frame.header.msg_id)]
    pend.result = frame
    pend.event.set()                              # link.send() 의 Event.wait() 해제

def _drain_request_queue(self) -> None:
    while True:
        try: req = self._txq.get_nowait()
        except queue.Empty: return
        self._write(req.frame)
        req.expect = expected_reply(req.frame.kind)    # contracts/frame.py (F-046)
        if req.expect is not None:                     # Request → RES_* / Notify → ACK
            req.deadline = time.monotonic() + self._profile.timeout_sec
            self._pending[(req.frame.header.node_id, req.frame.header.msg_id)] = req
        else:                                          # RES_*·ACK 송신 — 대기 없음
            req.result = None; req.event.set()

def _expire_pending(self) -> None:
    now = time.monotonic()
    for key, p in list(self._pending.items()):
        if now < p.deadline: continue
        if p.tries < self._profile.retry_count:   # 표 7-18 Retry Count
            p.tries += 1
            p.deadline = now + self._profile.timeout_sec
            self._write(p.frame)                  # 재전송 — msg_id 는 유지한다
        else:
            self._pending.pop(key, None)
            p.result = None; p.event.set()        # 타임아웃 → send() 가 None 반환
```

| 결정 | 값 | 이유 |
|---|---|---|
| read timeout | 50 ms | 무수신 시 송신 지연 상한. 9600 baud에서 프레임 1건은 최소 10 ms 이상 |
| 재전송 시 `Message Identifier` | **유지** | 새로 발번하면 노드가 중복 요청으로 처리한다 (표준 미규정 → 자체 결정) |
| 매칭 키 | `(Node ID, Message Identifier)` + **기대 Message Type** | msg_id는 16bit로 노드마다 독립 순환한다. 종류를 함께 보지 않으면 다른 요청의 응답이 소비된다 (7.2.2 / F-046) |
| 기대 종류 산출 | `contracts/frame.py` 의 `expected_reply()` | Request → 대응 `RES_*`, Notify → `ACK`. 서비스·전송 계층에 표를 복제하지 않는다 |
| 기대와 다른 프레임 | **대기 항목을 소비하지 않는다.** 로그만 남기고 흘린다 | 진짜 Response 가 아직 올 수 있다. 타임아웃은 `_expire_pending()` 이 판단한다 |
| `send()` 대기 상한 | `Timeout × (Retry Count + 1)` | 표 7-18의 두 값에서 유도. 호출자가 별도로 정하지 않는다 |

`SiapLink.send()`는 큐에 넣고 `Event.wait()` 할 뿐이다 — 계약(`Frame | None` 반환)이 그대로 지켜지고, 호출자는 스레드를 의식하지 않는다.

### 3.2 송신 (화면 → 노드)

```
[web] ──POST──> [api] ──> [fcs] ──> control_execution 기록 (승인 확인)
                                          │
                                          ├─ build.device_control(...)  → Frame
                                          └─ link.send(frame, timeout)
                                                    │
                                        [요청큐] ─> [I/O 스레드] ─> 바이트
                                                    │
                                        Response Frame ─> 반환 ─> RSC 확인
```

**순서가 중요하다.** `control_execution` 레코드를 **먼저** 기록하고, 성공한 경우에만 프레임을 송신한다. DB 제약(승인 게이트)이 송신의 선행 조건이 되어야 *"AI 출력이 직접 구동기를 제어하지 않는다"* 가 코드 경로로 보장된다.

## 4. 동시성 모델

### 4.1 결정 — 단일 프로세스 · 3 스레드

```
프로세스 1개
├─ 메인 스레드      uvicorn (FastAPI)          ← HTTP 요청 처리
├─ SIAP I/O 스레드  link.py 소유               ← 시리얼/소켓 단독 소유
└─ 모드 스레드      log replayer 또는 virtual node
                    (hardware 모드에서는 없음)
```

**왜 단일 프로세스인가** — 제약 #2. 심사자가 `python run.py --mode replay` 한 줄로 실행해야 한다. 프로세스를 나누면 기동 순서·포트 충돌·좀비 프로세스를 심사자가 감당하게 된다.

**왜 I/O 스레드를 분리하는가** — 시리얼 포트와 소켓은 **단일 소유자**를 가져야 한다. `recv()`가 블로킹하는 동안 API 스레드가 같은 포트에 쓰면 프레임이 깨진다.

### 4.2 스레드 간 통신

| 방향 | 수단 |
|---|---|
| API → I/O | `queue.Queue` 에 `(Frame, threading.Event, 결과칸)` 투입 |
| I/O → API | 위 `Event.set()` 으로 응답 반환 |
| I/O → DB | I/O 스레드가 `on_frame` 훅(= `run.py::_make_on_frame(db_path)`, F-167 — `bind(conn)` 을 직접 쓰지 않는다)으로 `ingest.handle()` 을 직접 호출 (F-154, 부수효과 전용 — 회신은 `_default_reply()` 가 따로 만든다) |
| DB → 화면 | API 스레드가 조회. 실시간은 SSE |

`SiapLink.send()`는 내부적으로 큐에 넣고 `Event.wait(timeout)` 한다. 호출자는 스레드를 의식하지 않는다 — 계약(`Frame | None` 반환)이 그대로 지켜진다.

### 4.3 왜 ingest를 별도 스레드로 빼지 않는가

9600 baud에서 최대 프레임 유입은 초당 수십 건이고, SQLite 로컬 쓰기는 1건당 1ms 미만이다. **I/O 스레드가 직접 DB에 쓰는 것이 큐를 하나 더 두는 것보다 단순하고, 순서 보장이 공짜로 얻어진다.** 유입이 늘어 병목이 되면 그때 분리한다.

### 4.4 SQLite 사용 규칙

| 항목 | 결정 | 이유 |
|---|---|---|
| 쓰기 주체 | **테이블별 단일 소유자** (§4.4-a) | 같은 행을 두 스레드가 고치지 않게 한다 |
| 저널 모드 | `PRAGMA journal_mode=WAL` | 읽기가 쓰기를 막지 않음. 쓰기는 여전히 한 번에 하나 |
| 대기 | 연결마다 `PRAGMA busy_timeout=5000` | 쓰기가 겹치면 즉시 `SQLITE_BUSY` 대신 대기 |
| 연결 | 스레드별 연결. `check_same_thread=False` 금지 | 연결 공유가 더 위험 |
| 외래키 | 연결마다 `PRAGMA foreign_keys=ON` | **SQLite 기본값이 OFF다** |
| 트랜잭션 | 짧게. 프레임 1건 = 트랜잭션 1건 | 부분 반영 방지 + 대기 시간 최소화 |
| 읽고-고치기 | `BEGIN IMMEDIATE` | 읽기 트랜잭션을 쓰기로 승격하면 교착이 난다 |

> `foreign_keys=ON`을 연결마다 켜지 않으면 `schema.sql`의 FK 제약이 **조용히 무시된다.** 스키마 검증이 전량 통과해도 런타임에서 뚫리는 지점이므로, 연결 팩토리 한 곳에서만 연결을 만들고 거기서 PRAGMA를 건다.

### 4.4-a 쓰기 소유권 — 초안의 "I/O 스레드 단독"은 성립하지 않았다 (F-053)

초안은 *"쓰기 주체는 I/O 스레드 단독, API 스레드는 읽기 전용(제어 실행 기록만 예외)"* 이라고 적었다. **그런데 API 표면을 확정하고 보니 규칙 생성과 승인도 DB 쓰기다.** 제어 실행 기록의 예외로 덮이지 않고, I/O 스레드에 위임하는 큐도 정의되어 있지 않았다. 문서대로 구현하면 규칙을 저장할 방법이 없다.

**원칙을 다시 세운다 — 소유권의 단위는 스레드가 아니라 테이블이다.**

**31개 테이블 전부가 정확히 하나의 소유자를 갖는다.** 빠진 테이블이 있으면 구현자가 문서만으로 결정할 수 없고, "단일 소유자"라는 불변식도 검증할 수 없다(F-057). `fix_log/meta_verify.py`가 이 표와 `schema.sql`의 테이블 목록을 대조한다.

**교차 지점은 `control_execution`·`alert` 2개다.** `control_execution`은 API 스레드가 INSERT하고 I/O 스레드가 나중에 응답 필드만 UPDATE하며, `alert`는 두 스레드가 서로 다른 `kind` 값만 쓴다(겹치는 `kind`가 없다 — `NODE_ERROR`·`DISCONNECT`는 I/O 스레드만, `CONTROL_TIMEOUT`·`NO_DATA`는 API 스레드만). 두 경우 모두 행 또는 컬럼의 생애가 겹치지 않고, `control_execution`은 `trg_exec_rule_immutable`이 권한 필드 변경을 막으므로 I/O 스레드가 잘못 건드리면 트리거에서 걸린다.

**왜 안전한가** — WAL에서 동시 쓰기 트랜잭션은 하나뿐이지만, 그건 *직렬화*이지 *손상*이 아니다. 위험은 두 가지이고 각각 막는다.

| 위험 | 대응 |
|---|---|
| `SQLITE_BUSY` 즉시 실패 | `busy_timeout=5000`. 이 프로젝트의 쓰기는 전부 밀리초 단위다 |
| 읽기→쓰기 승격 교착 | 읽고 고치는 트랜잭션은 `BEGIN IMMEDIATE` 로 시작한다 |
| I/O 스레드가 API 쓰기에 밀려 프레임을 놓침 | I/O 스레드의 쓰기는 항상 단일 INSERT. API 쓰기도 마찬가지로 짧다 |

**전용 쓰기 큐를 두지 않은 이유** — 모든 mutation을 I/O 스레드로 보내면 API의 실패 응답(예: 승인 게이트 위반 409)을 큐 왕복으로 되돌려야 한다. 그 계약이 §3.1-b의 요청 큐와 별개로 하나 더 생기고, 두 큐의 순서 관계라는 새 문제가 만들어진다. **9600 baud에서 초당 수십 건이 유입되는 부하에 두 개의 쓰기 스레드는 과한 문제가 아니다.**

> 이 절은 F-053으로 발견됐다. 원인은 아키텍처를 API 표면보다 먼저 확정하면서, 사람이 유발하는 쓰기를 "제어 실행 기록" 하나로만 상상한 것이다.

## 5. 전송 계층 추상화

### 5.1 모드 3종

| 모드 | 바이트 출처 | 용도 | 제출 |
|---|---|---|---|
| `hardware` | 실제 UART/RS-485/Wi-Fi | 개발 검증 · 영상 촬영 · 로그 캡처 | 코드 포함, 심사 환경 실행 불가 |
| `replay` | `logs/*.jsonl` 재생 | **심사자 기본 경로** | 필수 |
| `simulate` | 가상 노드 양방향 응답 | 등록 · 제어 왕복 시연 | 필수 |

### 5.2 구현

```python
# siap/transport.py
URLS = {
    "hardware": "/dev/ttyUSB0",
    "replay":   "socket://127.0.0.1:5555",
    "simulate": "socket://127.0.0.1:5556",
}
ser = serial.serial_for_url(URLS[mode], baudrate=9600, timeout=1)
```

pyserial의 URL 핸들러가 시리얼과 TCP를 같은 인터페이스로 덮는다. **파서 이하 코드는 모드를 모른다.**

| 규칙 | 내용 |
|---|---|
| `socat` 등 외부 도구 | **금지.** 심사자 OS 무관성 |
| replay/simulate 서버 | **같은 프로세스의 스레드**로 기동. 별도 실행 불필요 |
| 로그 캡처 | `hardware` 모드에서 `spy://` 래핑 — 별도 캡처 코드 없음 |
| 포트 점유 | 기동 시 확인, 사용 중이면 +1 씩 탐색 후 로그에 표시 |

### 5.3 캡처 형식과 변환 책임

`spy://`는 **hex dump 텍스트**를 뱉을 뿐 JSONL을 만들지 않는다. replay가 요구하는 형식으로 바꾸는 단계가 필요하다.

```
[hardware 모드]
  spy://file=logs/raw_01.txt  ──> pyserial hex dump (원본 증거)
                                        │
                              sim/capture.py 변환
                                        ▼
  logs/session_01.jsonl  {"t": <epoch>, "dir": "rx"|"tx", "hex": "..."}
```

| 파일 | 역할 | 제출 |
|---|---|---|
| `logs/raw_*.txt` | `spy://` 원본. 변환 전 증거 | 포함 (진위 근거) |
| `logs/session_*.jsonl` | replay 입력. 변환 결과 | **필수** |
| `sim/capture.py` | 변환기 | 포함 |

**캡처 → 변환 → replay 종단 테스트를 둔다.** 형식이 어긋나면 심사자 기본 경로가 멈춘다.

### 5.4 `replay` 모드의 타이밍

`t`는 **epoch 시각**이다. 첫 레코드에서 `sleep(t)`를 하면 57년을 기다린다. 첫 타임스탬프를 빼서 정규화하고 단조 시계와 비교한다.

```python
# sim/replayer.py — 게이트웨이의 RX 만 주입한다 (F-042)
rx      = [r for r in log if r["dir"] == "rx"]      # ★ 방향 필터가 먼저다
first_t = rx[0]["t"]
start   = time.monotonic()
for rec in rx:
    target = (rec["t"] - first_t) / speed
    time.sleep(max(0, target - (time.monotonic() - start)))
    sock.send(bytes.fromhex(rec["hex"]))
```

`time.time()`이 아니라 `time.monotonic()`을 쓴다 — 시스템 시계가 조정돼도 재생이 튀지 않는다. `--speed` 기본 1.0.

### 5.4-a `dir` 필터가 필수인 이유 (F-042)

`logs/session_*.jsonl`은 **게이트웨이 관점**의 캡처이므로 `dir: "rx"`(노드→GCG)와 `dir: "tx"`(GCG→노드)가 섞여 있다. 방향을 무시하고 전부 주입하면 **과거의 게이트웨이가 보낸 `RES_*`·`REQ_SET_DEVICE_CONTROL`이 현재 게이트웨이의 수신으로 들어온다.**

| 무시했을 때 생기는 일 | 영향 |
|---|---|
| `RES_SET_CONNECTION`이 RX로 들어옴 | 등록되지 않은 노드의 Response → `INVALID_NODE_ID` 위반이 조작 없이 발생 |
| 과거 `ACK`가 RX로 들어옴 | 대기 중이 아닌 msg_id 매칭 실패가 쌓인다 |
| 게이트웨이발 Request가 RX로 들어옴 | `reply_kind()`가 `None`이라 조용히 버려지되 `frame_log`는 오염된다 |

**결정**

| 항목 | 규칙 |
|---|---|
| replay 입력 | `dir == "rx"` 레코드만 소켓으로 주입한다 |
| `dir == "tx"` 레코드 | **기대 출력**으로 쓴다. 종단 테스트가 현재 게이트웨이의 송신과 대조한다 |
| 양방향 재현 | replay의 책임이 아니다. `simulate` 모드의 가상 노드(§5.5)가 담당한다 |
| 검증 | `tx` 대조 테스트를 `sim/tests/`에 둔다 — 재생 결과가 실제 실행과 같은지가 재현성의 정의다 |

### 5.5 `simulate` 모드의 가상 노드

`sim/virtual_node.py`가 노드 3종을 흉내낸다. **`siap/codec.py`를 재사용하지 않고 독립적으로 프레임을 만든다** — 같은 코덱을 쓰면 인코더 버그가 상쇄되어 드러나지 않는다.

| 동작 | 근거 |
|---|---|
| 기동 시 `REQ_SET_CONNECTION` 송신 | 0943 8.1.1 |
| `RES_SET_CONNECTION`(RSC=SUCCESS) 수신 뒤 `REQ_SET_NODE_DEVICE_PROPERTY_ALL` 1회 송신 — 노드가 자신의 디바이스 구성(DEVICE_PROPERTY×N)을 선언한다 | 0943 8.1.3.3(노드→GCG). **표준 미규정 결정(F-198, CLAUDE.md §3.5)** — `REQ_SET_CONNECTION`은 페이로드가 없어(표 8-4) 이 선언을 실을 수 없다. 언제 선언하는지는 0943이 절차를 규정하지 않아 "연결 성공 직후, 세션마다 1회"로 결정했다 |
| 주기적 `NOTI_DEVICE_VALUE` | 0943 8.2.1.2, 표 7-18 `Period` |
| `REQ_SET_DEVICE_CONTROL` 수신 → 상태 변경 → `RES_SET_DEVICE_CONTROL` | 0943 8.1.5 |
| `NOTI_KEEP_ALIVE` 주기 송신 | 0943 8.2.1.5 |
| **실행 중 노드 1개 추가 접속** | 기능 1 시연 |

**디바이스 구성 선언 — 단계 8 대응 필요 (F-198, 2026-08-12).** 위 결정(연결 성공 뒤 `REQ_SET_NODE_DEVICE_PROPERTY_ALL` 1회 선언)은 지금까지 `sim/virtual_node.py`(가상 노드)에만 구현됐다. 실물 펌웨어(`firmware/arduino_sensor_node`·`arduino_actuator_node`·`esp32_node`)는 단계 8(보드 3종 실물 통합) 착수 전까지는 미착수 상태이므로 같은 선언 절차가 아직 없다 — 단계 8에서 `node_state.c`의 `CONNECTING → RUNNING` 전이(§6.2)에 이 선언 송신·재전송을 반드시 포함해야 같은 결함(F-198)이 실물 경로에서 재발하지 않는다. `core/`(하드웨어 의존성 0, `CLAUDE.md` §1-5)에 두고 보드별 바인딩은 건드리지 않는다.

**센서값 출처 — 골든 벡터 DMI 값 재사용 (2026-08-09 사용자 확인, F-148 재확인).** 이 절은 원래 "센서값은 실측 로그의 값 분포를 재사용한다"고 정했다. 그런데 실측 로그(`project_code/logs/*.jsonl`)는 단계 8(보드 3종 실물 통합)에서만 채워진다 — 단계 4(이 절이 구현되는 시점)에는 존재하지 않는 산출물을 전제로 한 순환 의존이었다. 실측 데이터가 준비되기 전까지는 `contracts/vectors/golden.jsonl`의 `judgement=normal` DEVICE_MAIN_INFO.Value 값(사람이 손으로 만들고 코드로 검증한, 이미 감사된 프로젝트 산출물)을 재사용한다 — `random.uniform()`·`math.sin()` 같은 무작위·주기함수 생성은 여전히 금지다(CLAUDE.md §1-1). 개발_착수_지시서 §3.6(단계 4) "하지 않을 것" 항목이 `logs/`의 골든 벡터 재생을 이미 명시적으로 허용하며, 이 결정은 그 허용을 `sim/virtual_node.py`의 시뮬레이션 값 소스에도 동일한 근거로 확장한 것이다. 단계 8에서 실측 캡처가 준비되면 `_load_value_pool()`을 실측 로그 기반으로 교체한다. CLAUDE.md §3.5 결정 표에도 동일 항목을 기록했다.

## 6. 상태 머신과 오류 처리

### 6.1 노드 연결 상태 (0943 8.1.1, 5.2.2)

```
        REQ_SET_CONNECTION 수신
  IDLE ──────────────────────────> REGISTERED
                                       │
                    NOTI_KEEP_ALIVE ───┤ (타이머 갱신)
                                       │
   Keep Alive Interval 초과            │        NOTI_DISCONNECT 수신
        ┌──────────────────────────────┴──────────────────────┐
        ▼                                                      ▼
      STALE ──────────────────────────────────────────────> DISCONNECTED
                    재접속 시 REGISTERED 로 복귀
```

`Keep Alive Interval`은 `MSG_CONTROL_PROFILE`(표 7-18)에서 온다. 노드마다 다를 수 있다.

### 6.2 재전송 (0943 5.2.2, 그림 8-1 / 8-2)

```
send(frame) → 전송 → Message Receive Timeout 대기
                        │
              응답 있음 ─┴─ 응답 없음 → 재전송 (Num. of Retry 회)
                                          │
                              횟수 초과 → alert 기록 + None 반환
```

`Message Identifier`(표 7-6)로 Request↔Response를 매칭한다. 노드별로 독립 발번하며 65535 다음 0으로 순환한다.

**시간 단위 (F-033 구현 결정)** — 표 7-18은 세 시간 필드의 단위를 규정하지 않는다. 같은 표준에서 단위가 명시된 유일한 시간 필드가 표 7-15의 `Period`(sec)이므로 **전부 초(sec)로 통일**한다.

| 필드 | 단위 | 범위 | 기본값 | 비고 |
|---|---|---|---|---|
| `Message Receive Timeout` | **sec** | 1 ~ 65535 | **2** | 근거는 §6.2-a |
| `Notify Error Interval` | **sec** | 1 ~ 65535 | 30 | |
| `Keep Alive Interval` | **sec** | 1 ~ 65535 | 60 | |
| `Period` (표 7-15) | sec | 0 ~ 16383 | 60 | **표준 명시** |

C · Python · 가상 노드 · 골든 벡터가 같은 규칙을 공유한다.

### 6.2-a 타임아웃은 최대 프레임에서 유도한다 (F-064)

초안은 *"9600 baud에서 최대 프레임 51byte ≈ 53ms이므로 1초로 충분"* 이라고 적었다. **51byte는 `DEVICE_PROPERTY` 한 건을 담은 경우일 뿐 가변 개수 N의 최대가 아니다.**

`RES_SET_CONNECTION` = 헤더(12) + `RSC`(1) + `NODE_PROPERTY`(8) + `DEVICE_PROPERTY`(30)×N 이고, 표 7-13의 `Num. of Devices`가 8bit이므로 표준상 N은 255까지 간다.

| N | 프레임 크기 | 9600 baud 8N1 전송 시간 |
|---|---|---|
| 1 | 51 byte | 53 ms |
| 16 (**본 구현 상한**) | **501 byte** | **522 ms** |
| 63 | 1,911 byte | 1,991 ms |
| 255 (표준 상한) | **7,671 byte** | **7,990 ms** |

**산식** — 8N1은 바이트당 10 bit다.

```
wire_ms(bytes) = bytes × 10 × 1000 / baud
최대 프레임      = 12 + 고정부 + 30 × N
Timeout(sec)   ≥ ceil(2 × wire_ms(최대 프레임) / 1000)     ← 왕복·처리 여유 2배
```

**결정 — 노드당 디바이스 상한 N = 16.**

| 근거 | 내용 |
|---|---|
| AVR SRAM | Uno/Pro Mini는 SRAM 2KB다. `DEVICE_PROPERTY` 16건이 480 byte로, 수신·송신 버퍼와 스택을 함께 두려면 이 언저리가 현실적 상한이다 |
| 전송 시간 | 501 byte = 522 ms. `Timeout` 2초 안에 3.8배 여유 |
| 시연 규모 | 노드 3종 × 디바이스 2~5개. 상한까지 쓰지 않는다 |

**골든 벡터 `B03`이 정확히 이 프레임이다**(501 byte). 펌웨어 수신 버퍼 크기와 타임아웃의 근거가 같은 바이트열 하나로 묶인다.

> **표준이 정하지 않은 것** — 표 7-18의 `Timeout`과 `Num. of Devices`(8bit, 최대 255)의 관계에 대한 규정이 없다. 기본 프로파일을 그대로 쓰면 **정상 응답이 도착하기 전에 타임아웃·재전송이 일어난다.** `docs/standard-findings.md`에 등재했다(F-065).
>
> 배포에서 N을 늘리려면 `Timeout`을 위 산식으로 다시 잡아야 한다. `MSG_CONTROL_PROFILE`이 프로파일 필드인 것이 그래서 다행이다 — 재컴파일 없이 조정된다.

### 6.3 오류의 전파 경계

| 지점 | 처리 |
|---|---|
| 바이트 → Frame 실패 | **예외 없음.** `violations` 채운 `Frame` 반환 |
| Frame → DB 실패 | 트랜잭션 롤백 + `alert` 기록. I/O 스레드는 계속 |
| 전송 실패 (재전송 초과) | `link.send()` → `None`. 서비스 계층이 `alert` 기록 |
| API 요청 오류 | HTTP 4xx/5xx + 사유. 화면에 표시 |
| I/O 스레드 죽음 | 감시 후 재기동. 3회 실패 시 상태를 화면에 노출 |

> **I/O 스레드는 어떤 경우에도 조용히 죽지 않는다.** 죽으면 프레임이 멈추는데 화면은 마지막 상태를 계속 보여주므로, 심사자가 "동작 중"으로 오해한다. 헬스 상태를 API로 노출한다.

### 7.3 기능 3 — 기상 예보 연동 제어 규칙 (사람 승인)

```
[dms] 기상청 API 또는 fixtures/ ──> public_data_record 저장
                                          │
[mms] 예보 + 온실 현재 상태 ──> 생성형 AI ──> control_rule (approved_at=NULL)
                                          │
                                    rules.html 표시
                                          │
                                 사용자 검토 · 수정 · 승인
                                          │
                        POST /rules/{id}/approve → approved_at, approved_by
                                          │
[fcs] control_execution(origin='RULE') 기록  ← DB 트리거가 승인 확인
                                          │
                        build.device_control() → link.send()
                                          │
                                    노드 릴레이 동작
                                          │
                        RES_SET_DEVICE_CONTROL → result_rsc 갱신
```

**승인 전에는 `action_json`이 존재할 수 없고**(CHECK), **미승인 규칙으로는 `control_execution`이 생성되지 않는다**(트리거). 프레임 송신은 `control_execution` 기록 성공 이후에만 호출된다.

## 8. 기술 스택과 의존성

### 8.1 결정

| 영역 | 선택 | 근거 |
|---|---|---|
| 언어 | Python 3.11+ / C99 | 게이트웨이 · 펌웨어 |
| 웹 프레임워크 | **FastAPI + uvicorn** | 타입 힌트 기반, SSE 지원, 단일 프로세스 기동 |
| DB 접근 | **표준 라이브러리 `sqlite3` + 얇은 repository** | ORM 미사용 (§8.2) |
| 시리얼/소켓 | **pyserial** | URL 핸들러가 3모드를 하나로 덮음 (§5.2) |
| HTTP 클라이언트 | **표준 라이브러리 `urllib.request`** | 기상청 API 1개 GET. 의존성 추가 불필요 |
| 프론트엔드 | **vanilla JS + 단일 HTML** | **빌드 단계 없음.** `node_modules` 없음 |
| 실시간 | **SSE** (`text/event-stream`), 실패 시 1초 폴링 폴백 | WebSocket보다 단순, 표준 라이브러리로 충분 |

**직접 의존성은 3개다.** `fastapi`, `uvicorn`, `pyserial`.

> **전이 의존성에 플랫폼별 바이너리 휠이 있다.** `fastapi → pydantic → pydantic-core`는 Rust로 빌드되어 OS·Python ABI별로 휠이 다르다. "셋 다 순수 Python"은 직접 의존성만 센 것이며 사실이 아니다.

### 8.2 ORM을 쓰지 않는 이유

`schema.sql`이 정본이고 여기에 **트리거 37개와 CHECK 제약**이 들어 있다. ORM을 얹으면

- 스키마가 두 곳(`schema.sql`과 모델 클래스)에 생겨 어긋난다
- ORM이 제약을 우회하는 경로(bulk insert, raw update)를 열어준다
- `wheels/` 용량이 늘어난다

대신 `backend/models.py`는 **읽기 전용 dataclass**로 두고, `repository.py`가 SQL을 담당한다. 1369-P1 ER 모델의 표현은 `schema.sql`이 하고, 모델 클래스는 그 행을 담는 그릇일 뿐이다.

### 8.3 오프라인 패키징 — 플랫폼 문제

심사자 환경(OS · Python 버전)을 모르는 상태에서 오프라인 설치를 보장해야 한다. 이것이 재현성의 최대 위험 지점이다.

**대응 ① 버전 고정 + 다중 플랫폼 휠 동봉**

`requirements.txt`에 버전을 `==`로 고정하는 것은 **직접 의존성 3개뿐이다** (CLAUDE.md §4.3).
전이 의존성(`pydantic`·`starlette`·`anyio` 등)의 버전은 이 파일에 적지 않는다 — 대신
`wheels/`에 **패키지당 정확히 한 버전의 휠만** 담아 둔다. `pip download`가 그 시점의
의존성 그래프를 풀어 `wheels/`를 채우고, 이후 `--no-index --find-links wheels/` 설치는
후보가 하나뿐이라 항상 같은 버전으로 고정된다 — `wheels/` 자체가 전이 의존성의 잠금
파일 역할을 한다. F-099: 이 절이 예전에는 "requirements.txt 는 전이 의존성까지 고정한다"고
적어 CLAUDE.md §4.3·실제 구현(직접 의존성 3개만 기록)과 어긋났었다.

```bash
# requirements.txt 는 직접 의존성 3개만 == 로 고정한다. pip download 는 그 시점의
# 전이 의존성까지 풀어 wheels/ 에 내려받는다 — 그 결과물(휠 파일 집합)이 곧 잠금이다.
pip download -r requirements.txt -d wheels/ \
    --platform win_amd64      --python-version 311 --only-binary=:all:
pip download -r requirements.txt -d wheels/ \
    --platform manylinux2014_x86_64 --python-version 311 --only-binary=:all:
# macOS·다른 Python 버전은 필요 시 추가
pip install -r requirements.txt --no-index --find-links wheels/
```

**대응 ② 폴백 경로 — 의존성 없이도 최소 동작**

`pip install`이 어떤 이유로든 실패해도 심사자가 표준 준수를 확인할 수 있어야 한다.

| 경로 | 필요 의존성 | 확인 가능한 것 |
|---|---|---|
| `cd firmware/tests && make && ./test_siap_frame` | **없음** (C 컴파일러만) | 0943 표준 준수 |
| `python contracts/test_contract.py` | **없음** (표준 라이브러리) | 계약 일관성 |
| `python project_docs/db/verify.py` | **없음** (`sqlite3` 내장) | 1369-P1 무결성 제약 |
| `python run.py --mode replay` | fastapi · uvicorn · pyserial | 전체 기능 |

**앞의 셋은 표준 라이브러리만으로 동작한다.** README에 이 순서로 적어, 웹 실행이 실패해도 표준 활용성의 근거가 남게 한다.

**대응 ③ 조기 검증**

`wheels/` 검증은 D11이 아니라 **의존성을 추가하는 즉시** 한다. 최소 2개 플랫폼(Windows/Linux × Python 3.11)에서 클린 환경 설치를 확인하고, 결과를 README에 명시한다.

## 9. 진입점과 기동 순서

### 9.1 `run.py`

```bash
python run.py --mode replay              # 심사자 기본 경로
python run.py --mode simulate
python run.py --mode hardware --port /dev/ttyUSB0
python run.py --mode replay --log logs/session_01.jsonl --speed 2.0
python run.py --proto extended           # strict(기본) / extended
```

### 9.2 기동 순서

```
1. 인자 파싱
2. DB 준비 — 파일 없으면 schema.sql 실행, 시드 투입 (농장 1 · 온실 1 · 사용자 1)
3. 모드 스레드 기동 (replay 재생기 또는 virtual node) — hardware면 생략
4. SIAP I/O 스레드 기동 — transport 개통 → recv 루프 진입
5. uvicorn 기동 (메인 스레드) → http://localhost:8000
```

**2번이 매번 실행된다.** 심사자가 DB 파일을 지우거나 처음 실행해도 동작해야 한다. 시드는 고정값이며 `fixtures/seed.sql`에 둔다.

### 9.3 종료

`SIGINT` 수신 → I/O 스레드 중지 플래그 → 소켓/시리얼 close → 모드 스레드 중지 → uvicorn 종료. **좀비 스레드를 남기지 않는다** (심사자가 재실행할 때 포트 점유로 실패한다).
