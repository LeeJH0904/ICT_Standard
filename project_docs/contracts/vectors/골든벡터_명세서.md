# 골든 테스트 벡터 명세서 — 53건

> **범위**: C 구현 · Python 코덱 · 백엔드가 **같은 파일로** 검증받는 정답 집합
> **정본**: `golden_layout.py` (손으로 적은 비트 레이아웃) → `golden.jsonl` (생성물)
> **검증**: `python .../vectors/golden_verify.py` — **31/31 통과** (§6)
> **선행 문서**: `SIAP_메시지_명세서.md`(비트 레이아웃) / `Frame_구조_명세서.md`(기대 판정)

---

## 1. 이 파일이 없으면 증명할 수 없는 것

프로젝트의 핵심 주장은 *"서로 다른 MCU 3종이 동일 표준 프로토콜로 혼용 동작한다"* 이다. 이걸 말이 아니라 **증거**로 만들려면, C 펌웨어와 Python 게이트웨이가 **같은 바이트열을 같은 뜻으로 해석한다**는 것을 보여야 한다.

골든 벡터가 그 증거다. 세 곳이 같은 파일을 읽는다.

```
firmware/tests/test_golden.c   ─┐
siap/tests/test_codec.py       ─┼─→  contracts/vectors/golden.jsonl
backend/tests/test_ingest.py   ─┘
```

**세 구현이 각자 인코딩·디코딩해 이 파일과 일치해야 한다.** 어느 하나가 비트 하나를 잘못 놓으면 그 자리에서 드러난다. 표준 원문에는 실제 바이트열 예시가 단 하나도 없으므로(그림은 필드 배치 다이어그램일 뿐), 이 53건이 **표준 준수의 유일한 바이트 수준 근거**가 된다.

## 2. "손으로 만든다"를 어떻게 지켰나 (CLAUDE.md §6.2)

규약은 이렇게 적혀 있다.

> 손으로 만들고 코드로 검증한다. **코드로 생성한 것을 정답으로 삼으면 자기 검증 순환이 된다.**

53건 × 최대 51바이트를 hex로 직접 타이핑하는 것은 "손으로"의 문자적 해석이지만, 오히려 오타가 늘고 **틀렸을 때 어느 필드가 틀렸는지 추적할 근거가 남지 않는다.** 그래서 이렇게 했다.

### 2.1 손으로 적는 것 — 필드 레이아웃

```python
V("N26", "REQ_SET_DEVICE_CONTROL", "G->N", "8.1.5", "관수밸브 ON",
  H(0x000C, 26, 7),                       # 헤더: 표 7-5 ~ 7-8
  dmi(5, 1, 0x85, 1, 1),                  # DEVICE_MAIN_INFO: 표 7-14
  n=1)
```

`dmi()`는 표 7-14를 그대로 옮긴 **(필드명, 비트폭, 값)의 목록**이다.

```python
def dmi(device_id, dtype, subtype, vtype, value):
    """56 bit. 표 7-14."""
    return [F("Device ID", 8, device_id), F("Type", 1, dtype), F("Subtype", 8, subtype),
            F("Value Type", 2, vtype), F("Reserved", 5, 0), F("Value", 32, value)]
```

심사자는 이 여섯 줄을 표준의 표 7-14와 **한 줄씩 눈으로 대조**할 수 있다. hex 문자열로는 불가능한 일이다.

### 2.2 코드가 하는 일 — 비트 잇기뿐

```python
def pack(fields):
    """(비트폭, 값) 을 MSB 우선으로 잇는다. 구조 지식 0."""
```

`pack()`은 메시지가 무엇인지, 어떤 구조체가 있는지 **전혀 모른다.** 사람이 종이에 2진수를 이어 적는 것과 같은 일을 할 뿐이다. `siap/spec_verify.py`의 인코더는 **재사용하지 않았다.**

### 2.3 그래서 무엇이 검증되는가

| 대조 축 | 정답의 출처 | 무엇을 잡는가 |
|---|---|---|
| **독립 헤더 리더** | `golden_verify.py`가 표 7-5~7-8 오프셋을 **다시** 타이핑 | 쓰기/읽기 중 한쪽의 오프셋 오독 |
| **`contracts/frame.py`** | 벡터보다 먼저 존재한 계약. `resolve_kind` · `element_count` · RSC/NEC/Subtype 열거 | 기대 판정을 손으로 잘못 적은 것 |
| **`siap/spec_examples.json`** | `spec_verify.py`의 **독립 인코더**가 만든 예시 9건 | 명세서를 두 번 타이핑했을 때의 해석 차이 |
| **`CLAUDE.md` §6.3** | 규약이 정한 위반 8종 표 | 위반 케이스 누락·변질 |

**세 번째가 가장 중요하다.** 같은 명세서를 두 사람(두 번의 타이핑)이 읽어 같은 바이트가 나오면, 명세서 자체를 오독했을 확률이 크게 떨어진다. 9건이 페이로드 바이트 단위로 일치했다.

## 3. 구성 53건

| 분류 | 건수 | ID |
|---|---|---|
| 정상 메시지 | 34 | `N01` ~ `N34` |
| 경계값 | 11 | `B01` ~ `B11` |
| 위반 (기능 2 주입 시나리오) | 8 | `X01` ~ `X08` |

### 3.1 정상 34종 — 메시지 종류를 1건씩 전부

`MsgKind` 34종을 정확히 한 번씩 덮는다. 검증기가 집합 일치를 확인한다.

| 묶음 | 건수 | 페이로드 |
|---|---|---|
| 헤더만 | 10 | `REQ_SET_CONNECTION` · `REQ_SET_DEVICE_INIT_ALL` · `REQ_GET_NODE_PROPERTY` · `REQ_GET_NODE_DEVICE_PROPERTY_ALL` · `REQ_GET_MSG_FLOW_CONTROL_PROFILE` · `REQ_SET_REBOOT` · `NOTI_DISCONNECT` · `NOTI_REBOOT` · `NOTI_KEEP_ALIVE` · `ACK` |
| RSC 1 byte | 8 | `RES_SET_*` 6종 + `RES_SET_DEVICE_CONTROL` + `RES_SET_REBOOT` |
| 구조체 포함 | 16 | `DEVICE_ID×N` 3종 / `NODE_PROPERTY` / `DEVICE_PROPERTY×N` / `MSG_CONTROL_PROFILE` / `DEVICE_MAIN_INFO×N` / `RSC+…` 조합 등 |

**`NOTI_ERROR`(N33)와 `NOTI_DEVICE_VALUE`(N34)가 같은 코드 `0x0800`을 쓴다.** 표준 원문의 결함(F-001)이며, 페이로드 길이 1 byte(NEC) vs 7의 배수(DEVICE_MAIN_INFO×N)로 갈린다. 두 벡터가 나란히 있으므로 **구현이 이 판별을 실제로 하는지**가 바로 드러난다.

### 3.2 경계값 11종 — 8개 축

| 축 | 벡터 | 무엇이 걸리는가 |
|---|---|---|
| N=0 허용 | `B01` | **디바이스가 0대인 노드**의 연결 응답. 고정부(RSC+NP)가 있으면 가변부 0개는 정상이고, `Num. of Devices`도 0이라 자기모순이 없다 |
| N=0 거부 | `B02` | 가변부만 있는 메시지의 빈 페이로드. `resolve_kind`는 코드를 해석하지만 `element_count`가 `None`을 돌려 `INVALID_FORMAT`이 된다 |
| **지원 상한 최대 프레임** | `B03` | `RES_SET_CONNECTION` + `DEVICE_PROPERTY×16` = **501 byte**. 펌웨어 수신 버퍼 크기와 타임아웃 근거가 이 한 프레임으로 묶인다 (F-064). `Payload Length`가 255를 넘어 16bit 필드가 실제로 쓰인다 |
| msg_id 랩어라운드 | `B04` `B05` | `0xFFFF` 직전과 `0x0000` 직후 |
| 식별자 20bit 최댓값 | `B06` | GCG/Node ID `0xFFFFF`. **9번째 바이트를 반씩 나눠 쓰는 자리** |
| Value 타입별 경계 | `B07` `B08` `B09` | INT `-2^31`(`80000000`) / UINT `2^32-1`(`FFFFFFFF`) / FLOAT 최댓값(`7F7FFFFF`) |
| 필드 폭 최댓값 | `B10` | `Period` 14bit 최댓값 16383 + `Transfer Mode` 2bit — 둘이 한 바이트 경계를 넘는다 |
| **N 상한 초과 (F-120)** | `B11` | `REQ_SET_DEVICE_CONTROL` N=17. `Num. of Devices`(표 7-13, 8bit)는 표준상 N=255까지 열려 있지만, 노드당 디바이스 상한 N=16(CLAUDE.md §3.5)을 넘으면 `element_count`가 `None`을 돌려 `INVALID_FORMAT`이 된다 |

> `B07`과 `B08`은 **같은 비트열이 아니지만 같은 함정을 노린다** — `FFFFFFFF`를 INT로 읽으면 `-1`, UINT로 읽으면 `4294967295`다. 타입을 무시한 구현은 여기서 갈린다.

### 3.3 위반 8종 — 규약 §6.3 표 그대로

| ID | 주입 | 기대 코드 | clause |
|---|---|---|---|
| `X01` | `Version` = 0x99 | `INVALID_VERSION` (0x01) | 7.3.1 |
| `X02` | 미등록 `Node ID` = 0xABCDE | `INVALID_NODE_ID` (0x03) | 7.3.1 |
| `X03` | `Payload Length` 표기 24, 실제 1 | `INVALID_FORMAT` (0x09) | 7.3.1 |
| `X04` | `Message Type` = 0x000E (미정의) | `INVALID_FORMAT` (0x09) | 표 7-2 |
| `X05` | `Transmission Type` = 0x03 | `INVALID_TRANSMISSION_TYPE` (0x08) | 표 7-6 |
| `X06` | `Value Type` = 0x03 (RESERVED) | `INVALID_DATA_TYPE` (0x06) | 표 7-14 |
| `X07` | 미등록 `Subtype` = 0x7F | `INVALID_DATA_SUBTYPE` (0x07) | 표 7-14 |
| `X08` | `NEC` = 0x07 수신 | `ERROR_BATTERY_LOW` (0x07) — **알림이지 위반이 아니다** | 7.3.2 |

**검증기가 이 표를 `CLAUDE.md` §6.3에서 읽어 벡터와 대조한다.** 규약이 바뀌면 벡터도 바뀌어야 하고, 한쪽만 바뀌면 FAIL이다.

> **`X08`은 성격이 다르다 — 그리고 이 구분이 동작을 바꾼다 (F-060).** 앞의 7건은 프레임 자체가 표준을 어긴 것이고, `X08`은 **프레임은 정상인데 노드가 오류를 알리는 것**이다(0943 8.2.1.1 — `NOTI_ERROR`는 정상 Notify이고 GCG는 ACK를 보낸다).
>
> 초안은 `X08`의 기대를 `violations`에 넣었는데, 그러면 `Frame.is_valid`가 false가 되고 `ingest.handle()`이 격리 후 즉시 반환한다 — **`alert` 저장도 ACK 회신도 실행되지 않는다.** 노드는 ACK를 못 받아 `Notify Error Interval`마다 재전송한다.
>
> 그래서 벡터에 `judgement` 필드를 뒀다.

| `judgement` | 건수 | 의미 | 기대 동작 |
|---|---|---|---|
| `violation` | 7 | 프레임이 표준을 어겼다 | 격리 + 오류 RSC 회신(가능한 경우) |
| `alert` | 1 | 프레임은 정상, 노드가 오류를 알린다 | `alert` 저장 + **ACK 회신** |
| `normal` | 44 | 정상·경계 | 종류별 처리 |

**`violations`에는 `INVALID_*`만 들어간다.** `ERROR_*`(NEC)는 `nec_alert` 필드로 분리했고, 검증기가 이 규칙을 강제한다.

## 4. 벡터 1건의 구조

```json
{"id": "N26", "msg": "REQ_SET_DEVICE_CONTROL", "kind": "REQ_SET_DEVICE_CONTROL",
 "dir": "G->N", "category": "정상", "clause": "8.1.5", "note": "관수밸브 ON",
 "hex": "120030001A0007000010000305C2A000000001", "len": 19,
 "header": {"Version": 18, "Message Type": 12, "Transmission Type": 0,
            "Message Identifier": 26, "Payload Length": 7,
            "GCG ID": 1, "Node ID": 3},
 "n": 1, "violations": [], "axis": null, "judgement": "normal",
 "inject": null, "nec_alert": null,
 "fields": [{"name": "Version", "bits": 8, "value": 18}, ...]}
```

| 필드 | 용도 |
|---|---|
| `hex` | 세 구현이 인코딩 결과를 대조할 바이트열 |
| `header` | 디코더가 헤더 7필드를 옳게 잘랐는지 |
| `kind` | `0x0800` 판별 결과 포함. `null`이면 판별 불가가 정답 |
| `n` | 가변 요소 개수. `null`이면 산출 불가 = 형식 오류 |
| `violations` | `INVALID_*` 판정만. 기능 2 화면의 붉은 격리 영역 출력의 정답 |
| `judgement` | `violation` / `alert` / `normal` — **격리 대상인지 아닌지** (F-060) |
| `inject` | 위반 벡터의 주입 라벨. 검증기가 기대 코드와 1:1 대조 (F-062) |
| `nec_alert` | `ERROR_*`(NEC) 알림 기대. `violations`와 섞지 않는다 |
| `fields` | **필드 단위 분해.** 틀렸을 때 어느 필드에서 어긋났는지 바로 나온다 |

`fields`가 있어서 C 테스트가 *"19바이트 중 13번째가 다르다"*가 아니라 *"`Subtype`이 0x85가 아니라 0x0A로 나왔다"*라고 말할 수 있다.

## 5. `golden_ext.jsonl` — 개정 제안의 바이트 근거 5건

`strict` 모드가 표준 원문 그대로이므로 53건은 전부 `strict`다. 표준 결함 F-001·F-002에 대한 **개정 제안안**(`extended`)은 별도 파일에 최소 벡터만 둔다.

| ID | 메시지 | strict | extended |
|---|---|---|---|
| `E01` | `NOTI_ERROR` | 0x0800 | 0x0800 (유지) |
| `E02` | `NOTI_DEVICE_VALUE` | 0x0800 | **0x0801** |
| `E03` | `NOTI_DISCONNECT` | 0x0801 | **0x0802** |
| `E04` | `NOTI_REBOOT` | 0x0802 | **0x0803** |
| `E05` | `NOTI_KEEP_ALIVE` | 0x0803 | **0x0804** |

`E05`의 0x0804는 표준의 RESERVED 시작이 0x0805인 것과 정확히 맞물린다(F-002 — 원문은 0x0804가 비어 있다). **제안안이 표준의 예약 공간을 침범하지 않는다는 것이 바이트로 확인된다.**

> 두 파일을 나눈 이유: *"표준을 이렇게 구현했다"* 와 *"표준을 이렇게 고치자"* 가 한 파일에 섞이면, 심사자가 어느 쪽이 준수 근거인지 구분할 수 없다.

### 6.1 8차 검증에서 걸린 것 (F-060 ~ F-064)

골든 벡터 초판에 대한 첫 독립 검증에서 5건이 나왔고 **전부 타당**했다.

| 검출 | 성격 |
|---|---|
| 정상 NEC 알림을 `violations`에 넣어 격리 대상이 됨 | **동작이 바뀌는 결함.** `alert` 저장과 ACK가 사라진다 → `judgement` 분리 |
| extended 벡터가 양방향 알림을 `N->G`로 축소 | 생성 함수가 방향을 하드코딩 → strict와 대조하는 검사 추가 |
| 주입별 기대가 뒤바뀌어도 통과 | 검증기가 집합만 비교 → **주입 라벨 1:1 대조 + 바이트 재판정** |
| 생성기가 검증 중 산출물을 덮어써 드리프트를 마스킹 | `--check` 모드 도입. `spec_verify.py`도 같은 결함이라 함께 수정 |
| 최대 프레임을 51byte로 가정한 타임아웃 근거 | 실제 상한은 7,671byte(7.99초) → 지원 상한 N=16 선언 + 표준결함 F-065 등재 |

### 6.1-a 9차 검증 (F-066 ~ F-068)

| 검출 | 성격 |
|---|---|
| `Num. of Devices`와 `DEVICE_PROPERTY` 개수 불일치 | **지적은 `B03` 하나였는데 실제로는 5건**이었다. `NP_3DEV` 상수를 재사용한 것이 원인 → `NP(ndev)` 헬퍼 + 양쪽 불변식 |
| SIAP 명세서에 폐기된 51byte 근거 잔존 | F-064를 아키텍처만 보고 고쳤다. 같은 문서 §6-5c와도 모순이었다 |
| 재생성한 `spec_examples.json` 커밋 누락 | 코드 결함이 아니라 커밋 누락. **F-063의 `--check`가 의도대로 드러냈다** |

**`F-068` 수정을 교차 검증이 잡았다.** 골든만 고치고 `spec_verify.py`를 두자 `N27`과 `RES_SET_CONNECTION_1dev`의 페이로드 바이트가 어긋나 즉시 FAIL했다 — §2.3의 "두 번 타이핑한 것을 대조한다"가 말이 아니라 실제로 작동한다는 증거다.

세 번째와 네 번째는 **검증기 자신의 결함**이다. 골든 벡터는 세 구현의 정답이므로, 검증기가 느슨하면 **틀린 정답이 세 구현에 동시에 전파된다.** 다섯 건 전부 결함 주입으로 검출을 재확인했다.

### 6.2 작성 중 걸린 것 (초판)

| 검출 | 성격 |
|---|---|
| `B02`의 기대 `kind`를 `null`로 적었는데 계약은 `REQ_SET_DEVICE_CONTROL`을 돌려줌 | **내 기대가 틀렸다.** `resolve_kind`는 코드만 해석하고, N=0 거부는 `element_count`의 몫이다. 두 함수의 책임 분담을 벡터가 명확히 했다 |
| `CLAUDE.md`를 고정 상대경로로 찾아 로컬 배치에서 실패 | 검증기 결함 — `HERE`에서 위로 올라가며 찾도록 수정 |
| 경계 축을 `note` 첫 단어로 추정 | 약한 휴리스틱 — `axis` 필드를 명시하도록 벡터 구조를 바꿨다 |

첫 번째가 골든 벡터를 만드는 진짜 이유다. **"어느 함수가 무엇을 판정하는가"를 문서로 읽을 때는 안 보이던 것이 벡터 한 건에서 드러났다.**

### 7.1 생성기는 검증 중에 파일을 쓰지 않는다 (F-063)

`golden_layout.py`를 그냥 실행하면 JSONL 두 개를 **덮어쓴다.** 검증 파이프라인이 이걸 그대로 돌리면, 생성물이 변질돼 있어도 검증 도중에 복구되어 **그 사실이 사라진다.** 실제로 메타 검증이 그렇게 34/34를 출력하고 있었다.

```bash
python golden_layout.py            # 생성 (개발 중)
python golden_layout.py --check    # 대조만. 아무것도 쓰지 않는다 (검증 파이프라인)
```

`meta_verify.py`는 생성기를 `--check`로만 실행한다. `siap/spec_verify.py`도 `spec_examples.json`에 같은 문제가 있어 함께 고쳤다.
