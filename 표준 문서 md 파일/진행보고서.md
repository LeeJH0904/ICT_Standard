## 0. 주제

### 무엇을 만드는가

**표준 프로토콜 기반 개방형 스마트온실 노드 — 제조사 종속 없는 상호운용성 검증 플랫폼**

상용 스마트팜은 제조사별 독자 프로토콜에 묶여 있어, 센서 하나를 교체하려 해도 같은 벤더 제품만 써야 한다. 이 종속 비용 때문에 학교 텃밭·복지관 원예 같은 소규모 공공 시설은 진입 자체가 어렵다. TTA는 이를 풀기 위해 통신 프로토콜 표준을 제정했지만, **그 표준이 실제 저가 하드웨어에서 동작하는지 검증한 공개 구현체가 없다.**

우리는 이 표준을 서로 다른 MCU 3종에 직접 구현해 각기 다른 벤더 노드처럼 취급하고, 하나의 게이트웨이 위에서 혼용 동작시킨다.

### 핵심 포지셔닝

> **"스마트팜 앱"이 아니라 "TTA 표준의 참조 구현이자 상호운용성 검증 도구"다.**

스마트팜은 공모전 단골 주제이므로 "작물을 잘 키우는 시스템"으로 제시하면 참신성에서 감점된다. 심사자가 TTA 표준 관계자임을 고려하면 **"당신들이 만든 표준을 실제로 구현해서 이렇게 동작함을 증명했다"** 가 훨씬 강한 소구점이다.

### 심사자 재현 문제와 해법

평가자에게는 라즈베리파이도 MCU도 없다. 그렇다고 센서값을 난수로 대체하면 공고문의 "명백한 허위" 조항에 걸리고 표준 활용성의 근거 자체가 소멸한다.

**해법: 교체 대상을 데이터가 아니라 전송 계층 한 곳으로만 제한한다.**

실물 촬영·검증 시 원시 프레임을 로그로 남겨두고, 심사자 PC에서는 그 로그를 TCP 소켓으로 재생(`replay`)하거나 가상 노드가 응답까지 수행(`simulate`)하게 한다. 바이트가 UART에서 오는지 소켓에서 오는지만 달라질 뿐, **표준 프레임 파서 이하 로직은 심사자 PC에서 그대로 실행된다.** 여기에 더해 펌웨어의 표준 구현부를 하드웨어 의존성 0인 순수 C 코어로 분리해, `make && ./test_siap_frame` 한 줄로 아두이노 없이 표준 준수를 확인할 수 있게 한다.

## 2. DB 스키마 설계

`project_docs/db/` — 설계서 / `schema.sql` / `verify.py`

### 무엇을 했나

TTAK.KO-10.1369-Part1의 **ER 다이어그램을 직역**해 SQLite 스키마를 만들었다. 이 표준은 본문이 "~해야 한다" 식 서술형이라 처음엔 구현하기 어려워 보였지만, 논리적 모델 그림에 **엔티티·속성명·기본키·외래키·카디널리티가 전부 표기**되어 있어 그대로 테이블로 옮길 수 있었다.

### 구성 — 총 31개 테이블

| 구분 | 개수 | 내용 |
|---|---|---|
| 설정형 데이터 | 5 | 농장·온실·장치·장치설치·사용자 정보 |

| 프레임 로그 (기능 2) | 2 | 프레임 로그 / 표준 위반 내역 |

### 설계 판단 셋

**① 일반화 구조를 대상별로 다르게 처리했다.** 장치상태 6종은 속성이 실제로 다르므로(창개폐기=개폐정도, 관수펌프=압력+분사도) 서브타입 테이블로 분리했고, 환경상태 9종은 8종의 속성 구조가 완전히 동일해 판별자 컬럼 하나로 통합했다.

**② 두 표준을 잇는 지점을 한 테이블로 제한했다.** 장치설치정보 테이블에만 프로토콜 식별자(노드 ID·디바이스 ID·Subtype) 컬럼을 두고 접두사로 격리했다. 특히 **단위·유효범위 컬럼이 중요**한데, 프로토콜 프레임은 값만 싣고 단위를 싣지 않기 때문이다. 이 간극을 데이터 계층이 메우는 구조가 곧 두 표준을 조합한 실질적 이유다.

**③ 사람 승인 게이트를 DB 제약으로 만들었다.**

미승인 규칙은 실행 가능한 명령을 가질 수 없고(CHECK), 모든 제어 실행에는 승인된 규칙 또는 사용자 직접 지시라는 **권한 출처**가 있어야 한다(CHECK + 트리거). 애플리케이션 코드 버그로도 우회되지 않으므로, 2차 평가의 "사람 검토 지점" 항목에 이보다 강한 답변은 없다.

**④ 카디널리티는 개념적 모델에서 온다.** 논리적 모델(7.2)은 "쌍 유일성"만 규정하고, 실제 1:N 조건은 개념적 모델(7.1)에 있다. 이걸 놓쳐 8건이 미강제로 남아 있었고 GPT 검증에서 발견됐다(§5).

### 검증

DDL 실행 성공(테이블 31 / 트리거 37 / 인덱스 8) 후, **표준에서 유래한 제약이 실제로 동작하는지** 테스트해 전량 통과했다(이 단계 시점 76종, 이후 검증 라운드를 거쳐 **현재 98종**). 식별자·시간 불변, 관계 유일성, 1:N 카디널리티, 참조 무결성, 측정값 범위, 프로토콜 식별자 비트 폭, 승인 게이트가 모두 포함된다. 1369-Part1에는 예시 데이터가 없으므로 이 제약 테스트가 서버측 표준 준수의 유일한 증거가 된다.

> 이 검증 스크립트가 그대로 `backend/tests/test_schema_conformance.py`의 원형이 된다. 테스트 함수명에 조항 번호를 넣어 심사자가 목록만 봐도 준수 항목이 보이게 할 예정이다.

## 3. SIAP 메시지 명세

`project_docs/siap/` — 명세서 / `spec_verify.py` / `spec_examples.json`

### 무엇을 했나

TTAK.KO-10.0943이 정의하는 프로토콜(SIAP)의 **메시지 34종 전량을 바이트 단위로 명세화**했다. 이 문서가 프레임 코덱 구현의 직접 입력이며, 이것 없이는 코드를 한 줄도 쓸 수 없다.

표준 8장은 메시지별 포맷을 그림 61장으로 제시하는데, 본문에 "페이로드에 ~을 포함하여 전송된다" 형태로 24개 메시지의 구성이 서술되어 있었다. 서술이 없는 10개만 이미지로 직접 판독해 전체를 복원했다. **원문 PDF는 열지 않았다.**

| 헤더 | 96 bit / 12 byte 고정. 버전·메시지타입·전송타입·메시지ID·페이로드길이·제어기ID·노드ID |
| 페이로드 구조체 | 5종 (노드속성 8B / 디바이스 주속성 7B / 디바이스 속성 30B / 메시지 제어 프로파일 7B / 식별자 그룹 1B) |
| 메시지 | Request 14 + Response 14 + Notify 5 + ACK = **34종**, 각각 방향·페이로드 구성·크기 |
| 상태 코드 | 응답 상태코드 10종 + 알림 오류코드 10종 |
| Subtype 레지스트리 | 센서 10종 + 액추에이터 6종 |

### 새로 확정한 것 둘

**① 가변 요소 개수(N) 산출 규칙.** 표준이 N을 전달하는 필드를 정의하지 않아 페이로드 길이 역산이 유일한 방법이다. 메시지별 공식을 표로 정리했고, 나머지가 0이 아니면 형식 오류로 판정한다. 이것이 기능 2의 위반 판정 근거 하나가 된다.

**② 코드 충돌이 깨끗하게 해소된다.** 두 알림 메시지가 같은 코드를 쓰지만, 한쪽 페이로드는 1바이트이고 다른 쪽은 7의 배수라 길이 집합이 겹치지 않는다. **표준 내부 정보만으로 표준의 결함을 우회할 수 있음**을 확인한 셈이라, 기획서에서 "발견했다"에 그치지 않고 "이렇게 해소했다"까지 갈 수 있다.

### 표준에 없는 예시 프레임

표준 원문에는 실제 바이트열 예시가 없다(그림은 필드 배치 다이어그램일 뿐). 본 명세에서 유도해 **예시 프레임 9건을 생성하고 왕복 검증**했다. 프레임 해부 예시도 함께 만들어, 골든 테스트 벡터의 시드이자 발표 자료로 쓸 수 있게 했다.

### 검증

구조체 크기 8종이 표준 명시값과 일치, 34종 코드가 코드공간 및 블록 경계 내, **Request 코드 + 0x0400 = Response 코드가 14쌍 전량 성립**, 예시 프레임 9건 왕복 검증 — 전량 통과.

## 4. Frame 구조 (모듈 경계 계약)

`project_docs/contracts/` — 명세서 / `frame.py` / `siap_iface.py` / `test_contract.py`

### 무엇을 했나

프로토콜 계층과 서비스 계층 사이에 오가는 **유일한 타입**을 정의했다. 이 경계가 확정되면 두 계층이 서로의 내부를 몰라도 되고, Claude Code가 컨텍스트를 나눠 작업해도 일관성이 유지된다.

```
 [펌웨어] → [바이트] → [디코더] ──╂ Frame ╂──→ [DB] → [API] → [화면]
 [펌웨어] ← [바이트] ← [인코더] ←─╂ Frame ╂←── [제어 명령]
```

### 경계 원칙 넷

| 원칙 | 내용 |
|---|---|
| 단일 통행 타입 | 계층 간에 오가는 것은 `Frame` 하나뿐 |
| 표준 해석은 한 곳에서만 | 프로토콜 조항 해석은 전부 하위 계층. 상위 계층은 판정 결과를 렌더링만 |
| 예외를 던지지 않는다 | 파싱 실패해도 위반 내역이 채워진 `Frame`을 반환. 깨진 프레임이 기능 2의 표시 대상 |
| 불변 | 모든 타입이 `frozen`. 하위가 만든 값을 상위가 수정 불가 |

### 핵심 설계 결정 — 논리 종류와 전송 코드의 분리

표준의 코드 중복(알림 2종이 같은 코드)을 Python 열거형으로 그대로 옮기면 **뒤 멤버가 앞 멤버의 별칭이 되어 두 메시지의 구분이 언어 차원에서 소실**된다.

그래서 **논리적 메시지 종류**(34종, 항상 고유)와 **전송 코드**(모드별 매핑 테이블)를 분리했다.

| 모드 | 내용 | 고유 코드 수 |
|---|---|---|
| `strict` | 표준 원문 그대로 | 33 (중복 1건) |
| `extended` | 개정 제안안 — 코드 재배치로 중복 해소 | 34 |

`Frame`은 전송된 원본 코드와 해석된 논리 종류를 **둘 다** 보관한다. 검증 뷰가 원본 코드를 그대로 보여줄 수 있어야 하기 때문이다. 이 설계 자체가 표준 개정 제안의 근거 자료가 된다.

### 표준 외 확장 필드 셋

| 필드 | 목적 |
|---|---|
| `raw` | 원본 바이트 보존 — 검증 뷰가 hex를 다시 만들 필요 없음 |
| `violations` | 위반 판정 결과. **조항 번호 문자열을 담아** 화면이 `INVALID_FORMAT (0x09) — 7.3.1절`을 그대로 출력 |
| `t` | 수신 시각 — 리플레이 로그 재생 시 타임라인 복원 |

### 검증 — 53/53 통과

완전성(34종 전량 정의), 코드공간, Request↔Response 대응, 코드 중복 검출 및 해소, 코드 판별 로직, N 산출 18케이스, Subtype 구성, 구조체 상수, `Frame` 불변성, 전송 원본값 보존, 그리고 **SIAP 명세서의 예시 프레임 9건과의 교차 검증**까지 포함한다.

> **테스트가 설계 구멍 하나를 잡아냈다.** 가변부만 있는 메시지에서 N=0을 허용하면 페이로드가 비어 "페이로드 없음" 메시지와 구별되지 않는다. 이 경우를 거부하도록 규칙을 보강했고, 근거를 코드 주석에 남겼다.

## 5. 개발 규약 · 검증 체계

`ROLES.md` · `CLAUDE.md` · `GPT.md` · `fix_log/`

### 무엇을 했나

개발 방식이 2인 분업에서 **Claude Code 활용**으로 바뀌면서, 컨텍스트가 세션마다 끊겨도 일관성이 유지되도록 규약을 문서로 고정했다. 여기에 **GPT를 독립 검증자로 붙이는 체계**를 함께 만들었다.

| 문서 | 역할 |
|---|---|
| `ROLES.md` | AI 제품명과 무관한 작업자·검증자 역할 선택 및 권한 분리 정본 |
| `CLAUDE.md` | 작업자가 읽는 개발 규약 — 기존 조항 참조 호환을 위해 파일명 유지 |
| `GPT.md` | 검증자 역할 지시서 — 기존 조항 참조 호환을 위해 파일명 유지 |
| `fix_log/` | 발견 사항 기록 — 인덱스 + 개별 건 + 규약 |

### 설계에서 중요했던 것

**검증 가능 범위를 제품명이 아니라 현재 환경의 실제 능력으로 판단하게 했다.** 표준 원문의 상당 부분(0943 그림 61장, 1369-P1 그림 4장)이 이미지이므로 이미지 해석 기능과 원문 접근이 모두 있을 때만 판정하고, 아니면 `검증 불가`로 남긴다.

**검증자가 작업자의 문서를 전제로 삼지 않도록 했다.** 설계 명세서는 검증 대상이지 근거가 아니며, 표준 원문만이 정본이다. 이 원칙이 없으면 검증자가 작업자의 오류를 그대로 물려받는다.

**권한을 나눴다.** 검증자는 발견을 `신규` 상태로만 추가하고, 상태 전이(확인·수정완료·기각)는 작업자만 한다. 반대로 작업자는 항목을 삭제하지 않고 상태만 갱신한다 — 기록이 남아야 같은 지적이 반복되지 않는다.

**분류가 처리 방식을 가른다.** `요건위반`(최우선 수정) / `코드버그`(수정+회귀 테스트) / `문서불일치`(표준으로 판정 후 수정) / `표준결함`(고칠 수 없음, 기획서 자산). 이 넷을 섞으면 "고쳐야 할 것"과 "발견 성과"가 뒤엉킨다.

### 1차 검증 결과

GPT가 첫 검증에서 **6건**을 보고했고, 재현 검증 결과 **전부 타당**했다. 기각 0건.

| 발견 | 성격 |
|---|---|
| 검증 스크립트의 인코딩·경로 미지정 | Windows 기본 환경에서 재현 실패 |
| `Header`가 표준 미정의값을 담을 수 없음 | 계약 설계의 일관성 결함 |
| **1:N 관계의 카디널리티 미강제 8건** | 개념적 모델(7.1)을 안 읽고 논리적 모델(7.2)만으로 설계한 것이 원인 |
| 불변성 제약 11건 누락 | 검증 규모가 완전성을 오인하게 함 |
| 승인 게이트의 보장 범위 과장 서술 | 실행 테이블 우회 가능 |
| 표준 미규정 필드를 근거 없이 고정 | 구현 결정이 문서화되지 않음 |

전부 수정하고 회귀 테스트를 추가해, **DB 제약 테스트 32 → 56종**, **계약 테스트 29 → 36종**으로 늘었다.

> 가장 뼈아픈 것은 카디널리티다. 7.2는 "쌍 유일성"만 규정하고 실제 1:N 조건은 7.1 개념적 모델에 있는데, 7.2만 읽고 구현하면 8건 전부가 미강제로 남는다. **독립 검증자를 붙인 효과가 첫 회에 바로 나왔다.**

부수 효과로 제어 실행 모델이 좋아졌다. 우회 경로를 막으면서 `origin`(RULE/MANUAL)을 도입했는데, 이로써 0937 부속서 A의 수동·원격제어 시나리오까지 포괄하게 됐다.

### 2차 검증 결과

아키텍처 설계서를 포함해 다시 돌린 결과 **11건**이 보고됐다. 10건 타당, 1건은 부분 기각(사실관계 오류 + 타당한 지적이 섞여 있었다).

| 발견 | 성격 |
|---|---|
| **수신 요청·알림에 대한 회신 경로 부재** | 문서대로 구현하면 기능 1이 동작하지 않음 |
| 로그 캡처 형식이 재생 입력과 다름 + 시각 계산 오류 | 심사자 기본 경로가 멈춤 |
| 전이 의존성의 플랫폼별 바이너리 휠 누락 | 오프라인 설치 실패 위험 |
| 승인된 명령과 실제 실행 명령이 결속되지 않음 | 승인 게이트가 내용 수준에서 미성립 |
| 표준 커버리지 공백 3건 | 본문 요구를 그림 기준으로 위반 |
| 검증기 자체의 오판정 구조 | 테스트 결함이 통과로 위장 가능 |
| 그 외 5건 | 경로·import·중복 인자·원칙 서술·단위 미결정 |

**가장 심각한 것은 회신 경로였다.** 0943은 양방향 모델이라 노드도 요청을 보내고 모든 알림에 응답이 필요한데, 설계서의 수신 처리 함수는 반환값이 없어 응답을 만들 방법이 아예 없었다. 게다가 입출력 스레드에서 송신 함수를 부르면 자기가 처리할 큐를 자기가 기다리는 교착이 된다. 반환값으로 회신하는 경로를 신설하고 교착 경고를 명시했다.

**검증기 자체의 결함도 잡혔다.** 모든 예외를 "제약이 작동했다"로 집계하고 있어서, SQL 오타나 이름 오류가 통과로 위장될 수 있었다. 특정 예외만 인정하도록 좁히고, 의도적 오류를 넣어 검출을 확인했다.

**부분 기각한 1건**은 "이전 라운드에서 추가한 항목을 Claude가 삭제했다"는 지적이었다. 수신한 인덱스에 해당 행이 애초에 없었으므로 삭제할 대상이 존재하지 않았다. 다만 같은 문서에 담긴 "총계가 문서마다 다르다"는 지적은 타당해서, 표준결함 총계를 17건으로 통일하고 **"총계는 인덱스의 표준결함 행 수와 항상 일치한다"**는 불변식을 규약에 넣었다.

두 라운드 누적으로 검증 규모는 **DB 제약 32 → 61종**, **계약 29 → 37종**이 됐다.

### 3차 검증 결과

**6건**이 보고됐고 **전부 타당**했다. 기각 0건.

| 발견 | 성격 |
|---|---|
| **승인 스냅샷의 NULL·조건 변조 우회** | 승인 게이트가 내용 수준에서 다시 뚫림 |
| 즉시 회신 설계가 메시지 전량을 덮지 못함 | 2차에서 신설한 회신 경로가 절반만 구현 가능 |
| I/O 루프가 무수신 상태에서 송신을 못 함 | 제어 왕복이 성립하지 않음 |
| 재생이 송수신 방향을 무시함 | 과거의 자기 송신이 현재의 수신으로 되돌아옴 |
| 검증 메타데이터가 다시 어긋남 | 어느 문서가 정본인지 불명확 |
| 32비트 정수 범위가 조용히 래핑됨 | 골든 벡터의 정답 자체가 오염될 수 있음 |

**가장 심각한 것은 승인 스냅샷이다.** 2차에서 "승인된 명령과 실행 명령을 결속한다"는 트리거를 넣었는데, 승인 상태이면서 명령이 비어 있는 규칙을 만들면 그 비교가 SQL의 3값 논리 때문에 **참이 되지 않아 발화하지 않는다.** 즉 빈 승인을 하나 만들어 두고 아무 명령이나 붙이면 통과했다. 승인 상태에서는 조건식과 명령을 모두 갖추도록 강제하고, 비교를 NULL 안전 연산으로 바꾸고, 승인 후에는 조건식까지 봉인했다. 수정 전·후 스키마를 각각 만들어 우회가 실제로 성립했고 지금은 막힌다는 것을 따로 확인했다.

**2차의 수정이 절반짜리였다는 것도 드러났다.** 신설한 회신 경로는 노드가 보낼 수 있는 요청 5종 중 1종만 처리했고, 알림 5종 중 1종이 누락돼 있었으며, 회신을 만들 빌더가 계약에 아예 없었다. 방향표를 계약 파일로 올려 한 곳에서만 정의하고, 계약 테스트가 누락을 검출하도록 했다.

**같은 종류의 문제가 두 라운드 연속 나온 항목이 있다** — 문서에 적힌 수치와 실제 산출물의 불일치다. 사람이 세는 한 반복되므로 검사를 코드로 고정했다(`fix_log/meta_verify.py`). 인덱스와 개별 기록의 상태·심각도, 현황 집계, 표준결함 총계, DDL 객체 수, 회귀 테스트 존재 여부를 기계적으로 대조한다. **이 스크립트가 처음 실행되자마자 3차 인덱스의 집계 오류를 잡아냈다.**

### 4차 검증 결과

**5건**이 보고됐고 **전부 타당**했다. 기각 0건.

| 발견 | 성격 |
|---|---|
| **승인 명령과 실제 실행 대상 장치가 결속되지 않음** | 사람 승인 게이트가 "어느 장치를"을 보장하지 못함 |
| 승인 후 승인자·승인시각 위조 가능 | 감사 기록의 신뢰성 상실 |
| 응답 매칭이 메시지 종류를 보지 않음 | 다른 요청의 응답이 현재 호출 결과로 반환됨 |
| 디코딩이 Reserved 데이터 타입을 수용 | 기능 2가 해당 위반을 놓침 |
| 출력 문자 하나로 한국어 Windows에서 검증기 중단 | 심사자 기본 환경에서 자체 검증 불가 |

**가장 심각한 것은 대상 결속이다.** 3차에서 "승인한 명령과 실행 명령이 같아야 한다"를 강제했는데, **명령은 같고 장치만 다른 실행**은 그대로 통과했다. 승인 JSON이 A밸브를 명시해도 실행 레코드의 대상을 B밸브로 넣을 수 있고, 넣은 뒤 바꿀 수도 있었다. 제어에서 "무엇을"과 "어느 장치를"은 분리되지 않는다 — 승인 대상을 정규화된 컬럼으로 승격해 DB가 직접 대조하게 했다. JSON 안의 문자열은 파싱 없이 비교할 수 없기 때문에 컬럼이어야 한다.

**승인 감사 기록도 위조 가능했다.** 승인 철회만 막고 있어서, 승인자를 다른 사람으로 바꾸거나 승인 시각을 앞당기는 것이 통과했다. 두 값이 곧 "사람이 최종 결정했다"는 증거이므로 같은 강도로 봉인했다.

**앞선 라운드의 수정이 또 절반이었다.** 3차에서 신설한 응답 매칭은 노드 번호와 메시지 번호만 보고, 메시지 종류를 확인하지 않았다. 값 범위 검사도 인코딩만 막고 디코딩은 열려 있었다. **"고쳤다"의 범위를 스스로 좁게 잡는 경향**이 세 라운드 연속 나타났으므로, 이후 수정은 대칭 경로(인코딩↔디코딩, 삽입↔갱신, 송신↔수신)를 항상 함께 확인하기로 했다.

**재현성 결함이 새 문자열 때문에 재발했다.** 3차에서 추가한 검증 제목의 문장부호 하나가 한국어 Windows 기본 콘솔에서 인코딩되지 않아, 심사자 환경에서 검증기가 중간에 멈춘다. 문자를 바꾸는 것으로 끝내지 않고, **검증기 출력 전체를 해당 인코딩으로 시도해보는 검사**를 메타 검증에 넣었다. 리눅스에서도 윈도우 결함을 잡는다.

네 라운드 누적으로 검증 규모는 **DB 제약 32 → 76종**, **계약 29 → 53종**, 프로토콜 명세의 값 범위·왕복 **18종**, 메타 검증 **20종**이 됐다.

### 5차 검증 결과

API 명세를 포함해 돌린 결과 **5건**이 보고됐고 **전부 타당**했다. 기각 0건, 보류 1건(항목 안의 확장 결정).

| 발견 | 성격 |
|---|---|
| **메타 검증기가 출력 해석 실패를 통과로 처리** | 4차에 만든 검사가 정작 대상 환경에서 무효 |
| 제어 명령 객체가 열려 있어 금지한 대상 장치를 실을 수 있음 | 대상 단일 출처 결정이 API 계약에서 미성립 |
| API가 32비트 정수 범위를 강제하지 않음 | 계약만 보고 만든 클라이언트가 전송 불가능한 요청을 정상으로 판단 |
| API 쓰기가 "입출력 스레드 단독 쓰기" 원칙과 충돌 | 문서대로 구현하면 규칙을 저장할 방법이 없음 |
| 승인자 식별이 자체 주장 헤더 | 사람 승인의 증거력을 과장할 위험 |

**가장 무거운 것은 메타 검증기다.** 4차에서 "한국어 윈도우 콘솔에서 검증기가 멈추는 문제"를 잡으려고 자식 프로세스의 출력을 검사하는 장치를 만들었는데, **그 장치가 정작 윈도우에서는 검사 대상을 통째로 잃고 통과를 찍는 구조**였다. 파이썬의 하위 프로세스 구현이 윈도우에서는 별도 스레드로 출력을 해석하는데, 그 스레드가 죽어도 호출자에게는 예외가 오지 않고 빈 출력과 정상 종료코드만 돌아온다. 표준 라이브러리 소스를 직접 열어 확인했다.

바이트로 받아 해석을 검증기가 직접 하고, 출력이 비었거나 해석에 실패하면 실패로 처리하도록 고쳤다. **고쳤다는 말을 믿지 않기 위해, 저장소 사본에 문제 문자를 일부러 심어 검출되는지 확인했다.**

**두 건은 같은 원인이었다.** 제어 명령 객체가 대상 장치를 실을 수 있었던 것과 값 범위가 없었던 것 — 둘 다 검사가 *"스키마에 그 필드가 선언되어 있나"* 만 봤기 때문이다. 선언되지 않은 필드를 **허용**하는 것이 기본 동작이라는 점을 놓쳤다. 이제 검증기는 반례를 실제로 넣어보고 거부되는지 본다. 외부 패키지를 쓰면 의존성이 늘어 오프라인 배포에 실리므로, 필요한 만큼만 구현한 평가기를 검증기 안에 두고 개발 중에 널리 쓰이는 구현과 20개 사례에서 판정이 일치함을 확인했다.

**설계 문서 하나가 실제로 틀렸다.** 아키텍처는 "DB 쓰기는 입출력 스레드가 전담한다"고 적었는데, API를 확정하고 보니 규칙 생성과 승인도 DB 쓰기다. 문서대로 구현하면 규칙을 저장할 방법이 없다. **소유권의 단위를 스레드가 아니라 테이블로 바꿨다** — 노드에서 온 데이터는 입출력 스레드가, 사람이 만든 규칙과 지시는 API 스레드가 쓴다. 겹치는 테이블은 제어 실행 이력 하나뿐이고 컬럼이 분리된다.

**주장의 강도를 낮춘 것도 있다.** 승인자 식별은 호출자가 스스로 붙이는 헤더이므로, 승인 기록이 증명하는 것은 "이 식별자가 제출됐고 이후 위조되지 않았다"까지다. "그 사람이 실제로 결정했다"는 신원 보장이 아니다. 인증은 표준 3종 어디에도 규정이 없어 범위 밖으로 두되, **무엇이 보장되지 않는지를 문서 세 곳에 적고 검증기가 그 문구의 존재를 검사**하게 했다. 온실 관리자만 승인 가능하게 하는 인가 제약은 데이터 모델상 가능하지만, 기존 제약 테스트 98종의 판정 근거가 흐려질 위험이 있어 **일정 여유가 생기면 재검토하는 것으로 보류**했다.

다섯 라운드 누적으로 검증 규모는 **DB 제약 76종 · 계약 53종 · 프로토콜 명세 18종 · API 34종 · 메타 22종**이다.

### 6차 검증 결과

**3건**이 보고됐고 **전부 타당**했다. 기각 0건. 셋 다 **직전 라운드 수정의 빈틈**이라는 공통점이 있다.

| 발견 | 직전 수정의 무엇이 부족했나 |
|---|---|
| 실수형 값의 범위를 API가 강제하지 않음 | 5차에서 "두 계층이 같은 반례로 검증된다"고 적었지만, **그 반례에 실수형이 없었다** |
| 쓰기 경로 검사가 개수만 셈 | 5차에서 재정의한 쓰기 표면을 회귀 검사가 실제로 보호하지 못했다 |
| 쓰기 소유권 표에서 테이블 9개 누락 | 5차에서 "테이블별 단일 소유자"를 불변식으로 선언했는데 **표가 전체를 덮지 않았다** |

**이번 라운드의 교훈은 검사 방식이 아니라 검사 대상의 완결성이다.** 지난 라운드에는 "선언만 보지 말고 반례를 넣어보라"가 교훈이었다. 그 방식은 맞았는데, **반례 집합에 실수형이 통째로 빠져 있으면 결과는 같다.** 마찬가지로 소유권 표는 형식이 옳아도 테이블 9개가 빠지면 불변식이 아니다.

그래서 이번에는 **완결성 자체를 자동 검사로 고정했다.**

- 쓰기 경로는 개수가 아니라 **허용 집합과 정확히 대조**한다. 경로 하나를 지우고 다른 곳에 만든 변형으로 검출을 확인했다.
- 소유권 표는 설계 문서에서 테이블명을 뽑아 **스키마의 테이블 목록 전체와 대조**한다. 표에서 한 줄을 지운 사본으로 검출을 확인했다.
- 실수형 범위는 API와 프로토콜 양쪽에 넣고, 경계값이 실제 바이트로 어떻게 나오는지까지 확인한다.

**분류를 하나 새로 만들었다.** 소유권 표를 완결하면서 농장·온실·사용자 같은 설정형 데이터가 어디에도 속하지 않는다는 것이 드러났다. 이들은 기동 시 한 번 넣고 이후 아무도 쓰지 않는다 — **"시드 로더 소유, 런타임 쓰기 금지"** 라는 분류를 만들어 9개를 배정했다. 여기에 런타임 쓰기가 생기는 순간 계약이 깨진 것이다.

여섯 라운드 누적으로 검증 규모는 **DB 제약 76종 · 계약 53종 · 프로토콜 명세 23종 · API 35종 · 메타 27종**이다.

### 7차 검증 결과

**2건**이 보고됐고 **전부 타당**했다. 기각 0건. 이번에도 **직전 라운드 수정의 빈틈**이다.

| 발견 | 6차 수정의 무엇이 부족했나 |
|---|---|
| 값 변환 단계에서 원시 예외가 새어나감 | "호출자는 오류 하나만 잡으면 된다"는 계약이 **입력 형태에 따라 깨졌다** |
| 소유권 중복 배정을 검사기가 통과 | "정확히 하나"라는 불변식 중 **누락만 보고 중복은 안 봤다** |

**첫째는 검사 순서의 문제였다.** 6차에서 실수형 범위를 막았는데, `10**400` 같은 큰 정수는 **범위를 보기도 전에 형 변환 단계에서 실패**한다. 문자열이나 빈 값도 각각 다른 예외를 낸다. 같은 "32비트에 안 들어가는 값"이 입력 형태에 따라 서로 다른 오류로 나오면, 이 값을 받는 프로토콜 계층이 오류 처리를 두 갈래로 만들어야 한다. 변환 단계까지 감싸 하나로 정규화했다.

**지적은 실수형만 짚었지만 정수 경로에도 같은 누출이 있었다.** 원인이 같으므로 함께 고쳤다 — 지난 라운드들에서 반복해 지적받은 "고쳤다의 범위를 좁게 잡는" 패턴을 이번에는 먼저 넓혔다.

**둘째는 자동 검사가 절반만 보고 있었다.** 6차에서 "31개 테이블 전부가 정확히 하나의 소유자를 갖는다"를 자동 검사로 고정했는데, 그 검사는 **빠진 테이블만 찾고 두 곳에 배정된 테이블은 못 찾았다.** 모든 분류를 하나의 집합으로 합치면 중복이 소멸하기 때문이다. 분류별로 나눠 세도록 고치고, 문서에 적힌 개수도 믿지 않고 실제 행에서 도출하게 했다.

**새 검사가 즉시 내 문서의 모호함을 잡았다.** 설명용 인용문에 적은 표기를 배정으로 오인해 한 분류를 7개로 셌다. 배정으로 인정하는 범위를 표 안으로 한정했다. **결함 주입 3종**(중복·누락·개수 표기 조작)으로 셋 다 서로 다른 항목이 잡아내는 것을 확인했다.

일곱 라운드 누적으로 검증 규모는 **DB 제약 76종 · 계약 53종 · 프로토콜 명세 29종 · API 35종 · 메타 30종**이다.

골든 벡터 초판에 대한 첫 검증에서 **5건**이 보고됐고 **전부 타당**했다. 기각 0건.

| 발견 | 성격 |
|---|---|
| **정상 오류 알림을 위반으로 표시** | 격리되어 알림 저장과 응답이 모두 사라진다 |
| 최대 프레임을 잘못 잡아 타임아웃 근거가 틀림 | 다수 장치 노드에서 정상 응답 전에 재전송이 일어난다 |
| 주입별 기대가 뒤바뀌어도 검증기가 통과 | 틀린 정답이 세 구현에 동시에 전파될 수 있다 |
| 생성기가 검증 중 산출물을 덮어써 변질을 은폐 | 제출물이 정본에서 나온 것인지 증명 불가 |
| 개정 제안 벡터가 양방향 알림을 한쪽으로 축소 | 제안이 코드 외의 표준 의미까지 바꾼 것처럼 기록됨 |

**첫째가 동작을 바꾼다.** 노드가 배터리 부족을 알리는 것은 **정상 메시지**다(표준 8.2.1.1 — 제어기는 수신 확인을 보낸다). 그런데 벡터가 이걸 "위반" 목록에 넣어 두면, 설계서대로 구현했을 때 프레임이 격리되고 **알림 저장도 수신 확인도 실행되지 않는다.** 노드는 확인을 못 받아 일정 주기마다 같은 알림을 재전송한다. 벡터에 판정 종류(위반 / 알림 / 정상) 필드를 넣어 갈랐다.

**둘째는 산수를 다시 한 결과다.** 초안은 최대 프레임을 51바이트로 잡았는데, 그건 장치 한 대짜리 응답일 뿐이다. 표준은 노드당 장치를 255대까지 허용하므로 최대 7,671바이트, 9600 baud에서 **약 8초**가 걸린다. 기본 타임아웃 2초로는 정상 응답이 끝나기 전에 재전송이 시작된다.

노드당 장치 상한을 **16대**로 선언하고 근거(AVR 메모리 2KB, 전송 시간 0.52초, 시연 규모)를 적었다. 골든 경계 벡터 하나를 그 최대 프레임으로 교체해, **펌웨어 수신 버퍼 크기와 타임아웃 근거가 같은 바이트열 하나로 묶이게** 했다. 표준이 타임아웃과 장치 수의 관계를 규정하지 않는다는 점은 **표준 실구현 장애 지점으로 새로 등재**했다 — 17건에서 18건이 됐다.

**셋째와 넷째는 검증기 자신의 결함이다.** 골든 벡터는 세 구현이 공유하는 정답이므로, 검증기가 느슨하면 틀린 정답이 세 곳에 동시에 퍼진다. 이제 주입 라벨과 기대 코드를 1:1로 대조하고, **벡터에 적힌 기대를 보지 않고 바이트에서 위반을 다시 판정해** 대조한다.

넷째는 더 구조적이다. 생성기가 검증 파이프라인 안에서 산출물을 덮어쓰고 있었다 — **검증이 자기가 검사할 증거를 지우고 있었다.** 생성기 두 개에 "쓰지 않고 대조만 하는" 모드를 넣고, 검증 파이프라인은 그 모드로만 부른다. 지적은 골든만 짚었지만 앞 단계의 예시 프레임 생성기도 같은 문제라 함께 고쳤다.

여덟 라운드 누적으로 검증 규모는 **DB 제약 76종 · 계약 53종 · 프로토콜 명세 29종 · API 35종 · 골든 28종 · 메타 34종**이다.

### 9차 검증 결과

**3건**이 보고됐고 **전부 타당**했다. 기각 0건.

| 발견 | 성격 |
|---|---|
| **한 프레임이 장치 수를 두 값으로 주장** | 세 구현이 개수 불일치를 정상으로 받아들이게 된다 |
| 앞 단계 문서에 폐기된 타임아웃 근거가 남음 | 구현자가 먼저 읽은 쪽을 따르면 상한이 되돌아간다 |
| 재생성한 산출물을 커밋에 넣지 않음 | 제출물의 전체 검증 명령이 실패한다 |

**첫째가 실질적이다.** 연결 응답은 "노드 속성 + 그 노드에 연결된 N개 장치의 속성"을 담는데, 노드 속성 안의 장치 수 필드가 3인데 장치 속성은 16개가 붙어 있었다. 지적은 문제 벡터 하나를 짚었지만 **전 벡터를 훑으니 4건이 어긋나 있었고, 장치를 하나도 보내지 않으면서 3대라고 적은 것까지 5건**이었다. 상수 하나를 생각 없이 재사용한 결과다.

장치 수를 벡터마다 명시하도록 바꾸고, **표준의 이 불변식을 생성기와 검증기 양쪽에 넣었다.** 부수적으로 경계 벡터 하나가 오히려 좋아졌다 — "장치 0대인 노드의 연결 응답"이 되어 가변부 0개 허용의 의미가 자기모순 없이 성립한다.

**이 수정을 교차 검증이 잡아냈다.** 골든 벡터만 고치고 앞 단계의 예시 생성기를 그대로 뒀더니 같은 메시지의 바이트가 어긋나 즉시 실패했다 — "같은 명세서를 두 번 타이핑해 대조한다"는 장치가 말이 아니라 실제로 작동한다는 증거다.

**둘째는 또 '고쳤다의 범위'였다.** 직전 라운드에서 타임아웃 근거를 바로잡으며 아키텍처만 보고 프로토콜 명세서를 안 봤다. 같은 수치를 두 문서가 다르게 적고 있으면 구현자는 먼저 읽은 쪽을 따른다.

**셋째는 코드 결함이 아니라 커밋 누락이다.** 다만 **직전 라운드에 넣은 "검증 중 산출물을 덮어쓰지 않는다"는 장치가 의도대로 드러냈다** — 예전이라면 검증기가 파일을 덮어쓰며 조용히 지나갔을 상황이다.

아홉 라운드 누적으로 검증 규모는 **DB 제약 76종 · 계약 53종 · 프로토콜 명세 29종 · API 35종 · 골든 29종 · 메타 34종**이다.

> **일곱 라운드의 패턴이 뚜렷하다.** 4차 이후로 새로 보고된 결함은 대부분 **표준 해석의 오류가 아니라 직전 수정이 남긴 빈틈**이다. 설계 자체는 수렴하고 있고, 남은 것은 "고쳤다"의 경계를 스스로 좁게 잡지 않는 일이다. 그래서 매 라운드 **검사 자체를 자동화**해 왔고, 지금은 메타 검증만 30종이다.

## 6. 아키텍처 설계

`project_docs/arch/아키텍처_설계서.md`

### 무엇을 했나

앞서 만든 세 명세(프로토콜·데이터·모듈 경계)를 **하나의 실행 가능한 프로그램으로 조립하는 방법**을 정했다. 미결로 남아 있던 동시성 모델과 의존성 정책이 여기서 확정됐다.

### 모든 결정의 출발점 — 제약 4개

| 제약 | 귀결 |
|---|---|
| 심사자 PC에 하드웨어가 없다 | 전송 계층만 교체 가능한 구조 |
| 한 줄 명령으로 실행되어야 한다 | 단일 프로세스, 외부 데몬 없음 |
| 오프라인 설치가 기본 경로다 | 의존성 3개, 빌드 단계 없음 |
| 표준 해석은 한 곳에만 | 계층 간 통행 타입은 `Frame` 하나 |

### 확정한 것

**동시성 — 단일 프로세스에 스레드 3개.** 메인은 웹 서버, SIAP I/O 스레드가 시리얼·소켓을 단독 소유하고, 모드에 따라 로그 재생기 또는 가상 노드 스레드가 붙는다. 포트를 두 스레드가 건드리면 프레임이 깨지므로 소유자를 하나로 못박았다. DB 쓰기는 **테이블 단위로 소유자를 나눴다** — 노드에서 온 데이터는 I/O 스레드가, 사람이 만든 규칙과 제어 지시는 API 스레드가 쓴다. 겹치는 테이블은 제어 실행 이력 하나뿐이고 컬럼이 분리되어 있다(4차 검증에서 정정).

**의존성 3개** — `fastapi`, `uvicorn`, `pyserial`. 프론트엔드는 빌드 단계 없는 vanilla JS이고, HTTP 클라이언트는 표준 라이브러리를 쓴다. 다만 `fastapi`가 끌고 오는 `pydantic-core`는 플랫폼별 바이너리 휠이라, 오프라인 설치 시 심사자 플랫폼과 맞는 휠을 함께 배포해야 한다(2차 검증에서 정정). 이 의존성이 아예 없는 대체 경로도 함께 준비한다.

**ORM을 쓰지 않기로 했다.** `schema.sql`에 트리거 37개와 CHECK 제약이 들어 있는데, ORM을 얹으면 스키마가 두 곳에 생겨 어긋나고 제약을 우회하는 경로가 열린다.

**가상 노드는 게이트웨이 코덱을 재사용하지 않는다.** 같은 코덱을 쓰면 인코더 버그가 상쇄되어 드러나지 않기 때문이다.

### 놓치기 쉬운 지점 둘

**SQLite의 외래키는 기본값이 꺼져 있다.** 연결마다 켜지 않으면 스키마 검증을 통과해도 런타임에서 제약이 조용히 무시된다. 연결 팩토리 한 곳에서만 연결을 만들고 거기서 PRAGMA를 걸도록 했다.

**I/O 스레드는 조용히 죽으면 안 된다.** 죽어도 화면은 마지막 상태를 계속 보여주므로 심사자가 "동작 중"으로 오해한다. 헬스 상태를 API로 노출한다.

### 2차 검증 후 보강된 것

**회신 경로(§3.1-a)를 신설했다.** 초안에는 수신 처리만 있고 응답을 만들 경로가 없었다. 수신↔회신 대응표와 자기대기 교착 경고를 함께 명시했다.

**로그 캡처를 3단계로 분리했다.** 촬영 시 남기는 원본과 재생에 쓰는 파일은 형식이 다르므로 변환 단계가 필요하다. 원본은 진위 근거로 함께 제출한다.

**오프라인 설치에 무의존 폴백 경로를 넣었다.** 웹 실행에 필요한 패키지가 설치되지 않아도, 펌웨어 테스트·계약 테스트·DB 제약 테스트 셋은 표준 라이브러리만으로 돌아간다. 설치가 실패해도 표준 준수의 근거는 남는다.

**표준이 정하지 않은 시간 단위를 확정했다.** 프로파일의 시간 필드 셋을 전부 초로 통일했다 — 같은 표준에서 단위가 명시된 유일한 시간 필드에 맞춘 것이다.

### 3차 검증 후 보강된 것

**회신 대상을 표준 8장 전량으로 넓혔다.** 노드가 보낼 수 있는 요청 5종과 알림 5종의 대응표를 계약 파일에 두고, 설계서와 서비스 계층은 그 표를 참조만 한다. 표준 해석이 두 곳에 생기지 않는다.

**위반 프레임에도 답하기로 했다.** 초안은 위반을 격리만 하고 버렸는데, 표준은 요청 처리 실패 시 오류 코드를 담은 응답을 보내라고 규정한다. 오류 코드 표가 존재하는 이유가 그것이다. 다만 알림에 대한 응답에는 오류를 실을 자리가 없어 회신하지 않기로 했고, 이 결정은 표준 미규정 사항으로 기록한다.

**입출력 루프를 유한 대기로 바꿨다.** 무한 대기로 두면 수신이 없는 동안 화면에서 내린 제어가 포트로 나가지 못한다. 수신·송신·재전송 만료를 같은 루프에서 매 회 처리하고, 응답 매칭 키와 재전송 시 식별자 유지 규칙을 확정했다.

**재생은 수신 방향만 주입한다.** 캡처 파일에는 게이트웨이의 송신도 함께 들어 있어, 방향을 무시하면 과거에 자신이 보낸 프레임을 노드가 보낸 것으로 처리한다. 송신 기록은 대신 **기대 출력**으로 써서 재생 결과가 실제 실행과 같은지 대조한다.

### 4차 검증 후 보강된 것

**승인 스냅샷이 대상 장치까지 포함한다.** 제어 규칙에 대상 장치 컬럼을 추가하고, 승인 상태에서는 조건식·명령·대상 셋이 모두 채워지도록 강제했다. 규칙 기반 실행은 그 대상과 일치해야만 기록될 수 있고, 기록 후 대상 변경도 막힌다. 사용자가 직접 지시하는 수동 제어는 권한 출처가 사용자 자신이므로 이 제약에서 제외된다.

**승인 봉인 트리거를 7종으로 정리했다.** 명령·조건식·대상·승인자·승인시각·철회·실행 레코드의 권한 필드를 각각 다른 트리거가 막는다. 어느 하나가 열려 있으면 "사람이 승인한 대로만 나간다"가 성립하지 않는다.

**응답 매칭이 세 조건을 본다.** 노드 번호·메시지 번호·**메시지 종류**다. 기대와 다른 프레임은 대기 항목을 소비하지 않고 흘려보낸다 — 진짜 응답이 아직 올 수 있기 때문이다. 기대 종류는 계약 파일의 함수 하나가 정하고, 이 함수는 회신 종류를 정하는 함수와 쌍을 이룬다.

**검증기 출력의 문자 집합을 검사 대상에 넣었다.** 심사자 환경 재현성은 문서가 아니라 테스트로 지켜야 한다.

## 7. API 명세 (REST + SSE)

`project_docs/api/` — 명세서 / `openapi.json` / `api_verify.py`

### 무엇을 했나

화면과 서버 사이의 HTTP 표면 **20종**을 OpenAPI 3.1로 확정했다. 세 표준 어디에도 HTTP 규정은 없으므로, 이 단계의 목적은 "표준을 지켰다"가 아니라 **표준 3종의 요구가 화면까지 손상 없이 도달하는가**를 보이는 것이다.

문서 형식은 JSON을 택했다. YAML이 읽기 좋지만 검증 스크립트에 외부 패키지가 필요해져 직접 의존성이 3개에서 4개로 늘고 오프라인 패키지 용량에도 실린다. 사람이 읽는 몫은 명세서가 맡는다.

### 표면이 주장을 대신하게 만든 것 셋

**① 노드 종류가 경로에도 스키마에도 없다.** 센서별 경로를 만드는 순간 "서버 코드 수정 0줄"이 거짓이 된다. 종류는 데이터로만 존재하며, 측정 항목은 열거되지 않은 문자열이다. 장치상태처럼 서브타입마다 속성이 실제로 다른 경우는 속성 묶음을 통째로 객체에 담아, DB에 테이블을 더해도 API가 변하지 않게 했다.

**② 승인 게이트를 표면으로 옮겼다.** DB는 이미 트리거 8종으로 봉인되어 있지만, API를 평범한 CRUD로 열면 "막히긴 하는데 시도는 할 수 있는" 상태가 된다. 세 곳에서 **시도 자체를 불가능하게** 했다 — 초안 생성은 실행 가능한 필드를 받지 못하고, 승인 요청은 승인자·시각을 실을 수 없으며, **규칙 실행 요청에는 본문이 아예 없다.** 명령과 대상은 서버가 승인 스냅샷에서 읽는다.

**③ 오류가 조항 번호와 차단한 제약 이름을 돌려준다.** 트리거가 막으면 그 사실을 삼키지 않고 그대로 올린다. 제약 이름은 디버깅 편의가 아니라 증거다 — 심사자가 그 이름으로 스키마 파일을 검색하면 차단 근거가 애플리케이션 코드가 아니라 DDL에 있음을 즉시 확인할 수 있다.

## 8. 골든 테스트 벡터 52건

`project_docs/contracts/vectors/` — 명세서 / `golden_layout.py` / `golden.jsonl` / `golden_verify.py`

### 무엇을 했나

C 펌웨어와 Python 게이트웨이, 백엔드가 **같은 파일로 검증받는 정답 집합**을 만들었다. 표준 원문에는 실제 바이트열 예시가 하나도 없으므로(그림은 필드 배치 다이어그램일 뿐), 이 52건이 **표준 준수의 유일한 바이트 수준 근거**가 된다.

세 구현이 각자 인코딩·디코딩해 이 파일과 대조한다. 어느 하나가 비트를 잘못 놓으면 그 자리에서 드러난다 — **"세 MCU가 같은 프로토콜로 동작한다"를 말이 아니라 증거로 만드는 장치**다.

### "손으로 만든다"를 어떻게 지켰나

규약은 *"손으로 만들고 코드로 검증한다. 코드로 생성한 것을 정답으로 삼으면 자기 검증 순환이 된다"* 고 정하고 있다. 52건을 hex로 직접 타이핑하는 것이 문자적 해석이지만, 그러면 오타가 늘고 **틀렸을 때 어느 필드가 틀렸는지 추적할 근거가 남지 않는다.**

그래서 **벡터마다 (필드명, 비트폭, 값)을 표준 표를 보며 손으로 적고**, 메시지 구조를 전혀 모르는 비트 결합기만 통과시켰다. 심사자가 여섯 줄짜리 구조체 정의를 표준의 표와 한 줄씩 대조할 수 있다.

**앞서 만든 명세 검증기의 인코더는 재사용하지 않았다.** 같은 명세서를 두 번 타이핑해 같은 바이트가 나오는지가 사람의 오독을 잡는 유일한 장치이기 때문이다. 겹치는 9건이 페이로드 바이트 단위로 일치했다.

### 구성

| 분류 | 건수 | 내용 |
|---|---|---|
| 정상 | 34 | 메시지 종류를 정확히 한 번씩. 같은 코드를 쓰는 알림 2종이 나란히 있어 길이 판별을 실제로 하는지 드러난다 |
| 경계 | 10 | 7개 축 — 가변 개수 0·최대, 메시지 번호 랩어라운드, 20비트 식별자 최댓값, 정수·실수 타입별 경계, 필드 폭 최댓값 |
| 위반 | 8 | 규약이 정한 기능 2 주입 시나리오. 검증기가 규약 문서에서 표를 읽어 대조한다 |

벡터마다 **필드 단위 분해**를 함께 담았다. C 테스트가 "19바이트 중 13번째가 다르다"가 아니라 "Subtype이 0x85가 아니라 0x0A로 나왔다"라고 말할 수 있다.

개정 제안안(같은 코드를 쓰는 알림 2종을 분리하는 안)은 **별도 파일**에 5건만 뒀다. "표준을 이렇게 구현했다"와 "표준을 이렇게 고치자"가 한 파일에 섞이면 심사자가 준수 근거를 구분할 수 없다.

### 검증 — 29/29 통과

정답의 근거를 **벡터를 만든 코드가 아닌 곳**에서 가져온다. 헤더 오프셋을 검증기에서 다시 타이핑해 재판독하고, 벡터보다 먼저 존재한 계약 파일로 판정을 재산출하고, 독립 인코더의 예시와 바이트를 대조하고, 위반 8종을 규약 문서와 맞춘다.

**작성 중 세 건이 실제로 걸렸고, 첫 번째가 이 단계의 수확이다.** 가변부만 있는 메시지의 빈 페이로드를 "판별 불가"로 기대했는데 계약은 메시지 종류를 정상적으로 돌려줬다. 코드 해석과 개수 산출은 **다른 함수의 책임**이고, 거부는 후자에서 일어난다. 문서를 읽을 때는 보이지 않던 책임 분담이 벡터 한 건에서 드러났다.

## 9. 펌웨어 설계

`project_docs/firmware/` — 펌웨어 설계서 · `firmware_verify.py`

### 무엇을 했나

앞선 문서들이 **바이트열이 어떻게 생겼는지**를 확정했다면, 이 단계는 **그 바이트열을 2KB SRAM 위에서 어떻게 다루는지**를 확정했다. 결정 일곱 가지 중 넷이 표준이 정하지 않은 것이다.

### 이 단계에서 가장 큰 결정 — 스트리밍 디코드

최대 프레임은 501 byte다(골든 `B03`). Uno / Pro Mini의 SRAM은 2,048 byte뿐이라, 프레임 하나를 통째로 담는 버퍼만으로 SRAM의 4분의 1이 사라진다.

세 전략을 비교해 **고정부까지만 버퍼링하고 가변 요소는 하나씩 읽어 즉시 소비하는 방식**을 택했다. 필요 버퍼가 501 → **51 byte**로 줄고, 더 중요하게는 **수신 버퍼 크기가 상대가 보낸 개수와 무관해진다.** 표준이 디바이스 개수를 8비트(최대 255)로 열어둔 것을 2KB MCU가 받아낼 수 있는 유일한 방법이다.

노드 3종의 예상 SRAM 사용률이 12~14%로 내려갔다. 통째로 버퍼링했다면 상한 노드에서 83%가 되어 스택 여유가 사라진다.

### 하드웨어 경계를 함수 포인터로 그었다

`firmware/core/`는 보드 헤더를 하나도 include하지 않고, 전송·디바이스 I/O를 각각 구조체 하나로만 안다. 링크타임 심볼 치환이 더 짧지만 **한 바이너리에 구현이 하나뿐이라 호스트 테스트에서 노드 둘을 동시에 돌릴 수 없다.** 간접호출 비용은 프레임당 31μs로, 응답 대기 2초 대비 무시할 수준임을 계산으로 확인했다.

"`core/`를 수정하지 않았다"는 주장의 **판정 방법**도 명시했다 — 3종 빌드 전후 해시 동일, 보드 판별 매크로 0개, 골든 52건에서 동일 바이트. 조건부 컴파일이 하나만 들어가도 "동일 응용계층"이 아니라 "분기가 있는 공통 코드"가 된다.

### 구동기 입력 경로가 하나임을 설계로 못박았다

승인 게이트의 펌웨어 쪽 대응이다. 구동기를 움직일 수 있는 경로는 표준의 제어 요청 수신 한 군데뿐이고, 노드 내부 규칙 엔진도 AI 추론 코드도 두지 않는다. **노드는 승인 여부를 확인할 수단이 없고 확인할 필요도 없다 — 경로 자체가 하나이므로 서버를 우회할 방법이 없다.**

### 표준결함 1건 신규 — 프레임 경계·무결성 검사 미규정

표준은 통신 환경으로 RS232/485를 명시하면서 **프레임 시작 구분자도, 길이 프리앰블도, 체크섬도 정의하지 않는다.** 바이트 하나가 유실되면 수신기는 프레임 경계를 영구히 잃고, 손상된 바이트는 탐지되지 않은 채 유효 필드로 해석된다. 원문을 전수 검색해 확인했다.

**이것은 문서 작업만으로는 나오지 않는 종류의 발견이다.** 명세 단계에서는 프레임이 이미 한 덩어리로 주어진다고 가정하게 되고, 바이트 스트림 위에 올려놓는 펌웨어 설계에 들어가서야 드러난다. 표준결함 18 → **19건**.

본 구현은 표준 프레임 형식을 **바꾸지 않는다** — 구분자나 체크섬을 덧붙이면 그 순간 준수가 아니게 된다. 대신 수신측에서 헤더 네 조건을 동시에 만족할 때만 프레임 시작으로 인정하는 재동기 규칙을 둔다.

### 검증 — 50/50 통과

설계서는 산문이라 틀려도 통과한다. 그래서 문서의 숫자를 전부 파싱해 **문서 밖의 출처**로 재산출한 값과 맞추는 검증기를 신설했다. 메모리 표의 합계·백분율, 위반 8종 표와 골든 벡터의 대응, 응답 코드 분류의 전수 커버까지 기계가 본다.

**작성 중 실제로 두 건이 걸렸다.** 헤더 단계에서 걸러지는 위반을 5종으로 적었으나 실제로는 4종이었고, 상태 하나가 전이표에서 빠져 있었다. 둘 다 읽어서는 눈에 띄지 않는 종류다.

### 검증 후 보강 — 상태 머신을 두 번 고쳤다

외부 검증에서 5건이 나왔고 그중 둘이 무거웠다.

**표준의 알림 흐름을 통째로 빠뜨렸다.** 표준은 알림에도 요청과 동일한 응답 대기·재전송을 요구한다. 원문 그림 세 장을 직접 판독해 확인했다 — 알림은 재전송 횟수 안에서 반복되고, 리부팅은 **응답을 받거나 재전송을 소진한 뒤에야** 완료된다. 초안은 송신 버퍼에 쓴 것만으로 리부팅을 완료 처리했다. 수신 쪽도 한 상태에서만 응답했다. 표준 문언은 응답 조건을 "정상적으로 수신했을 경우"로 적을 뿐 노드 상태를 조건에 두지 않는다 — **응답을 상태와 무관한 전이로 올렸다.**

**오류 상태가 연결 승인을 우회하고 있었다.** 부팅 자가진단에 실패한 노드가 연결 절차를 한 번도 거치지 않고 정상 운용으로 복귀할 수 있었다. 오류 상태를 연결 이후 전용으로 좁히고, 연결 전 오류는 두 갈래로 나눴다 — 진단 실패는 연결을 막지 않고(알릴 수단이 연결 뒤에만 있다), 연결이 영구히 거부되면 정지 상태로 간다. **후자는 지적에 없던 같은 계열 오류를 함께 드러냈다** — 초안은 거부된 노드가 오류 알림을 반복하게 했는데, 그 알림은 게이트웨이가 받지 않는다. 없는 수단을 있는 것처럼 적는 것이 더 나쁘다고 보아 한계를 명시했다.

### 이 라운드의 교훈 — 녹색 결과가 증거가 되려면

가장 아픈 지적은 **검증기 자신에 대한 것**이었다. 26/26 이라는 결과가 나오는 상태에서 필수 응답 전이를 통째로 지우고, 요약의 수치를 터무니없는 값으로 바꾸고, 항목 개수를 변조해도 **셋 다 그대로 통과**했다. 검사가 상태 이름의 존재와 "나가는 줄이 하나 이상"만 보고 있었기 때문이다.

검사를 26 → **37종**으로 늘렸다. 표준 조항별 필수 전이 12종을 이름이 아니라 **내용으로** 대조하고, 요약표의 수치를 본문 표 실측과 맞추고, 항목 개수와 구조체 크기를 **계약과 C 선언에서 다시 계산**한다.

**보강한 검사가 곧바로 오류를 하나 더 잡았다.** 구조체 크기 재산출을 붙이자 문서의 값이 틀렸음이 드러났고, **재산출 로직 자체도 첫 구현에서 틀렸다** — 함수 포인터의 인자 목록에 있는 이름을 구조체 멤버로 세고 있었다. 재산출 검사는 재산출 로직이 검증되어야 의미가 있다는 것을 그대로 보여준 사례라 문서에 남겼다.

결함 주입 6종(보고된 3종 + 자체 3종) 전량에서 검출을 확인했다.

### 한 번 더 — 이번엔 정본이 어긋나 있었다

다음 검증에서 3건이 더 나왔고, **셋 다 같은 모양이었다.** 설계서 안은 맞는데 **개발 규약 문서가 반대로 적혀 있었다.** 앞 라운드에서 설계서만 고치고 규약을 함께 고치지 않은 결과다. 개발은 규약 문서를 먼저 읽으므로, 이 불일치는 설계서 내부 오류보다 구현에 더 직접 반영된다. **검증기가 규약 문서를 함께 읽도록 바꿨다** — 이전에는 설계서만 보고 있었다.

**정상 설정에서 알림 하나가 영구히 굶는 결함도 나왔다.** 센서값 전송 주기와 연결 확인 주기의 기본값이 둘 다 같은 값이라 매번 동시에 만료하는데, 동시에 하나만 대기할 수 있고 밀린 쪽은 다음 주기로 넘기게 되어 있었다. 검사 순서에서 지는 쪽이 한 번도 나가지 못한다. 밀림 표시 한 비트와 회전 순서 한 바이트로 해소했다 — 큐를 쌓지 않으므로 링크가 오래 막혀도 메모리가 늘지 않고 복구 직후 폭주하지도 않는다.

**비트 패커의 안전장치는 실제로 컴파일해 검증했다.** 앞 라운드에서 "반환값을 두면 컴파일러가 검사 누락을 잡아준다"고 적었는데, 확인해 보니 **반환형만 바꾸는 것으로는 경고가 나오지 않는다.** 전용 속성을 붙여야 한다. 범위 검사식도 틀렸다 — 쓰려던 식이 8비트 MCU와 호스트 양쪽에서 정의되지 않은 동작이고, 실제로 컴파일러가 "검사가 항상 참"이라고 경고했다. 시프트를 쓰지 않는 마스크식으로 바꾸고 1~32비트 전 폭을 실제로 돌려 통과시켰다.

검증기는 50종이 되었고, 결함 주입 11종 전량에서 검출을 확인했다.

## 10. 시연 시나리오

`project_docs/demo/` — 시연 시나리오 · `demo_verify.py`

### 무엇을 했나

만들 것이 두 개라는 점부터 확정했다. **1차 서면평가에 내는 2분 영상**과 **2차 발표평가의 현장 라이브 시연**이다. 같은 기능을 보여주지만 편집 가능 여부, 실패 대응, 네트워크 전제가 전부 다르므로 한 문서 안에서 분리해 설계했다.

### 영상은 배점표에서 거꾸로 설계했다

2분을 감으로 나누지 않고, 평가 항목마다 담당 컷을 먼저 배정한 뒤 길이를 붙였다. **어느 항목도 담당 컷이 없으면 안 된다**는 것이 원칙이다.

배점이 가장 큰 항목(표준 활용성 30점)에 **전체의 45%인 53초**를 배정했다. 이 컷에서 위반 프레임을 실제로 주입하고, 판정 결과에 **표준 조항 번호가 그대로 화면에 출력**된다. 조항 번호가 화면에 보이는 시간이 곧 그 항목의 점수라고 보았다.

주입할 위반은 앞서 만든 골든 벡터에서 그대로 가져온다. **영상에 나오는 바이트열과 제출하는 벡터 파일의 바이트열이 같아야** 심사자가 대조할 수 있고, 공고문의 "진위·창작성" 조항을 통과한다.

### 촬영 순서가 컷 순서와 다른 이유

화면 시연 세 장면을 **한 세션에서 끊지 않고** 녹화해야 한다. 제출하는 실측 프레임 로그가 이 촬영 세션에서 캡처한 것이기 때문이다. 컷 번호대로 따로 찍으면 로그가 갈려서 영상과 제출물의 대조 근거가 사라진다.

로그에 결측·위반·지연·오류 알림을 **의도적으로 남긴다.** 완벽하게 깨끗한 로그는 오히려 합성을 의심하게 만들고, 2차 평가의 "오류 대응 및 사람 검토 지점" 항목에 답할 재료도 없어진다.

### 블라인드는 되돌릴 수 없다

문서의 개인 경로는 제출 직전에 정리하면 되지만 **영상은 편집으로 되돌릴 수 없다.** 촬영 시점에 이미 프로젝트가 중립 경로에 있어야 하고, 터미널 프롬프트·브라우저 북마크·창 제목이 전부 정리되어 있어야 한다. 하드웨어 촬영은 검은 배경지에 근접으로 잡아 방 구조와 반사면을 배제한다.

음성 내레이션은 쓰지 않기로 했다. 목소리는 특정 가능성이 있고, 2분에 담을 정보량은 자막이 더 크다.

### 현장 시연은 실패를 전제로 설계했다

2차 평가는 배점 100점 중 50점이 시연과 발표 순서에 걸려 있다. 그래서 **폴백을 4단계로** 두었다 — 실물 하드웨어가 안 되면 가상 노드, 그것도 안 되면 실측 로그 재생, PC 자체가 문제면 제출 영상. 전환이 명령 한 줄이라 무대에서 10초면 끝난다. **폴백이 있다는 사실 자체를 발표에서 말하는 편이 낫다** — "전송 계층만 교체되므로 어느 모드에서도 같은 코드가 돕니다"가 그대로 기술 설명이 된다.

시연 중 한 장면은 **심사위원이 직접 고르게** 한다. 정해진 순서를 재생하는 것과 임의 입력에 반응하는 것은 다르고, 후자만이 "시나리오가 아니라 도구"임을 보인다.

승인 게이트 시연은 **거부를 먼저** 보여준다. 승인 후 동작만 보이면 게이트가 있는지 알 수 없다. 거부 상태에서 구동기가 움직이지 않는 것을 먼저 보여야 게이트의 존재가 증명된다.

### 검증 — 31/31 통과

시간 배분은 손으로 더하다 어긋나기 쉽고, 어긋난 채 촬영하면 2분을 넘겨 규격 위반이 된다. 컷 시트의 길이 합·시작 시각 연속성·상한을 기계가 검산하고, 평가 항목 다섯이 전부 담당 컷을 갖는지, 주입 시연이 실제 벡터와 1:1인지, 화면에 나갈 조항 번호가 벡터 실측과 같은지까지 대조한다.

결함 주입 8종(길이 초과, 시작 시각 어긋남, 조항 오기, 벡터 누락, 배점 항목 삭제, 세부 합 불일치, 폴백 단계 제거, 촬영 규약 삭제) 전량에서 검출을 확인했다.

## 11. 0937 요구사항 대조

`project_docs/services/` — 0937 요구사항 대조표 · `0937_clauses.json` · `services_verify.py`

### 왜 이 문서가 필요했나

표준 3종 중 둘은 실행 가능한 준수 근거가 있다 — 통신 프로토콜은 골든 벡터 52건이, 데이터 모델은 스키마 제약 98건이 그 역할을 한다. **클라우드 서비스 표준만 요구사항 문서라 실행할 수 있는 것이 없다.** 그래서 조항 대 구현의 전수 대조표가 그 자리를 대신한다. 배점 최대 항목(표준 활용성 30점)의 근거 문서다.

서비스 요구사항 33건과 부속서 시나리오 31건을 전부 펼쳐 놓고, 각 조항에 담당 모듈과 구현 근거를 붙였다. 요구의 강도는 원문 종결어미를 그대로 옮겼다 — "해야 한다"와 "할 수 있다"를 임의로 뒤섞지 않는 것이 이 표의 신뢰성이다.

### 대조표를 쓰자마자 설계 오류가 하나 드러났다

아키텍처가 노드 속성 설정을 **데이터관리서비스**에 배정하고 있었다. 그런데 표준의 데이터관리서비스는 "공공데이터로부터 외부 데이터를 수집하는 서비스"이고, 노드 속성 설정은 **장치관리서비스**의 "설치·변경·삭제"다. 특히 수집 주기 설정은 장치관리서비스가 명시적으로 요구하는 항목이다.

**직전까지의 검증 79건이 전부 놓친 지점이다.** 문서 안에서는 한 모듈이 두 가지 일을 하는 것이 자연스러워 보였고, 조항을 하나씩 모듈에 대응시켜야만 정의문과의 충돌이 보였다. 배정을 옮기고, 같은 결정이 두 문서에 따로 적히지 않도록 대조표를 정본으로 선언했다.

### 범위 밖을 숨기지 않는다

6개 서비스 중 5개만 구현한다. 나머지 하나는 영농일지·경영정보를 다루는 농장 경영 서비스로, 이 프로젝트가 증명하려는 네 가지 주장 어디와도 접점이 없다. **다만 그 서비스의 데이터 기반은 이미 있다** — 농가·시설하우스·영역 식별자 체계는 데이터 모델 표준에서 이미 구현했다. "기반은 있고 업무 기능만 없다"가 정확한 서술이다.

부속서의 네 시나리오는 수동 ⊂ 원격 ⊂ 자동 ⊂ 써드파티로 누적된다. **자동제어까지가 대상**이고 써드파티 개방은 범위 밖이다. 여기서 얻은 것 하나 — 자동제어 시나리오가 *"위자드 선택 방식, 스크립트 입력 방식 등으로 제어 명령을 직접 만들어서 등록할 수 있어야 한다"*를 필수로 요구한다. **승인 게이트가 여기서 근거를 얻는다**: 표준이 요구하는 "사용자가 직접 만들어 등록"을 지키면서 AI를 붙이는 유일한 방법이다.

### 검증 후 세 건이 더 나왔고, 하나는 검증기 자신이었다

가장 무거운 지적은 **새로 만든 검증기가 대조표 한 파일만 읽는다**는 것이었다. 그러면 검사하는 것이 "문서가 자기 자신과 일치하는가"뿐이다. 실제로 요구 문구를 서로 바꾸거나, 존재하지 않는 컬럼을 근거로 적거나, 방금 고친 서비스 배정을 되돌려도 **전부 통과**했다.

독립 입력을 넷으로 늘렸다 — 표준 종결어미 발췌, 아키텍처 문서, 스키마, API 명세. 이제 근거로 적은 컬럼·경로·진입점이 실물에 있는지 기계가 찾는다.

나머지 둘도 이 보강에서 나온 것과 같은 종류다. **강도 분류 규칙에 "~가능해야 한다"가 빠져 있어** 7건이 잘못 올라갔고, **"테이블이 있으면 충족"으로 판정해** 6건의 근거가 비어 있었다. 인용한 컬럼 하나는 아예 실재하지 않았다. 판정 의미를 "설계가 닫혀 있다"로 다시 정의하고, 4건은 부분 충족으로 낮추고 2건은 설계 계약을 추가해 닫았다. 남은 것은 후속 과제로 근거와 우선순위를 붙여 열어 뒀다 — **검증기가 모든 부분 충족 항목이 후속 과제에 연결되는지 검사**하므로 방치되지 않는다.

## 12. 화면 설계

`project_docs/web/` — 화면 설계서 · `web_verify.py`

### 무엇을 했나

화면 넷을 설계했다. 앞선 세 문서가 각각 데이터·프로토콜·서비스를 정했다면, 이 문서는 **그것이 사람에게 어떻게 보이는지**를 정한다. 심사자가 실제로 보는 것은 화면이므로, 표준이 어디에 반영되었는지가 화면에서 보여야 한다.

### 빌드를 두지 않기로 했다

번들러도 외부 라이브러리도 쓰지 않는다. 공고문이 빌드 산출물 제외를 요구하고 재현성을 필수로 걸었으므로, **설치 단계가 하나 늘어나는 것 자체가 위험**이다. 차트도 라이브러리 없이 직접 그린다.

부수 효과가 더 크다 — **심사자가 화면 파일을 열면 소스가 그대로 보인다.** 화면의 조항 번호가 어디서 왔는지 추적하면 API 호출 한 줄에 닿는다. 번들된 코드였다면 이 추적이 끊긴다.

### 화면이 하지 않는 것을 먼저 정했다

위반 코드를 한국어로 바꾸는 표, 장치 종류 이름표, 비트 언팩 — 전부 화면에 두지 않는다. 하나라도 두면 표준 해석이 두 곳에 생기거나, 새 장치를 붙일 때 화면까지 고쳐야 한다. 여섯 가지 금지 각각에 **검사 방법**을 붙였다. 지킬 수 없는 금지는 적지 않는다는 뜻이다.

관측 화면 둘(대시보드·검증 뷰)에는 **쓰기가 아예 없다.** 상태를 볼 수만 있는 화면에서 상태를 바꿀 수단을 두지 않는 것이 승인 게이트의 전제다.

### 접근성이 기능의 성립 조건이다

평가 항목에 접근성이 15점 걸려 있지만, 그것과 무관하게 **검증 뷰는 위반을 색으로 표시한다.** 색에만 의존하면 색각 이상 사용자에게 정상과 위반이 구분되지 않고, 그 순간 이 기능은 아무 의미가 없어진다. 부가 기능이 아니라 성립 조건이다.

여덟 항목을 목표로 잡되 **기계로 확인할 수 있는 것만** 검사 대상에 넣었다. 근거 없이 "준수"를 주장하지 않기 위해서다. 명도대비는 실제로 계산한다 — 색을 고르다 대비가 무너지는 것이 가장 흔한 회귀다.

### 설정 화면을 넣어 부분 충족 세 건을 닫았다

앞 단계에서 부분 충족으로 남았던 셋(구역·주기 지정, 사용자 주기 지정, 알림 조건 지정)이 전부 같은 원인이었다 — **표준이 상정하는 설정 화면이 없었다.** 화면 하나와 쓰기 경로 하나를 추가해 셋을 닫았다.

대신 **그 경로가 제어값을 쓰지 못하게 막았다.** 표준의 장치 속성 여덟 필드 중 사용자가 정하는 넷만 받고, 제어값 필드는 스키마에서 원천 차단한다. 쓰기 경로가 하나 늘어난 만큼 승인 게이트 우회 가능성을 검사로 고정했다.

### 검증 — 55/55 통과

화면이 쓴다고 적은 API가 실제 명세에 있는지, 주입 시연 여덟 종이 골든 벡터와 1:1인지, 화면에 나갈 조항 번호가 벡터 실측과 같은지, 영상 컷 배정이 시연 시나리오와 맞는지를 대조한다.

### 검증 후 여덟 건 — 화면이 선언한 흐름에 HTTP 경로가 없었다

이 라운드는 성격이 달랐다. 앞 라운드들이 "문서 안의 수치가 어긋났다"였다면, 이번 지적 여덟 건 중 **치명 둘은 화면 설계서가 선언한 사용자 흐름에 대응하는 서버 경로가 아예 없다**는 것이었다.

**AI 초안 생성이 서버 실행이 아니었다.** 초안 생성 요청이 클라이언트가 이미 만든 문장을 받아 저장할 뿐이었다. 그러면 저장된 행만 봐서는 서버가 모델을 돌렸는지 사용자가 타이핑했는지 구별되지 않는다 — **생성형 AI를 활용했다는 주장의 근거가 데이터에 남지 않는다.** 요청 스키마에서 문장 필드를 조건부로 금지해 서버 실행 외의 경로를 막고, 실제로 어느 경로로 만들어졌는지(AI인지 임계값 폴백인지)를 별도 열로 남기게 했다. 요청자의 의도와 서버의 실행 결과는 갈릴 수 있으므로 두 값을 따로 둔다.

**규칙 거부가 어디에도 없었다.** 화면과 발표 시나리오는 "심사위원이 반려하는 장면"을 전제하는데 API에도 DB에도 거부 상태가 없었다. 표준의 자동제어 시나리오가 요구하는 "최종 의사결정 후 조정"에는 반려가 포함되며, **거부 사실이 남지 않으면 초안 직후와 반려 후가 구별되지 않아 사람 검토 지점이 기록으로 증명되지 않는다.** 영속 상태로 결정하고 불변 트리거를 붙였다.

**위반 주입 버튼도 마찬가지였다.** 브라우저가 로컬 파이썬 모듈을 호출할 방법은 없는데, 검증 화면의 쓰기 경로는 0개였다. 골든 벡터 여덟 종만 받는 열거형 요청으로 API를 신설하고, 실물 장비가 물린 모드에서는 거부하게 했다 — 자유 바이트열을 받으면 "주입 결과가 골든 벡터와 같다"는 판정 근거가 사라지고, 실측 라인에 합성 프레임을 얹으면 합성 데이터 금지에 직접 저촉된다.

### 이번에도 검증기 자신이 걸렸다

화면 검증기가 **설계서가 당시 적은 "경로 21종"을 통과시키면서 화면에는 "경로 20"을 출력하고 있었다.** 값을 읽어 놓고 대조를 하지 않았다. 존재하지 않는 스크립트를 로드한다고 적은 것도, 코드 예시가 없는 필드명을 읽는 것도 전부 통과했다.

**직전 라운드의 지적과 정확히 같은 부류다** — 검증기가 검증 대상 한 파일만 읽어 자기 자신과의 일치만 본다. 두 번째이므로 개발 규약에 규칙으로 올렸다: *"검증기는 검증 대상 파일 하나만 읽지 않는다. 적어도 하나의 독립 입력과 대조한다."* 독립 입력을 다섯으로 늘려 40 → **55종**.

### 수정 도중 나온 두 가지

**새로 넣은 DB 제약 하나가 무효였다.** "AI 초안이면 생성 경로가 있어야 한다"는 검사를 넣었는데, 생성 경로를 생략한 삽입이 그대로 통과했다. 원인은 SQL의 3치 논리다 — 값이 비어 있으면 `IN` 비교가 거짓이 아니라 **미정**이 되고, 미정으로 끝난 검사는 통과로 취급된다. **3차 검증에서 승인 게이트를 뚫었던 것과 같은 함정이다.** 비어 있지 않음을 앞에 두어 닫았다.

**반대로, 새로 넣은 제약 셋은 지울 근거가 나왔다.** 하나씩 제거해 보니 셋 다 어떤 시험도 실패시키지 못했다 — 이미 다른 제약이 덮고 있었다. 근거 없이 남기면 "제약 39개"가 실제 보장보다 부풀려진 숫자가 된다. 지우고 트리거를 **37개**로 줄였다. 남긴 제약은 제거 시 시험이 뒤집히는 것을 주입으로 확인했다.

여덟 건 전량 수정, 기각 0건.

### 한 번 더 — "required 는 키만 본다"

다음 검증에서 5건이 나왔고 **넷이 같은 형태였다.** 직전 라운드에서 스키마에 `required`·`oneOf`·`minProperties` 를 넣고 닫혔다고 선언했는데, **JSON Schema 의 `required` 는 키가 있는지만 보고 값이 비어 있어도 통과한다.**

그래서 `모델 식별자가 null 인 AI 초안 요청`, `대상이 null 인 설정 요청`, `원본 프레임이 빠진 오류 알림`이 전부 유효한 요청으로 남아 있었다. DB 도 같은 부류였다 — 사람이 만든 규칙에 "AI 가 생성했다"고 표시하는 것, 사유 없이 반려하는 것, 반려 사유를 나중에 바꾸는 것이 모두 가능했다. **거부 기록이 곧 "사람이 검토했다"의 증거인데, 그 증거가 위조 가능한 상태였다.**

분기마다 값의 타입까지 좁히고, 응답에서는 생성 경로와 승인·거부 기록을 **비어 있더라도 반드시 실어 보내게** 했다. 필드를 통째로 빼면 화면이 "경로 미상"과 "값이 없음"을 구별하지 못하고, 구현이 빠뜨려도 계약 위반이 아니게 된다. DB 에는 불변식 3종을 더했다.

### 검증기가 걸린 것은 이번이 세 번째다

다섯 번째 지적이 다시 검증기 자신이었다. 위 네 건이 전부 실재하는데도 API 60/60 · 웹 55/55 · 메타 47/47 이었다. **검사가 "키워드가 있는가"만 보고 "그 키워드가 무엇을 막는가"를 보지 않았기 때문이다.**

정상값과 반례를 **쌍으로 넣어보고 판정을 대조하는 매트릭스 43종**으로 바꿨다. 그런데 여기서 함정이 하나 더 나왔다 — **의존성을 늘리지 않으려고 직접 만든 스키마 검사기가 필요한 키워드 다섯 개를 구현하지 않고 있었다.** 그 상태로는 미구현 키워드가 조용히 통과로 바뀐다. 바로 그것이 이번 네 건이 통과한 이유였다.

다섯을 구현하고, **표준 라이브러리가 설치돼 있으면 같은 매트릭스를 한 번 더 돌려 판정이 일치하는지 대조**하게 했다. 43종 전량 일치했다. 설치돼 있지 않으면 **생략했다는 사실을 결과에 남긴다** — 조용히 건너뛰면 녹색 결과의 의미가 달라진다.

문서 수치 대조는 대상 목록을 지정하던 방식이 이번에 목록에 없던 문서를 놓쳐, **설계 문서 전체를 훑는 방식**으로 바꿨다. 역사적 전이 수치는 지우지 않고 시점 표시로 구분한다.

다섯 건 전량 수정, 기각 0건. 검증 규모는 **DB 제약 98종 · 계약 56종 · API 71종 · 화면 62종 · 펌웨어 50종 · 서비스 42종 · 시연 31종 · 골든 29종 · 메타 52종**이며, 결함 주입 19종 전량에서 검출을 확인했다.

### 지금 있는 검증기는 전부 설계 문서용이다

이것이 착수 전에 짚어야 했던 문제다. 아홉 개 검증기는 `openapi.json`을 검사하지 서버 라우트를
검사하지 않고, `schema.sql`을 검사하지 실제 DB를 검사하지 않는다. **코드가 설계와 같은지를
보는 검증기는 아직 하나도 없다.**

그래서 단계마다 하나씩 신설한다. 이것들이 곧 **이 프로젝트가 반드시 성립해야 한다고 선언한
주장 넷의 기계 판정**이 된다.

| 주장 | 판정 방법 |
|---|---|
| MCU 3종이 동일 프로토콜로 혼용 동작 | `core/` 오브젝트 해시 3종 동일 · 보드 판별 매크로 0개 · C↔Python 골든 52건 바이트 일치 |
| 하드웨어 없이 표준 준수를 검증 | 외부 도구 의존 0 · 네트워크 없이 `replay`/`simulate` 왕복 |
| 노드 추가 시 서버 코드 수정 0줄 | `backend/`에 장치 종류 문자열 하드코딩 0 |
| 표준의 실구현 장애 지점을 발견·해소 | 표준결함 19건 (이미 문서로 확정) |

**검증기 자신도 검증 대상이다.** 설계 단계에서 검증기 결함이 네 번 나왔으므로(초안 검증기의
거짓 통과 → 자기 자신과의 일치만 검사 → 존재 확인만으로 통과 → 미구현 키워드가 통과),
개발 단계 검증기에도 같은 규칙 넷을 그대로 건다. 단계 종료 전에 **고친 것을 되돌려 실패하는지**
반드시 확인한다.

### 독립 검증 환경의 능력을 먼저 확인한다

검증자는 AI 제품명만 보고 C 컴파일·이미지 해석·브라우저 렌더링·하드웨어 접근 가능 여부를 가정하지 않는다. 세션에서 각 능력을 실제로 확인하고, 가능한 검사는 직접 실행하며, 불가능한 항목은 이유와 함께 `검증 불가`로 남긴다.

제출물에는 **출구 명령의 실행 로그와 컴파일 로그 원문**도 보존한다. 다만 독립 검증자는 실행 가능한 환경에서는 제출 로그를 통과 근거로 대신 쓰지 않고 명령을 직접 실행한다.

### 일정과 축소 순서

마감까지 17일이고 여유가 0이다. 그래서 **무엇을 먼저 자를지**를 미리 정해 두었다 —
지연이 발생한 시점에 정하면 판단이 급해진다.

먼저 자를 것은 데모 경로 밖의 확장성 검증 노드, 그다음이 표준 개정 제안 벡터의 구현 반영,
설정 화면의 쓰기 기능 순이다. **절대 자르지 않는 것**은 골든 52건 양쪽 통과, 위반 8종 판정과
조항 번호 화면 출력, 승인 게이트, 재현 모드 둘, 오프라인 설치다. 이 다섯 중 하나라도 빠지면
출품의 근거 자체가 성립하지 않는다.

### 검증 — 35/35 통과

지시서도 검증 대상이다. 단계표와 상세 절이 같은 집합인지, 신설 검증기 목록이 세 곳에서
일치하는지, **출구 조건이 인용한 통과 건수가 실제 실행 결과와 같은지**, 축소 대상이 실재하는
산출물인지, 일정이 마감을 넘지 않고 모든 단계가 배정됐는지를 기계가 본다.
결함 주입 15종 전량에서 검출을 확인했다.
